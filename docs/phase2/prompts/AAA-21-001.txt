# 10. NÃO EXECUTAR O HARNESS DIRETAMENTE NO HTTP

Regra arquitetural:

HTTP ingestion NÃO deve ser a autoridade de execução do agente.

Fluxo desejado:

HTTP
 ↓
persist
 ↓
enqueue
 ↓
return 202

Depois:

worker
 ↓
claim
 ↓
execute.

Isso permite:

- crash recovery;
- retry;
- backpressure;
- replay safety;
- horizontal workers;
- auditabilidade.

# 15. IDEMPOTENCY

Prove idempotência de entrada.

tenantId + idempotencyKey

→ returns existing execution

ou comportamento equivalente.

Não teste apenas sequencialmente.

# 17. WORKER CLAIMING

Implemente claiming seguro.

Objetivos:

- dois workers não executam o mesmo job simultaneamente;
- claim possui ownership;
- claim pode expirar;
- crash não deixa trabalho perdido;
- stale claim pode ser recuperado.

Considere:

SELECT ... FOR UPDATE SKIP LOCKED

ou mecanismo existente equivalente.

Não force implementação se já houver solução melhor.

---

# 18. LEASE / FENCING

Para efeitos de maior risco, avalie lease/fencing.

Se necessário, implemente:

lease owner
lease generation/fencing token
lease expiration

Um worker antigo que perdeu lease NÃO deve conseguir publicar efeito
posteriormente como se ainda fosse proprietário.

Se não for necessário nesta fase, documente por que.
