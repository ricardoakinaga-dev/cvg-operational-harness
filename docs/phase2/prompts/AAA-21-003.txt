# 91. SCHEMA INVARIANTS

Defina invariantes importantes no banco quando possível.

Exemplos:

- execution_id único;

- state válido;
- attempt >= 0;
- effect identity única no escopo correto;
- approval vinculada ao tenant correto;
- timestamps coerentes.

Não dependa exclusivamente da aplicação para invariantes que podem ser
garantidos com segurança pela persistence layer.

Teste violações relevantes.

# 92. OPTIMISTIC / PESSIMISTIC CONCURRENCY

Analise onde utilizar:

Não aplique locks indiscriminadamente.

Documente especificamente para:

execution state transition
worker claim
approval consume
effect journal
idempotency registration.

Evite:

read
→ modify in memory
→ blind write

quando concorrência puder produzir lost update.

# 93. EXECUTION VERSION / CAS

Quando apropriado, adicione mecanismo equivalente a:

version
revision
updated_at guard

para evitar transições concorrentes silenciosas.

Exemplo conceitual:

UPDATE executions
SET state = ...
WHERE execution_id = ?
AND version = ?

Se zero rows forem alteradas:

STATE_CONFLICT.

Não force CAS se a transação/locking existente já garantir corretamente.

# 94. STATE TRANSITION AUTHORITY

Não permita que qualquer package escreva livremente:

# 95. TERMINAL STATE IMMUTABILITY

ou semântica explicitamente separada.

Não mutacione história.

# 96. RESULT / EFFECT CONSISTENCY

Defina invariantes entre:

execution terminal result

e:

effect journal.

Exemplo:

UNKNOWN
STARTED
FAILED

sem explicação semântica.

Crie verificações/testes.

# 97. UNKNOWN EFFECT OUTCOME

Trate explicitamente o caso difícil:

Tool chamou serviço externo
→ conexão caiu
→ não sabemos se o serviço executou.

Não classifique automaticamente como:

FAILED_SAFE_TO_RETRY.

Crie estado/erro equivalente a:

EFFECT_OUTCOME_UNKNOWN

quando necessário.

Estratégias possíveis:

- provider idempotency key;
- reconciliation;
- external lookup;
- manual intervention;
- terminal uncertainty.

Documente a garantia real.

# 110. EVENT HISTORY

Avalie se execution precisa de uma timeline durável.

Documente diferença entre:

---

# 111. OUTBOX IS NOT AUDIT

Não trate outbox como trilha de auditoria.

Outbox responde:

"o que precisa ser entregue/processado?"

Audit responde:

"o que aconteceu e por quê?"

Execution state responde:

"em que estado estamos?"

Essas responsabilidades devem permanecer distintas.

---

# 112. EFFECT JOURNAL IS NOT AUDIT

Effect Journal responde:

"qual efeito tentamos/executamos e com qual identidade?"

Audit responde:

"qual decisão e sequência levaram a isso?"

Não misture.
