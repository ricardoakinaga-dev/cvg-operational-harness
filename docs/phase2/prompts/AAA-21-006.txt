# 276. WORK EXECUTION STRATEGY

Antes de implementar, produza internamente um plano de execução.

Divida o trabalho em lanes não sobrepostas sempre que possível:

LANE A — Architecture / Contracts
LANE B — Persistence / Migrations
LANE C — HTTP Ingestion
LANE D — Worker / Claim / Lease
LANE E — Runtime Composition
LANE F — Effect Journal / Idempotency
LANE G — Approval / Resume
LANE H — Audit / Telemetry
LANE I — Integration Tests / Fault Injection
LANE J — Security / Critic / Evidence

Não permita que múltiplos builders alterem os mesmos arquivos sem coordenação.

Se utilizar subagentes:

- defina ownership explícito;
- defina arquivos permitidos;
- exija relatório de mudanças;
- integre somente após revisão.

---

# 277. SCOUT BEFORE BUILD

Antes de alterar cada subsistema crítico, faça reconnaissance do código real.

Especialmente:

- persistence atual;
- outbox atual;
- worker atual;
- Runtime V1;
- approval engine;
- effect journal;
- audit;
- telemetry;
- Model Gateway;
- API server;
- existing migrations.

Não reconstrua uma solução paralela quando já houver uma implementação
adequada.

Regra:

REUSE
→ ADAPT
→ EXTRACT
→ ONLY THEN CREATE NEW.

---

# 278. NO DUPLICATE SUBSYSTEMS

Não termine a Phase com:

old outbox + new outbox
old execution state + new execution state
old approval lifecycle + new approval lifecycle
old effect journal + new effect journal

sem uma decisão explícita.

Se coexistência temporária for inevitável:

declare:

CANONICAL
LEGACY
DEPRECATED

e adicione migration/removal plan.

---

# 279. CANONICAL AUTHORITY MAP

Ao final deve existir apenas uma autoridade canônica para cada responsabilidade:

Execution state
→ one authority

Queue/outbox
→ one canonical mechanism

Worker claim
→ one mechanism

Policy
→ one authority

Approval
→ one authority

Tool execution
→ one governed path

Model access
→ one Model Gateway

Audit
→ one canonical evidence path.

Evite arquitetura ambígua.

---

# 280. MIGRATION-FIRST DISCIPLINE

Quando persistence mudar:

1. definir schema;
2. definir invariants;
3. criar migration;
4. testar migration;
5. implementar repository;
6. implementar service;
7. integrar Worker;
8. integrar HTTP.

Não começar pela rota HTTP e improvisar persistence depois.

---

# 281. CONTRACT-FIRST DISCIPLINE

Quando boundary pública mudar:

1. definir contrato;
2. validar compatibilidade;
3. escrever teste;
4. implementar;
5. integrar.

Evite espalhar objetos ad hoc entre layers.

---

# 282. FAILURE-FIRST DISCIPLINE

Para cada novo fluxo crítico, desenhe primeiro:

happy path
failure before effect
failure after effect
duplicate
restart
concurrency.

Só considerar o fluxo concluído depois desses casos.

---

# 283. CRASH BEFORE OPTIMIZATION

Prioridade:

correctness
→ durability
→ recoverability
→ observability
→ performance.

Não sacrifique garantia de execução para reduzir alguns milissegundos nesta fase.

---

# 284. DATABASE CONSTRAINTS AS DEFENSE

Sempre que uma invariância crítica puder ser reforçada corretamente no banco,
considere fazê-lo.

Exemplos:

unique tenant/idempotency scope
unique effect identity
valid foreign keys
version constraints.

Aplicação + DB devem se complementar.

---

# 285. DO NOT HOLD DATABASE TRANSACTION ACROSS LLM

Não mantenha uma transaction SQL aberta enquanto:

Model Gateway aguarda provider

ou:

Tool externa aguarda rede

salvo justificativa arquitetural extraordinária e documentada.

Use state transitions + leases + journal.

---

# 286. EFFECT EXECUTION PROTOCOL

Para side effect governado, modele explicitamente um protocolo seguro.

Exemplo conceitual:

1. validate tool invocation
2. authorize
3. bind approval if required
4. create/claim effect journal entry
5. execute with idempotency identity
6. record external reference/result
7. mark effect completed
8. persist runtime outcome
9. audit causal events.

Considere falha em cada fronteira.

---

# 287. SIDE EFFECT AUTHORITY

Somente o componente governado de Tool Execution pode iniciar side effect.

Persistence não executa efeito.

Worker não executa efeito.

Orchestrator não executa efeito.

Model não executa efeito.

HTTP não executa efeito.

---

# 288. TOOL EXECUTOR CONTRACT

Se necessário, formalize:

ToolExecutor.execute(invocation)

com:

execution identity
tenant
tool identity/version
validated payload
authorization evidence
idempotency identity
deadline/abort context
trace context.

Não passe objeto gigante com dependências internas arbitrárias.

---

# 289. TOOL RESULT CONTRACT

ToolResult deve distinguir, quando necessário:

SUCCESS
FAILED
OUTCOME_UNKNOWN

e fornecer:

safe output
external reference
effect metadata.

Não force Tool a fingir certeza que não possui.

---

# 290. EFFECT JOURNAL STATE MACHINE

Formalize estados conceituais como:

PREPARED
IN_FLIGHT
SUCCEEDED
FAILED
UNKNOWN

ou equivalentes.

Defina transições válidas.

Teste:

duplicate start
duplicate completion
unknown recovery
terminal immutability.

---

# 291. IDEMPOTENCY LAYERS

Documente as diferentes idempotências:

REQUEST IDEMPOTENCY
→ evita duplicar execution.

EVENT IDEMPOTENCY
→ evita processar mensagem durável duas vezes semanticamente.

TOOL/EFFECT IDEMPOTENCY
→ evita duplicar side effect.

APPROVAL IDEMPOTENCY
→ evita consumir aprovação repetidamente.

Não trate uma única idempotency key como solução universal.

---

# 292. EXECUTION ATTEMPT IDENTITY

Cada retry técnico deve poder ser distinguido.

Considere:

executionId
+
attemptNumber

ou:

attemptId.

Audit deve conseguir mostrar:

Execution X
Attempt 1 failed
Attempt 2 succeeded.

---

# 293. CLAIM IDENTITY

Claim deve possuir identidade suficiente para detectar Worker antigo.

Exemplo:

claimId
workerId
leaseVersion.

Não confie apenas em:

state = RUNNING.

---

# 294. WORKER IDENTITY

Cada Worker process deve possuir identificador efêmero único.

Use para:

claims
logs
telemetry
debugging.

Não use hostname sozinho como garantia de unicidade.

---

# 295. WORKER PROCESS MODEL

Documente se Worker:

polls continuously
processes one
processes batch
uses concurrency pool.

Escolha modelo simples e previsível.

---

# 296. POLLING STRATEGY

Se usar PostgreSQL polling:

- bounded interval;
- backoff quando vazio;
- shutdown-aware;
- não busy-loop.

Se infraestrutura existente tiver mecanismo melhor, preserve.

---

# 297. QUEUE VISIBILITY

Deve ser possível obter ao menos operacionalmente:

queued count
running count
retryable count
waiting approval count
failed count.

Não precisa criar UI.

Query/metric é suficiente.

---

# 298. STUCK EXECUTION DETECTION

Defina critério para detectar:

RUNNING além do lease/deadline esperado.

Não deixe "RUNNING para sempre" sem mecanismo de identificação.

---

# 299. STUCK EXECUTION RECOVERY

Determine:

reclaim
fail
quarantine

dependendo de estado/effect uncertainty.

Não requeue cegamente.

---

# 300. APPROVAL IS A DURABLE EVENT

Approval não deve existir apenas em memória ou request context.

Deve ser persistida com:

consumed state.

# 301. APPROVAL CONSUMPTION ATOMICITY

Dois Workers não podem consumir a mesma approval para efeitos independentes.

Prove concorrência.

quem aprovou

→ terminal/quarantine
→ no further automatic claim.

# 319. TERMINAL ERROR PRESERVATION

Preserve último erro seguro e classificação.

Não sobrescreva causa original com erro secundário de cleanup sem necessidade.

---

# 320. MULTIPLE FAILURE CAUSALITY

Quando:

Audit also fails,

Não perca causalidade.

---

# 321. CLEANUP FAILURE

---

# 322. AUDIT ORDER TEST
