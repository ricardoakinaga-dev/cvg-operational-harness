# 198. PASS CRITERIA

Phase 2 só pode receber PASS se, no mínimo:

- canonical HTTP path existe;
- persistence durável existe;
- Worker canônico existe;
- Harness public composition é usada;
- Runtime V1 é executado pelo Worker;
- policy é aplicada;
- Tool não pode bypassar governança;
- idempotency é provada;
- effect journal é provado;
- approval pause/resume é provado;
- audit é durável;
- telemetry existe;
- tenant isolation é provada;
- worker restart é provado;
- nenhuma regressão nova existe;
- testes críticos são não-flaky;
- PostgreSQL real participa das provas de durabilidade.

Se alguns requisitos estruturais passarem mas a infraestrutura real não
puder ser provada:

CONDITIONAL_PASS.

---

# 199. FAIL CRITERIA

Marque FAIL se ocorrer qualquer um:

- efeito duplicado em cenário que deveria ser idempotente;
- cross-tenant leakage;
- approval bypass;
- policy bypass;
- lost durable work;
- terminal state inconsistente;
- Worker duplo produz efeito duplicado;
- crash deixa corrupção não recuperável;
- nova regressão crítica;
- audit afirma evento que não ocorreu;
- evidência fabricada/inconsistente.

---

# 200. PRODUCTION GO CRITERIA

Não confunda Phase PASS com Production GO.

Production GO exige evidência adicional de:

real PostgreSQL
backup/restore
load
performance
operational runbook
monitoring/alerting
provider certification
deployment certification
security closure
incident recovery.

Se não provado:

PRODUCTION = NO_GO.

# 201. INDEPENDENT CRITIC

O crítico NÃO deve ser o mesmo agente lógico responsável pela implementação,
quando o ambiente de orchestration permitir separação.

O crítico deve tentar REJEITAR o candidato.

Avaliar:

- evidence validity;
- canonical path reality;
- hidden bypasses;
- race conditions;
- idempotency;
- effect uncertainty;
- crash recovery;
- approval resume;
- tenant isolation;
- false PASS claims;
- architecture drift.

Produza:

docs/phase2/evidence/INDEPENDENT_CRITIC.md

APPROVE
REJECT.

# 202. CRITIC QUESTIONS

O crítico deve responder no mínimo:

Q1. O HTTP realmente não executa o agente inline?

Q2. O trabalho sobrevive a restart?

Q3. Dois Workers podem executar o mesmo efeito?

Q4. Duplicate HTTP request produz duplicate effect?

Q5. Crash depois do side effect é seguro?

Q6. Approval sobrevive a process restart?

Q7. Policy pode ser bypassada?

Q8. Tool execute vazou para Orchestrator?

Q9. Model pode autorizar a própria ação?

Q10. Tenant A consegue tocar estado de B?

Q11. Audit corresponde à causalidade real?

Todos devem ter:

PASS
FAIL
NOT_PROVEN.
