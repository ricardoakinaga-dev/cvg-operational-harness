# SPEC0229 — Contrato inicial de qualificação Claude100

Task `C100-Q01-QUALIFIER-001`, ligada a C100-G04/Q01. Data17/10/2026. Estado `DRAFT_FOR_INDEPENDENT_REVIEW / HUMAN_T3_REVIEW_PENDING / BUILD_NOT_AUTHORIZED`.

Esta unidade especifica o verificador e o protocolo de evidência da primeira medida. A trilha do cartão Q01 é **T3**; o pedido de implementar o programa preserva a revisão explícita desta SPEC antes de código. Implementação após aprovação: `tests/claude100/qualification/**` e `scripts/claude100-qualify.mjs`, com testes próprios no primeiro diretório. Um manifesto privado local pode existir dentro de tests, sem novo workspace/export público de aplicação. Sem root package/lock, banco, install ou import de produto. Reusar kitQ03 quando qualificado; nenhum clone de normalizador. Preparar driver Claude apenas após recon de porta real: esta SPEC não autoriza assumir uma API keyless inexistente nem importar código do executável.

O primeiro artefato é um **validador de evidência e comparador**, sem produzir `PASS_CURRENT` por conta própria. Consome uma execução registrada pelo operador de captura e uma regra congelada por cenário. Diferencial com captura funcional ausente devolve `BLOCKED_REFERENCE`. Controles de parser/esquema com dados sintéticos podem passar como testes do comparador, identificados como tal; nunca são um par referência/CVG conhecido correto funcional.

## Interface local e limites

CLI proposta: `node scripts/claude100-qualify.mjs --manifest <arquivo> --catalog <arquivo> --rule <arquivo> --capture-index <arquivo> --authority-index <arquivo> --evidence-root <diretorio> --out <diretorio>`. Todas as sete opções são obrigatórias, estritas, sem duplicatas e sem argumentos posicionais. Inputs são caminhos de dados, nunca código, módulo, shell, URL, regex ou comando. Execução somente em diretório de evidências próprio; escrita com criação exclusiva, sem sobrescrever captura/receipts anteriores. Caminho real deve permanecer sob o root de evidências declarado pelo operador; recusar symlink, traversal e arquivos especiais. Conservar handles abertos e ler/hash os mesmos bytes, sem reabrir por nome entre validação e uso; troca de arquivo no intervalo não pode trocar o conteúdo comparado.

Limites: catálogo1MiB, regra128KiB, manifesto256KiB, cada índice1MiB, cada receipt1MiB, cada artefato bruto/expectedArtifact4MiB,32artefatos por lado e32entradas por índice. Total64MiB inclui todos os inputs, índices, receipts, artefatos e expectedArtifact, contado uma vez por arquivo físico. JSON UTF-8 estrito sem chaves duplicadas, número não finito, campo desconhecido nos envelopes de controle, profundidade superior a64 ou string acima de64KiB. Arquivo maior falha antes de parse. Arrays preservam ordem; entradas inválidas não são truncadas nem omitidas. Digest é SHA-256 dos bytes brutos e SHA-256 canônico dos objetos validados. Regra version1 seleciona exclusivamente CVG-CANON-1, definido no apêndice normativo; versão desconhecida não escolhe outro algoritmo implicitamente.

Nenhuma execução de processo/modelo/rede é admitida pelo manifesto ou regra. Captura funcional é tarefa separada de driver com contrato de processo e autorização próprios. O comparador não acessa homes/configurações reais, `.env`, secret store ou serviços.

## Dados fechados

`manifest.version=1`, `runId`, `scenarioId`, `requirementIds`, `catalogSha256`, `ruleSha256`, `fixtureSha256`, `createdAt`, `reference`, `cvg`, `captureAttestations`. IDs são strings não vazias limitadas a128caracteres ASCII alfanumérico/underscore/hífen/ponto; requisito precisa existir no catálogo e pertencer à regra. Sem IDs duplicados, requisitos extras ou variante desconhecida.

Cada lado registra somente `identity`, `artifacts` e `execution`, nos formatos exatos do apêndice. `artifacts` contém somente `path`, `sha256`, `bytes`, `role` (`RAW_INPUT`, `RAW_STDOUT`, `RAW_STDERR`, `RAW_EVENTS`, `RAW_STATE`, `RAW_EFFECTS`). Paths relativos únicos, todos os arquivos declarados e nenhum substituto por texto esperado. RAW_INPUT é obrigatório e contém os bytes da fixture realmente consumida pelo driver, com sha256 igual a fixtureSha256; o driver revisado deve provar a relação dessa entrada com os requests nativos preservados. Timeout/infra nunca se comparam como sucesso funcional.

`captureAttestations` referencia registros externos à captura com lado,runId,scenarioId,identidade,digests dos artefatos e identidade do operador/coletor. O comparador recebe um inventário de capturas confiáveis fornecido separadamente pelo Lead; um manifesto não pode acrescentar sua própria origem confiável. Hash vincula conteúdo, não autentica o autor. Sem correspondência exata a uma captura observada por REA ou coletor revisado, estado `UNTRUSTED_CAPTURE`. Não ler decisões de autoridade de um campo controlado pela própria fixture. O inventário do Lead é insumo hash-bound registrado no pacote da revisão e só deriva de capturas realmente executadas; não é credencial de aplicação.

`capture-index` tem somente `version=1`, `catalogSha256`, `entries`. Cada entrada tem `captureId`, `collectorId`, `runId`, `scenarioId`, `side` (`reference|cvg`), `identitySha256`, `artifactSetSha256`, `receiptPath`, `receiptSha256`. `captureAttestations` contém somente os dois captureIds pertinentes (um no casoCVG_CONTROL). Recusar duplicatas/ambiguidade. O conjunto de artefatos é a lista canônica ordenada por path dos registros declarados; as leituras efetivas devem corresponder integralmente. Receipt externo é envelope fechado de captura, não texto de autorização nem código: `version=1`, `captureId`, `collectorId`, `runId`, `scenarioId`, `side`, `fixtureSha256`, `ruleSha256`, `identity`, `execution`, `artifacts`. Todos os campos consumidos do manifesto devem ser canonicamente iguais aos do receipt confiável, inclusive fixture/input, status de execução, timeout, exitCode, identidade e lista completa de artefatos; os índices redundantes de identity/artifactSet também devem coincidir. O hash bruto do receipt vem do índice separado do Lead. Alterar somente execution ou fixtureSha256 mantendo bytes/índice originais devolve UNTRUSTED_CAPTURE, não MATCH. Manifesto/catalog/regra não podem fornecer o índice nem alterar suas entradas durante a execução.

`authority-index` tem somente `version=1`, `catalogSha256`, `entries`. Cada entrada tem `decisionId`, `scopeId`, `ruleSha256`, `specPath`, `specSha256`, `decisionReceiptPath`, `decisionReceiptSha256`, `decision` (`APPROVED|DENIED|PENDING`), `expiresAt` (UTC ou null). A referência de equivalência da regra é um decisionId único; `scopeId` precisa ser o scenarioId exato. Só APPROVED atual e vínculos íntegros admitem comparação. Autoridade ausente, negada, expirada ou para outro cenário devolve `BLOCKED_CVG_SPEC`. O Lead fornece esse índice após conferir a decisão real do usuário/escopo; um bool na fixture ou no relatório não a substitui. Os dois índices, seus digests e a origem do pacote do Lead são insumos obrigatórios da revisão independente, e a cópia consumida deve ficar imutável na evidência. A fronteira de confiança é o operador/revisor desse pacote local, não um assinante remoto ou uma credencial de runtime; adicionar autenticação distribuída requer outra SPEC.

Regra por cenário: `version=1`, `scenarioId`, `requirementIds`, `verificationClass`, `equivalenceDecisionRef`, `requiredRoles`, `projection`, `assertions`, `normalizationPolicy`, `expectedExecution`; o único campo adicional permitido é `expectedArtifact`, obrigatório somente paraCVG_CONTROL e proibido paraFUNCTIONAL_PARITY. Não há regra implícita por título. `verificationClass` é `FUNCTIONAL_PARITY|CVG_CONTROL` e deve coincidir com cada requisito; separar regras se houver classes diferentes. ControleCVG tem reference=null no manifesto, mas exige SPEC e autoridade aprovadas verificáveis no pacote do Lead.

`projection` enumera campos e transformações finitas revisadas por cenário; nenhuma expressão executável. Nesta primeira unidade, suportar apenas `EXACT_JSON` (documentos completos) e `EXACT_BYTES`. Outras relações semânticas permanecem `UNSUPPORTED_RULE` até SPEC própria aprovada. As únicas assertions são igualdade exata, quantidade e ordem exatas de eventos/efeitos e igualdade de relações de identidade declaradas. Não inferir sucesso de texto livre do modelo. Formatos entre Claude e CVG incompatíveis ainda precisam de adapter/projeção de cenário posterior: não os declarar equivalentes nesta unidade.

Forma fechada desta versão: `projection={kind,referenceRole,cvgRole}`, com kindEXACT_JSON ouEXACT_BYTES e roles do enum de artefatos. ParaCVG_CONTROL, referenceRole é null e a regra exige um `expectedArtifact` separado, com path/hash/bytes no pacote de autoridade aprovado; não é uma resposta de referência fabricada. Cada lado tem no máximo um artefato por role; role ausente/ambígua falha. `requiredRoles` é a lista sem duplicatas dos roles presentes exigidos, e todos são verificados por integridade, mesmo que não sejam a projeção principal. `assertions` tem nesta versão somente `[{kind:"EQUAL_COMPLETE"}]`: comparação integral inclui quantidade e ordem do documento selecionado. Comparação de contagem, vínculo ou predicado em outro documento requer regra adicional explícita, não expressão inventada dentro da fixture. Normalização só se aplica aEXACT_JSON cujo documento seja array de envelopes; política não vazia com outro documento ouEXACT_BYTES é inválida. Rejeitar campos adicionais em todos os envelopes de controle; o JSON bruto de eventos/payloads permanece dado completo e não perde campos por ser desconhecido do comparador.

`normalizationPolicy` reutiliza o contrato fechado do kitQ03; padrão identidade. Somente metadados de envelope declarados, com namespaces que preservem igualdade/distinção. Nunca normalizar conteúdo, tenant, efeito, approval, erro, operação, custo ou contadores. Para todo controle de autoridade/efeito, verificar bruto antes de projeção. Chave desconhecida da regra ou normalização falha; nenhuma seleção que descarte evento extra.

## Apêndice normativo — wire version1

Todos os campos a seguir são obrigatórios, salvo null e expectedArtifact explicitamente indicados. Objetos fechados recusam extras. IDs seguem a regra ASCII de128caracteres; digest é string hexadecimal minúscula de64caracteres. Paths são relativos ao evidence-root e sujeitos às regras físicas anteriores. UTC é string ISO exata `YYYY-MM-DDTHH:mm:ss.sssZ`, validada por roundtrip e início≤fim. Nenhum default altera um dado ausente.

| Objeto                     | Campos exatos e tipos                                                                                                                                                                                                                                                                  |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| identity LOCAL_BINARY      | kind literalLOCAL_BINARY; version string1–128; artifactSha256,configSha256,driverSha256 digests                                                                                                                                                                                        |
| identity CVG_SOURCE        | kind literalCVG_SOURCE; commit stringhex40ou64; sourceSha256,configSha256,schemaSha256,driverSha256 digests; imageSha256 digestou null                                                                                                                                                 |
| identity REMOTE_SERVICE    | kind literalREMOTE_SERVICE; serviceId,region,testProfileId IDs; clientSha256,configSha256,driverSha256 digests; build string1–128ou null; `observedAt` tipoUTC                                                                                                                         |
| execution                  | `startedAt`,`endedAt` tipoUTC; exitCode inteiro0..255 ou nullsomenteINFRA_FAILURE; timeout boolean; outcomeKindSUCCESS,PRODUCT_FAILUREouINFRA_FAILURE. SUCCESS requer exitCode0 e timeoutfalse; PRODUCT_FAILURE requer exitCode1..255 e timeoutfalse; timeouttrue exige INFRA_FAILURE. |
| expectedExecution da regra | reference e cvg; cada um tem somente outcomeKindSUCCESSouPRODUCT_FAILURE e exitCode compatível com a regra de execution. reference=nullsomenteCVG_CONTROL. Não se autoriza INFRA_FAILURE como resultado esperado.                                                                      |
| expectedArtifact           | path,sha256,bytes inteiro0..4MiB. Arquivo separado do pacote de autoridade; não pertence ao lado referência.                                                                                                                                                                           |
| artifact                   | path,sha256,bytes inteiro0..4MiB,role do enum. No máximo um por role por lado; paths únicos e lista ordenada lexicograficamente por path no manifesto/receipt.                                                                                                                         |
| captureAttestations        | array de captureIds únicos em ordemreference,cvg; somentecvgparaCVG_CONTROL                                                                                                                                                                                                            |

No manifesto, reference aceita LOCAL_BINARY ouREMOTE_SERVICE, ou null para registrar referência ausente; emFUNCTIONAL_PARITY esse null conduzBLOCKED_REFERENCE, emCVG_CONTROL é obrigatório. A chave reference continua obrigatória: omiti-la é INVALID_INPUT. cvg aceita somenteCVG_SOURCE. Identidade de serviço com buildnull é captura datada com limitação explícita; não comprova versão estável do SaaS. Cada índice tem entradas únicas por ID e pela chave run/scenario/side ou decisionId, conforme aplicável. DecisionAPPROVED requer bytes daspec/receipt íntegros e expiresAtnull ou futuro tanto no início quanto na emissão do relatório; DENIED/PENDING nunca permitem MATCH. A igualdade com expectedExecution é exigida além da igualdade dos documentos projetados.

**CVG-CANON-1:** validar JSON simples pelo contrato do kitQ03; ordenar chaves de cada objeto pela comparação UTF-16 de `Object.keys(...).sort()` doJavaScript; serializar chaves e escalares com JSON.stringify, sem whitespace; arrays mantêm ordem; não normalizar Unicode; número finito usa JSON.stringify, incluindo -0→0. Hash SHA-256 dos bytesUTF-8 dessa string. Campos de controle não são omitidos por undefined porque undefined é inválido. version1 do rule/receipt/índices seleciona este algoritmo, sem campo implícito extra. Exemplo: `{"b":[true,null],"a":1}` produz exatamente `{"a":1,"b":[true,null]}`; chave duplicada ou NaN é inválido antes da canonicalização. Isto define algoritmo local, sem alegar conformidade com padrão externo.

**Relatório version1:** somente `version=1`, `runId` (IDou null se input inválido), `scenarioId` (IDou null), `requirementIds` (lista validada ou vazia), `status` do enum fechado, `exitCode`0/1/2, `inputs`, `identities`, `checks`, `diffs`, `evidence`, `limitations`, `reviewStatus` literalPENDING. `inputs` tem somente manifestSha256,catalogSha256,ruleSha256,captureIndexSha256,authorityIndexSha256 (digestou null se indisponível). `identities` tem referenceSha256 e cvgSha256 (digestou null). `checks` é array de `{id:ID,status:PASS|FAIL|NOT_RUN,message:string≤1024}`; mensagens não concedem autoridade. `diffs` é array de `{role:roleEnum,location:string≤1024,kind:MISSING|EXTRA|VALUE,referenceDigest:digest|null,cvgDigest:digest|null}`. `evidence` tem reference e cvg (listas deartifact, vazias se ausentes), normalized(lista deexpectedArtifact com outputs materializados no diretório novo). `limitations` é lista não vazia de strings≤1024, incluindo mecanismoisolado/revisãopendente; sem PASS_CURRENT ou autoaprovação.

**Precedência determinística:** usoCLI inválido→INVALID_INPUT/exit2; arquivo/JSON/cap/digest de integridade inválido→INVALID_INPUT/exit1; versão ou kind de regra desconhecido, mas com tipos corretos e JSON legível→UNSUPPORTED_RULE/exit1; demais violações de esquema→INVALID_INPUT/exit1; referência requerida declaradanull→BLOCKED_REFERENCE/exit1; origem/receipt ausente ou conteúdo manifesto≠receipt→UNTRUSTED_CAPTURE/exit1; SPEC/decisão ausente/negada/expirada→BLOCKED_CVG_SPEC/exit1; execução autenticada com timeouttrueouINFRA_FAILURE→INFRA_FAILURE/exit1; execução autenticada≠expectedExecution ou documentos diferentes→MISMATCH/exit1; somente todos os anteriores satisfeitos→MATCH_REQUIRES_REVIEW/exit0. Avaliar nessa ordem e registrar os checks posteriores comoNOT_RUN. Falha do próprio comparador/I/O de output produz INFRA_FAILURE/exit1; stderrdiagnóstico se nem o diretório novo puder ser criado. Receipts adulterados que relabelam timeout falham na origem antes da classificação de outcome, nunca passam a SUCCESS.

Os [exemplos sintéticos do wire](../04_audit/evidence/CLAUDE100-EXEC-20261017/qualifier-wire-example/README.md) materializam campos e digests para teste futuro do mecanismo. São exemplos documentais fabricados, não capturas da referência, decisões reais ou evidência funcional. Um índice real do Lead não inclui esses exemplos. Casos negativos alteram somente execução/fixture mantendo receipt/índice fixos, e documentam a rejeição esperada.
