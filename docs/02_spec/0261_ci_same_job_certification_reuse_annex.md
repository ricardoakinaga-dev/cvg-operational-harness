# SPEC0261 — Anexo normativo do protocolo r3

Este anexo r3 contém a correção M01 após o replanejamento explícito da r2; a r2 recebeu REVISE e não é tratada como aprovada. Ele trata F01–F04 da revisão r1. Faz parte da revisão T3; as escolhas abaixo não ficam para o BUILD. Não implementa o protocolo. Em caso de diferença com a descrição geral, prevalecem este anexo e o hash do conjunto revisado. Não há equivalência de conteúdo do banco entre instantes distintos.

## A. Notação, representação e recusa

Todos os objetos do protocolo têm exatamente as chaves declaradas, sem campos adicionais ou opcionais implícitos. `null` é explícito. Arrays têm no máximo o cap indicado, ordem definida e entradas únicas quando descritas como conjuntos. JSON com chave duplicada, inclusive após decodificar escapes, é inválido. Nenhuma coerção de número/boolean/string. Não usar propriedades herdadas.

- `D`: SHA-256 hexadecimal minúsculo de 64 caracteres, sem prefixo. `S`: Git SHA minúsculo de 40 caracteres. `U`: UUID v4 minúsculo.
- `P`: path POSIX relativo não vazio, no máximo 512 bytes UTF-8; sem NUL, `..`, componente vazio, drive, barra inicial ou link. Normalizar o nome dentro do root confiável e rejeitar aliases; nunca aceitar dois nomes para o mesmo arquivo. Nomes de ferramenta resolvidos no host ficam em campos próprios, não em `P`.
- `J(x)`: JSON UTF-8 sem espaços/newline, chaves de objeto ordenadas por ordem de código UTF-16, arrays na ordem declarada, strings por JSON.stringify, números inteiros seguros não negativos. Percentuais são números finitos de 0 a100 no formato do relatório Istanbul. O digest do objeto é SHA-256 de `J(x)`; o digest de arquivo é dos bytes exatos, sem recanonicalizá-los.
- `A`: referência `{path:P,size:integer,sha256:D}` a arquivo regular lido com cap+1. Snapshot tem inventário fixo por papel; não percorrer diretório para descobrir proof extra. Campos livres de diagnóstico não recebem corpo, senha, mensagem de terceiro nem path de credencial.

Classes estáveis: `REUSE_MODE_INVALID`, `REUSE_SCHEMA_INVALID`, `REUSE_ANCHOR_MISSING`, `REUSE_IDENTITY_MISMATCH`, `REUSE_PROFILE_MISMATCH`, `REUSE_TOOLCHAIN_MISMATCH`, `REUSE_SERVICE_UNAVAILABLE`, `REUSE_SERVICE_MISMATCH`, `REUSE_SOURCE_DRIFT`, `REUSE_ARTIFACT_INVALID`, `REUSE_HASH_MISMATCH`, `REUSE_RESULT_INVALID`, `REUSE_INVENTORY_MISMATCH`, `REUSE_NATIVE_COMPONENT_FAILED`. Toda recusa é não-zero, sem fallback. Preservar o primeiro motivo; cleanup pode acrescentar falha, nunca transformar emPASS.

## C. Install e closure

`InstallReceipt={kind:'cvg-install-profile-v1',identity,command:['npm','ci','--ignore-scripts'],lock:D,node:D,npm:D,tree:A,treeDigest:D}`. `identity` é o deB sem measurement. `treeDigest=sha256(J(Tree))`; `tree` aponta para bytes canônicos deTree. Install passa somente após validar o receipt; receipt eTree são artefatos adicionais do gate install e seus hashes entram no seal externo.

`Tree={packages:[{path:P,name,version,files:[{path:P,size,sha256:D}],links:[{path:P,target:P}]}],binLinks:[{path:P,target:P}]}`. Ordenar porpath; sem duplicatas. Enumerar pacotes reais de npm ci pelo índice node_modules/.package-lock.json, incluindo dependências aninhadas; dentro de cada pacote, todos os arquivos regulares, podando apenas subdiretórios node_modules que pertencem a outra entrada. Links só internos ao root instalado ou para workspace da candidata. Links de workspace registram destino e referenciam o manifesto de candidata; não confundir com pacote externo. O receipt liga toda essa árvore, não apenas o CLI.

Ficam fora da árvore somente caches `node_modules/.vite/` e `node_modules/.cache/`, não pacotes, e os outputs de build já classificados pelo coletor. A captura exige que eles não sejam origem de pacote/entry point; o launcher limpa caches próprios antes de cada medição e não reutiliza transform cache. Qualquer outro arquivo instalado novo, removido ou modificado recusa. No consumo rederivar a mesma árvore e os executáveis, sem confiar no digest de arquivo fornecido pelo adversário. Não instalar biblioteca nova ou alterar lockfile para implementar isso.

## D. Projeção de PostgreSQL

Só aceitar URL postgres/postgresql, host literal127.0.0.1, porta5432, database `cvg_test`, user `postgres`, senha presente, sem querystring/fragmento. Esta é a forma do serviço descartável atual; outro destino exige outra revisão de perfil. A senha não é registrada nem hasheada. Endereço de autenticação e estado do conteúdo não são comparados por hash de segredo.

Conexão real via pacote pg instalado, acquisition2s/query1s, em transação READ ONLY; executar `SELECT current_database() AS database,current_user AS role,inet_server_addr()::text AS address,inet_server_port() AS port,current_setting('server_version_num') AS version,to_char(pg_postmaster_start_time() AT TIME ZONE 'UTC','YYYY-MM-DD"T"HH24:MI:SS.US"Z"') AS epoch`. Fechar cliente no finally. Falha/timeout recusa antes de apagar outputs.

`service={driver:'postgres',connectHost:'127.0.0.1',connectPort:5432,database:'cvg_test',role:'postgres',serverAddress,serverPort,serverVersion,postmasterEpoch,disposable:true}`. Address é literal IPv4/IPv6 canônico; port inteiro1..65535; version decimal e major16; epoch UTC com seis casas fracionárias. Igualdade exata em todas as chaves no consumo, conexão real novamente. Não comparar tabelas/dados/transaction IDs; medições anteriores são observações anteriores, e PG/E2E posteriores continuam nativos.

## E. Schemas, hash edges e versões

Inventários grandes ficam em arquivos referidos por `A`, não no output do step. Limites: profile/receipt256KiB, report/discovery/installedTree64MiB cada, coverageSummary32MiB, log64MiB; seal codificado<=32.000caracteres; máximo300.000arquivos instalados,100.000cases,10.000fontes e10.000testfiles. Estouro falha; não truncar.

`Discovery={kind:'cvg-discovery-v1',identity,executionId:U,testFiles:[{path:P,sha256:D}],coverageSources:[{path:P,sha256:D}],cases:[{id,file:P,fullName,ordinal}],suites:[{id,file:P,parentId:null|string}]}`. Cases/suites vêm do collector antes da execução no mesmo filho; arrays porfile e ordem de coleta, IDs nativos únicos dentro da execução. Strings de ID<=256 e fullName<=4096. Os arquivos list-only referidos por Profile.discovery têm schemas exatos `TestFilesInventory={identity,testFiles:[{path:P,sha256:D}]}` e `CoverageSourcesInventory={identity,coverageSources:[{path:P,sha256:D}]}`, sem cases/suites ou chaves extras. Por medição, seus paths são `gate-outputs/<id>/certification/reuse/<id>/test-files.json` e `gate-outputs/<id>/certification/reuse/<id>/coverage-sources.json`; id é exatamente unit ou coverage. Identity é igual ao Profile/Producer; arrays são ordenados por path único. Os três digests (dois list-only e Discovery completo) são partes da prova. As listas do Discovery completo devem ser byte a byte iguais às listas dos arquivos list-only após J; qualquer diferença recusa.

`Producer={kind:'cvg-measurement-producer-v1',measurement,identity,executionId:U,profile:A,profileDigest:D,discovery:A,command:Profile.command,outcome:'PASS',exitCode:0,rawReport:A,coverageSummary:null|A,rawLog:A,startedAt,finishedAt}`. Times inteiros emms, finished>=started; são janela da execução, não identidade semântica. Unit coverageSummary=null; coverage exige summary. Todos esses arquivos são artefatos declarados do gate, capturados e validados contra hashes do live-frame antes do seal.

`Consumer={kind:'cvg-certification-measurement-reuse-v1',measurement,identity,consumerGate:'certify',profileDigest:D,producerStep:'gate_unit'|'gate_coverage',producerSealSha256:D,producer:A,snapshots:[A],origin:'REUSED_MEASUREMENT',consumedAt:integer}`. Não escolher produtor pelo receipt; unit sógate_unit, coverage sógate_coverage. `producerSealSha256` é hash da string codificada do output GitHub esperado, nunca de valor descoberto em disco.

Seals v2 mantêm os campos comuns observados em ci-bar-provenance: kind,contract,gateId,status,exitCode,github,runId,candidateId,nodeVersion,entrySha256,logSha256,snapshotSha256. Kind=`cvg-ci-gate-seal-v2`, contract=`hiso-010-v2-core-same-run-reuse-sealed`. V2 acrescenta `measurementProof:null|{producer:D,profile:D,discovery:D}`: não-null apenas em unit/coverage; install acrescenta `installProof:null|{receipt:D,tree:D}` não-null sóinstall. Compatibilidade também captura as saídas originais unit e coverage declaradas hoje. Os dois nomes do mesmo conteúdo são mirrors porhash, nunca duas fontes de verdade. Mapas `snapshotSha256` aceitam apenas essa lista de paths e as saídas legadas exatas do gate, sem chave adicional. Ambos os inventários list-only são obrigatórios nos snapshots dos dois gates, mesmo unit. Profile.discovery referencia exatamente os dois A desses snapshots; Consumer.snapshots inclui ambos. O verificador independente valida presença, nomes fixos, tamanho/digest e igualdade com as listas de Discovery antes de calcular denominadores. Omitir um, referenciar path ausente ou adicionar chave extra recusa; não resolver refs de fora do conjunto selado.

Predecessores obrigatórios no consumo: `gate_runtime`, `gate_install`, `gate_unit`, `gate_coverage`; cada `steps[id].outcome` e conclusion=`success`, output.seal decodificado por schema fechado, mesma identity/candidate e exit0. Nunca passar esse mapa parcial à finalização completa; finalização exige os34seals. O valor esperado é o output GitHub do step, capturado pelo contexto deworkflow; cópia em arquivo não o substitui.

## F. Rota autenticada dos bytes

O adversário não controla source, executáveis, memória do parent nem stdout pipe dos filhos; pode substituir os arquivos publicados. Permissão0700/chmod ou chamar um path de “imutável” não é proteção suficiente contra ele. Nenhuma decisão v2 reabre um mirror para derivar resultado.

Reporter Vitest v2 deriva da classe JsonReporter4.1.12. Usa os callbacks de coleta para Discovery; `onTestRunEnd` recebe os mesmos testModules usados pelo JsonReporter, conserva o binding de IDs/ordem e chama a implementação original. Override de `writeReport(report)` recebe os bytes **antes** da escrita: conserva-os, adiciona metadata `cvg={executionId,caseBindings:[{fileIndex,assertionIndex,nativeId,mode,state}],suiteStates:[{id,mode,state}]}`, valida o alinhamento com o collector e grava o JSON. `mode/state` são os nativos, inclusive ausência/queued/run; não confiar no mapeamento de estado desconhecido para skipped do JsonReporter.

Para cobertura, `onCoverage(coverageMap)` conserva o mapa recebido do provider. `istanbul-lib-coverage`3.2.2 gera o summary total/porarquivo a partir desse objeto; nunca ler o coverage-summary mutável para construir esse digest. A semântica numérica é a do json-summary atual. Esse summary é a fonte v2; o path coverage/coverage-summary.json é sómirror.

O reporter publica no stdout real do filho exatamente uma frame delimitada `CVG_REPORT_V1\t<J(frame)>\n` (tab e newline reais no wire), `{executionId,measurement,rawReport:{size,sha256},discovery:{size,sha256},coverageSummary:null|{size,sha256}}`. Para o formato de frame, measurement admite exatamente unit, coverage, postgres, chaos e e2e; para Producer/Profile de reuso, somente unit/coverage. Fora de coverage, coverageSummary=null. O parent passa executionId novo no env, captura a frame diretamente do pipe e a mantém em memória. Frame ausente, duplicada, nonce/medição divergente, saída parcial ou child não-zero falha. Leitura posterior do arquivo só é aceita se o buffer lido tem o digest da frame; trocar/restaurar arquivo depois não muda o buffer. O parent produz profile/Producer de seus próprios buffers, grava mirrors e sela comparando **contra os digests em memória**. Uma rehash do arquivo adversário não muda a âncora do pipe.
