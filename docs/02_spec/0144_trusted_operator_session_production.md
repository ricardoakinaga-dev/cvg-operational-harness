# SPEC-PR301/302-001 — sessão confiável no caminho publicado

- Trilha: **T3** (identidade, autorização, persistência e possível migration).
- Estado: `APPROVED_FOR_T3_BUILD` pelo usuário em 27/09/2026, junto com D-09 (OIDC com MFA obrigatório). O usuário escolheu IdP OIDC **local com MFA** para desenvolvimento/homologação; issuer corporativo será informado depois. A integração real ainda exige issuer, client, claims de MFA e mapeamento de grupos; produção e release seguem sem autorização.
- Tasks: [PR-301 e PR-302](../03_build/0356_production_backlog_2026-09-26.md); achado [AUD-0579-08](../04_audit/0579_current_candidate_deep_audit_2026-09-27.md).

## Recon e comportamento observado

`apps/api/src/main.ts` chama `buildServerFromEnv` sem `operatorSessionStore`. Na composição PostgreSQL de `apps/api/src/server.ts`, `buildServer` recebe `effectiveBuildOptions`, mas nenhum store é criado. O único store automático aparece no ramo `API_PERSISTENCE_MODE=memory`, `NODE_ENV=test`, `identityMode=trusted`. A rota `GET /v1/session` devolve 503 se o store não estiver presente. Isso é uma falha fechada de configuração, não um bypass de autenticação, mas impede a sessão de operador no entrypoint publicado.

A API já aceita retomar uma sessão existente pelo cookie sem novo bootstrap token. `apiClient.getSession` também aceita token `null`. O `createTrustedSessionBootstrap().load()` na web, porém, lança 401 antes da chamada quando não há token. O provider padrão consome o token global de uso único; a recarga posterior pode exibir autenticação necessária apesar de cookie válido. Os testes atuais injetam store manual e o E2E sobe a web em `simulation`, portanto não exercitam o caminho publicado. Esta conclusão de recarga é inspeção de fluxo, ainda sem E2E de produção controlada.

## Invariantes e fronteiras

1. Produção com console confiável não sobe sem store de sessão compartilhado e disponível; falhas do store resultam em erro estável, redigido e observável, sem recorrer a headers de simulação.
2. O cookie é `HttpOnly`, `Secure` em HTTPS e `SameSite=Strict`; a sessão pertence a um operador e tenant autenticados pelo IdP definido em D-09. Nenhum identificador fornecido pelo browser amplia o tenant ou o papel.
3. Uma recarga com cookie válido restaura a mesma identidade sem reutilizar o token de bootstrap. Expiração, revogação, logout e troca de tenant removem o acesso; token de outro operador não reutiliza a sessão anterior.
4. A sessão permanece consistente entre réplicas e reinícios. O store falha fechado se indisponível, com bounded timeout e sinal operacional. Não persistir token de bootstrap em storage do navegador.
5. A tabela, role, RLS/lookup pré-autenticação, retenção, índices, limpeza de expirados e rotação de credenciais precisam de desenho e revisão de segurança antes de migration. O lookup pré-autenticação é uma fronteira explícita, não autorização pelo `sessionId` isolado.

## Opções e proposta para revisão

| Opção                                                                              | Avaliação                                                                                                                                                               |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Manter apenas store injetado nos testes                                            | Falha no entrypoint publicado; rejeitada.                                                                                                                               |
| Criar store em memória no processo de produção                                     | Recuperação e réplicas não compartilham revogação; rejeitada para a plataforma.                                                                                         |

A web deve usar o contrato atual da API: quando houver token novo, trocá-lo por sessão; quando não houver, chamar `getSession(null)` com cookie. Resposta 401 mostra autenticação necessária; 503 mostra indisponibilidade sem descartar um cookie potencialmente válido. A futura entrada OIDC + PKCE de PR-301/302 substitui a origem do bootstrap e preserva esse contrato de sessão. PostgreSQL foi aceito na revisão T3; o desenho de lookup/role ainda exige revisão de segurança antes da migration.

## Revisão de segurança local I1 — 27/09/2026

A inspeção independente da fronteira PostgreSQL recomendou schema de autenticação separado, cookie opaco aleatório de 256 bits com somente o digest no banco e funções `SECURITY DEFINER` para criar, consultar e revogar. O lookup ocorre antes de haver tenant autenticado; a policy comum de tenant não serve para esta tabela. O papel de runtime deve ter apenas `USAGE` no schema e `EXECUTE` nas funções, sem DML direto; startup deve verificar owner, grants, RLS, `FORCE ROW LEVEL SECURITY`, policies e `search_path`. PostgreSQL orienta fixar o `search_path` de funções com privilégio elevado e revogar o `EXECUTE` público na transação de criação ([CREATE FUNCTION](https://www.postgresql.org/docs/current/sql-createfunction.html), [RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)).

**Pendência de desenho antes da migration:** definir provisionamento do owner/schema de autenticação com a role de migração sem `CREATEROLE`, grants para a role de runtime e preflight verificável. A troca de sessão atual cria a nova antes de revogar a anterior; o store precisa oferecer substituição atômica. O logout atual limpa o cookie antes de confirmar a revogação; a rota deve emitir a limpeza só depois do commit. Falhas em qualquer etapa retornam 503 e preservam o cookie anterior. Não usar store em memória como fallback em produção.

Para o IdP, a direção é Authorization Code + PKCE conduzido pela API, com `state` e `nonce` de uso único, validação de JWT/JWKS, MFA e mapeamento explícito de grupo para tenant/papel. O cookie temporário do retorno do IdP precisa ser compatível com o callback entre sites; o cookie da sessão operacional permanece `SameSite=Strict`. O token HMAC existente não será interpretado como JWT OIDC. Issuer, client, redirects, claims de MFA/grupos e política de logout federado ainda precisam ser informados. A revisão I1 foi estática e **não aprovou migration nem integração real**.

## Desenho de migration de autenticação — I3–I5 rejeitadas, I6 aceitou início do BUILD

As críticas I3–I5 mostraram que a tabela no schema de produto exigiria uma allowlist ampla de grants e funções e que o logout de uma sessão antiga poderia deixar ativa sua substituta. A proposta revisada usa **schema de autenticação separado**, definido por `POSTGRES_AUTH_SCHEMA`, diferente de `POSTGRES_SCHEMA`. A migration de autenticação tem runner e marcador próprios em `packages/persistence/migrations/operator-session/`; não entra na sequência padrão `0000`–`0026`, portanto não cria schemas órfãos nos testes existentes que apagam apenas o schema de produto. Os testes novos criam e apagam explicitamente os dois schemas. Nenhum SQL foi aplicado nesta revisão.

- O job externo de migration recebe a credencial DDL, aplica as migrations do produto e da autenticação e termina antes do servidor iniciar. A API de produção rejeita `DATABASE_MIGRATION_URL` no ambiente de serving; recebe somente `DATABASE_URL` para dados do produto e `OPERATOR_SESSION_DATABASE_URL` para uma role exclusiva do processo de API. O worker não recebe a segunda credencial. A role de sessão não é owner, não tem `BYPASSRLS`, `CREATEROLE`, `CREATE` ou **qualquer membership**, inclusive capacidade de `SET ROLE`, e não tem `USAGE` no schema do produto. O preflight prova essas propriedades e que não há grants de função ou tabela extras no schema de autenticação. O issuer OIDC validado pela API é a autoridade para mint; o banco restringe apenas o processo que pode chamar as funções.
- O schema de autenticação é propriedade da role de migração, tem `USAGE` somente para a role de sessão e nenhum privilégio para `PUBLIC` ou outras roles. A migration cria `operator_session_families(family_id bytea PRIMARY KEY, revoked_at timestamptz)` e `operator_sessions(token_digest bytea PRIMARY KEY, family_id bytea REFERENCES operator_session_families, tenant_id text, operator_id text, role text, created_at timestamptz, expires_at timestamptz, revoked_at timestamptz)`, com `NOT NULL` e checks de digest de 32 bytes, identidade e papel. `family_id` é o digest inicial e evita extensão para UUID. O preflight confere a PK de `token_digest`, a FK de `family_id`, o owner e RLS; inspeção exata de todas as constraints e índices ainda é gate antes de produção. O cookie opaco contém 32 bytes aleatórios; somente seu SHA-256 chega ao banco. O prazo absoluto é no máximo 15 minutos, limitado ao `exp` da autenticação; retenção e purga após expiração precisam da decisão do controlador/DPO antes de produção.
- A role de migração cria quatro funções `SECURITY DEFINER` com SQL estático e objetos qualificados pelo schema validado; `SET search_path = pg_catalog, pg_temp`. Assinaturas: `operator_session_create(bytea,text,text,text,timestamptz) RETURNS void`; `operator_session_get(bytea) RETURNS TABLE(tenant_id text, operator_id text, role text, expires_at timestamptz)`; `operator_session_replace(bytea,bytea,text,text,text,timestamptz) RETURNS void`; `operator_session_revoke(bytea) RETURNS void`. A migration revoga `EXECUTE` de `PUBLIC` para todas **na mesma transação em que as cria**. Depois do commit, o job DDL concede `EXECUTE` apenas nessas quatro assinaturas à role de sessão e termina. Não há grants de tabela ou coluna à role de sessão.
- `create` e `replace` rejeitam digest diferente de 32 bytes, identidade/papel inválidos, expiração vencida ou acima de `clock_timestamp() + interval '15 minutes'`; a PK rejeita digest duplicado inclusive sob concorrência. `get` devolve somente sessão não expirada/não revogada cuja família também não foi revogada. `replace` trava a linha da família `FOR UPDATE`, valida sessão antiga ativa e distinta da nova, insere a sucessora com o mesmo `family_id` e revoga a anterior na transação. `revoke` localiza a família a partir de qualquer digest da linhagem, inclusive já substituído, trava essa família e grava `family.revoked_at`; é idempotente para digest desconhecido. Assim, `replace` e logout se serializam: após logout bem-sucedido, nenhuma sessão da linhagem funciona, mesmo se uma resposta de troca atrasada instalar seu cookie. A rota só limpa o cookie após o commit de `revoke`; erro do banco retorna 503 e preserva o cookie anterior.
- `operator_sessions` e `operator_session_families` usam `ENABLE` e `FORCE ROW LEVEL SECURITY`, com policy `TO` somente a role owner, permitindo as leituras e escritas restritas das funções. A role de sessão tem apenas `USAGE` no schema e `EXECUTE` nas quatro funções. O preflight lê os objetos **vivos** e verifica ACL do schema, inventário de tabelas/sequências/funções e privilégios em colunas do schema de autenticação, ausência de grants efetivos extras (`has_table_privilege` e `has_any_column_privilege`) e de grants a outras roles, owner, role membership, RLS/FORCE/policy, PK/FK e seis constraints `CHECK` validadas com definição exata. A inspeção de índices permanece gate. Para cada função confere assinatura, retorno, linguagem, `prosqlbody`, `prosecdef`, `proconfig`, ausência de defaults/overloads, owner e ACL sem `PUBLIC`; compara `pg_proc.prosrc` byte a byte ao corpo canônico versionado na API, renderizado apenas com identificador de schema validado. O teste PostgreSQL comprova que a migration produz exatamente esse corpo. O runner de migration verifica seu marcador/checksum contra o arquivo local; o preflight de serving usa a definição viva sem credencial DDL. Não há hash de definição guardado no mesmo banco como suposta âncora externa.
- Rollout: provisionar roles e credenciais, aplicar migrations em job isolado, revogar `PUBLIC` na transação de criação, conceder as quatro funções, fechar o job, executar preflight com as credenciais de runtime/sessão e só então iniciar o serving sem DDL. Timeouts limitam conexão e queries; falha fecha a entrada sem store em memória. Rollback de código mantém sessões até expiração. Testes negativos: cookie forjado/duplicado/expirado/revogado, duas réplicas e restart, troca e logout concorrentes em ambas as ordens, grants de tabela/coluna/função indevidos, owner/RLS/definição adulterados, falta de schema ou role exclusiva, falha do banco e ausência de credencial DDL no processo serving. Sem esses testes e E2E confiável, a migration não é aceita.

A crítica I6 **aceitou iniciar BUILD controlado**, não aceitou a migration pronta. No preflight, rejeitar `SUPERUSER` e todo privilégio efetivo de criação da role de sessão. A futura purga deve preservar o vínculo de digests antigos enquanto qualquer sucessora da família estiver ativa, para que logout por cookie substituído revogue toda a linhagem.

## BUILD local do vínculo de identidade OIDC — 27/09/2026

`apps/api/src/oidc-identity.ts` recebe **somente claims de ID token já verificados criptograficamente** pelo futuro cliente OIDC. Confere issuer e audience configurados, `azp` quando há múltiplas audiences, subject opaco, expiração, autenticação recente e `amr` com `pwd` e `otp`. Exige exatamente um grupo `/tenant_<uuid>/<Operator|Approver|Supervisor|Admin>` e deriva `operatorId` estável do hash de issuer e subject. Limita a sessão a 15 minutos ou à expiração do ID token, o que vier primeiro. Nenhum claim vindo diretamente do browser pode chamar esse mapeador para criar sessão.

O verificador do Keycloak local foi ampliado e comprovou em navegador real que o ID token após OTP válido contém `pwd`, `otp` e `auth_time` recente, além do grupo. Testes negativos do mapeador exercitam MFA, grupos múltiplos/malformados, audience/issuer, tempo e subject. A crítica I12 aceitou a fatia local e apontou compatibilidade de `aud` em lista unitária, corrigida. A [prova da fatia](../04_audit/evidence/PR301-OIDC-MAP-20260927/proof.json) registra os gates finais. Ainda faltam o cliente OIDC com assinatura/JWKS/nonce/state/PKCE validados, rotas API/web, composição do store, E2E confiável e gates integrados; produção permanece `NO_GO`.

## Desenho da persistência de `state` OIDC — PR-301, T3

O contrato `OidcLoginStateStore` exige `reserve` e `consume` atômicos entre réplicas, com falha fechada se o banco cair. A role exclusiva de sessão já possui acesso apenas ao schema de autenticação, cujo preflight exige inventário exato; o novo estado pertence a esse schema, sem acesso à tabela de produto e sem fallback em memória. O state aleatório fica no cookie autenticado; o banco recebe apenas SHA-256 do state e o prazo de cinco minutos, sem nonce, verificador PKCE, token ou identidade.

- A migration incremental `0001_oidc_state.sql` tem versão/checksum próprios na tabela `schema_migrations`. Cria `oidc_login_states(state_digest bytea PRIMARY KEY, created_at timestamptz NOT NULL, expires_at timestamptz NOT NULL)` com `CHECK` de digest de 32 bytes e prazo `created_at < expires_at <= created_at + 5 minutos`, índice simples de expiração, `ENABLE/FORCE RLS` e policy somente da role owner. O runner executa `0000` e `0001` sob o mesmo cliente/uma transação para instalações novas; em bancos existentes verifica o checksum de `0000` sem reescrevê-lo e aplica `0001` de forma transacional. O preflight antigo rejeita objetos extras: no ambiente local sintético, parar todas as réplicas, revogar ou expirar todas as sessões locais, obter snapshot descartável, migrar e subir apenas o binário novo. Rollback local: parar o novo binário e restaurar o snapshot anterior; nenhuma sessão local sobrevive ao rollback. Antes de ambiente real, é obrigatório um release anterior de preflight compatível com os dois inventários, com teste de coexistência e rollback sem restauração de dados.
- Funções `SECURITY DEFINER` `oidc_state_reserve(bytea,timestamptz) RETURNS boolean` e `oidc_state_consume(bytea) RETURNS boolean`, com SQL estático qualificado e `SET search_path = pg_catalog, pg_temp`. A API tolera no máximo 30 segundos de diferença positiva entre relógios de réplicas; o banco aceita um prazo solicitado de até cinco minutos mais 30 segundos contra `clock_timestamp()`, mas grava `LEAST(p_expires, clock_timestamp() + 5 minutos)`, limitando a validade real a cinco minutos pelo relógio do banco. `reserve` insere com `ON CONFLICT DO NOTHING` e confirma sucesso somente para linha nova. `consume` faz `DELETE ... RETURNING expires_at` em uma instrução e compara o prazo retornado com um `clock_timestamp()` novo, inclusive após espera por lock; só uma chamada concorrente obtém sucesso. Erro de banco fecha o fluxo e retorna erro tipado de indisponibilidade para a futura rota responder 503 sem limpar o cookie pendente; state inválido retorna erro distinto. A API consome o state **antes** de trocar o code; falha posterior exige novo início de login.
- O job DDL revoga `PUBLIC` na transação de criação e concede à role de sessão apenas `EXECUTE` nas seis funções permitidas e `USAGE` no schema, sem DML direto. O preflight do serving passa a exigir exatamente as quatro tabelas, três policies, sete índices, constraints, ACLs e seis funções/corpos/assinaturas canônicos; inspeciona também tipos, `NOT NULL`, defaults, identidade e geração das colunas e recusa triggers, rules, objetos ou grants extras. O adapter usa o mesmo pool e role de sessão, limita conexão/query a dois segundos e nunca expõe o digest ao browser.
- Testes obrigatórios: migration nova e incremental/checksum, duas réplicas e restart, duas reservas do mesmo digest, consumo sequencial e simultâneo com exatamente um vencedor, expirado, prazo inválido e espera em lock além do vencimento, indisponibilidade do banco, DML direto negado, `PUBLIC` negado, e preflight adversarial de RLS, grants, coluna, índice, constraint e corpo alterado. A purga de expirados será job separado com role controlada, lote máximo de 1.000 linhas a cada dez minutos e alerta se a linha expirada mais antiga ultrapassar uma hora ou o backlog exceder 100 mil; execução, telemetria e decisão DPO sobre retenção são gates antes de produção. A role da API não recebe permissão de purge.

Este detalhamento implementa o requisito de `state` de uso único da SPEC 0144 já aprovada pelo usuário. Ele não autoriza produção, segredo real, integração corporativa ou mudança nos caminhos ativos da PR-L04.

## BUILD local da transação de login OIDC — 27/09/2026

`apps/api/src/oidc-login-transaction.ts` prepara o redirect Authorization Code + PKCE S256 com `state`, `nonce`, `max_age=300` e `response_mode=query`. O cookie temporário é `HttpOnly`, `SameSite=Lax`, tem limite de cinco minutos e contém `state`, `nonce` e verificador PKCE cifrados com AES-256-GCM por chave compartilhada entre réplicas; o contexto autenticado vincula issuer, client e redirect. Em HTTPS, o cookie recebe `Secure`. O callback só libera nonce e verificador depois de validar cookie, state e prazo e consumir atomicamente o digest do state em `OidcLoginStateStore`. O redirect de teste usa o URI exato do Keycloak local: `/v1/auth/oidc/callback`.

A revisão independente I15 rejeitou a primeira versão porque o state era reutilizável e o callback de teste divergira do realm; ambas as falhas foram corrigidas. A rechecagem I15 aceitou **somente a fatia local**. O `Map` do teste exercita replay concorrente, mas não prova atomicidade entre réplicas: a integração precisa de adapter durável e compartilhado com `reserve` e `consume` atômicos, com falha fechada. A API ainda precisa obter e fixar discovery do issuer, trocar código, validar assinatura/JWKS, issuer, audience e nonce do ID token, aplicar o mapeador MFA/tenant, limpar o cookie temporário no callback e compor as rotas com o store de sessão. O cliente OIDC e o E2E confiável permanecem `NO_GO`; o cookie operacional mantém `SameSite=Strict`.
