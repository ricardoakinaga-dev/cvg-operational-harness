## 2. Decisão de arquitetura proposta

Escolhido: **attach de byte I/O já em execução**, em Python CPython 3.11+ com stdlib; primeiro alvo suportado Linux/POSIX e `asyncio.SelectorEventLoop`. A versão observada local é 3.12.3, não prova suporte às demais versões. Testar 3.11 e 3.12 antes de anunciá-las; versões superiores só após prova. Não oferecer adaptador genérico para qualquer `BinaryIO`: pipes/descritores POSIX não bloqueantes são o contrato concreto.

Host abre e possui os dois descritores, configura não bloqueante antes do attach, garante exclusividade de leitura/escrita e mantém-nos válidos até `close()` terminar. O cliente usa `os.read`/`os.write` via readiness `loop.add_reader/add_writer`; nunca `readline()` bloqueante, `to_thread`, executor, thread daemon ou buffer de `StreamReader` sem orçamento. O cliente não duplica, fecha ou altera flags dos descritores, não abre arquivos/sockets, não descobre processo, tenant, cwd, env ou credenciais. Aceitar inteiros de FD distintos, válidos, não bloqueantes e suportados pelo selector; rejeitar `bool`, FD regular, FD inválido, plataforma/loop incompatível ou opções inválidas antes de registrar callbacks/escrever. Se o segundo registro falhar, desfazer o primeiro. O host não pode reutilizar/fechar os FDs durante a conexão; violação desse contrato não é contenção suportada.

Alternativas: cliente síncrono com pipes bloqueantes falha em limitar escrita/shutdown; threads podem sobreviver ao timeout; spawn embutido ampliaria autoridade, ambiente e gerenciamento sem benefício para esta fatia. Windows Proactor, transporte próprio de processo, HTTP, ACP/SSH, servidor Python e wheel/pip ficam para propostas próprias. Sem fallback silencioso de plataforma, protocolo, tenant ou método.

## 3. Superfície atual confirmada nas fontes

### Envelope, IDs e métodos

`SDK_PROTOCOL_VERSION = 1`, `jsonrpc = "2.0"`. Request contém `id`, `method`, `params` opcional. Resultado: `{"jsonrpc":"2.0","id":ID,"result":...}`; falha: mesmo envelope com `error:{code,message,data?}`. Exatamente um entre result/error. Não há batch, notification ou handshake de autenticação; `hello` negocia versão/capabilities, não identidade.

IDs válidos: string não vazia após trim JS, até **200 unidades UTF-16**, sem NUL; ou número inteiro seguro entre `-9007199254740991` e `9007199254740991`. Tipo+valor correlacionam: `1` difere de `"1"`; `-0` e `0` são o mesmo número. Não aceitar booleano Python como número. `null` pode aparecer em `JsonRpcFailure` do dispatch para request inválida, mas **não é resposta correlacionável**: o transporte stdio encerra por invalid_response. Não inventar ID nulo de chamada.

| Método v1        | Params enviados pelo Python           | Resultado validado antes de resolver                                                                                                                                                                             |
| ---------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sdk.hello`      | `{protocolVersion:1}`                 | `protocolVersion:1`; capabilities com sessions/events boolean e methods único, só os quatro métodos; hello/turn obrigatórios; open iff sessions, events iff events; events implica sessions                      |
| `session.open`   | `{sessionId}`                         | mesmo sessionId e `formatVersion:1`                                                                                                                                                                              |
| `turn.send`      | `{userMessage, sessionId?}`           | stopReason conhecido, response string, modelCalls/toolCalls seguros >=0, usage com inputTokens/outputTokens seguros >=0 e costUsd numérico finito >=0; sessionId igual ao pedido ou campo ausente se não enviado |
| `session.events` | `{sessionId, afterSequence?, limit?}` | `{events:[...]}` com até limit/default100; validar cada evento, identidade e ordem descritas abaixo                                                                                                              |

sessionId usa a regra de string/200 UTF-16/sem NUL. userMessage é string não vazia após trim JS, até **65536 bytes UTF-8**. afterSequence é inteiro seguro >=0, default0; limit é inteiro seguro 1..500, default100. O servidor exige sessionId em turn.send quando sessions está composto; caso contrário permite sua ausência. O Python não memoriza uma sessão implícita nem cria nova sessão automaticamente. Omitir optional com `None`; não emitir `null` (embora `??` no servidor trate null de cursor/limit como default). Args desconhecidos são erro local; a API não aceita kwargs de tenant/actor/budget/policy/approval.

Composição full atual `createSdk` usa InMemorySessionEventStore por default; `createSdkMinimal` anuncia somente hello/turn, sessions/events false. O cliente expõe o mesmo conjunto de métodos Python nas duas composições; chamada de sessão contra minimal pode receber **1003** do servidor, sem downgrade/retry local. Não afirmar persistência entre processos ou que `session.open` é um RPC de resume. No mesmo servidor/store vivo, outro transporte pode ler a sessão conhecida; isso prova reconexão de leitura, não retomada de execução durável.

Vocabulário exato STOP_REASONS observado em contracts: `COMPLETED`, `NEEDS_USER_INPUT`, `APPROVAL_REQUIRED`, `HUMAN_TAKEOVER`, `POLICY_DENIED`, `INSUFFICIENT_EVIDENCE`, `MAX_STEPS`, `MAX_COST`, `MAX_DURATION`, `MAX_TOKENS`, `MAX_MODEL_CALLS`, `MAX_TOOL_CALLS`, `MAX_REPLANS`, `MAX_KNOWLEDGE_CALLS`, `MAX_VERIFICATION_CALLS`, `VERIFICATION_FAILED`, `LOOP_DETECTED`, `TOOL_FAILURE`, `MODEL_FAILURE`, `INTERNAL_FAILURE`, `STATE_CONFLICT`, `CANCELLED`, `UNSAFE_REQUEST`. Um resultado `MODEL_FAILURE` continua resultado válido, não erro JSON-RPC nem autorização de retry. A presença de `CANCELLED` não cria método de cancelamento.

### Erros, sem códigos inventados

| Origem atual              | Nome / código                                                                                                     | Tratamento Python proposto                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| SDK_ERROR_CODES           | parse_error -32700; invalid_request -32600; method_not_found -32601; invalid_params -32602; internal_error -32603 | Preservar código remoto válido; não sintetizar resposta RPC       |
| SDK_ERROR_CODES           | unsupported_protocol_version 1001; session_not_found 1002; capability_not_available 1003                          | Preservar; nenhuma adaptação/reexecução automática                |
| SDK_TRANSPORT_ERROR_CODES | frame -32080; response_too_large -32081; timeout -32082; transport -32083; limit -32084; invalid_response -32085  | Mesmas constantes na projeção Python; closed usa transport -32083 |

O stdio atual rejeita frame/envelope/params inválido **fechando a conexão**, sem emitir necessariamente parse_error/invalid_params. Dispatch direto pode responder -32600/-32602. Unknown method com request válida chega a -32601; `toString`, `constructor`, `__proto__` não viram handlers. `sdk.hello` com versão numérica incompatível chega a1001. -32700 está no catálogo, não há promessa de que o framing atual o emita. Request inválida localmente é frame/limit not_dispatched e nunca teste fictício de erro remoto.

Mensagem remota tem 1..1024 bytes UTF-8 e code inteiro seguro (códigos desconhecidos seguros também são preservados); data opcional permanece dentro do orçamento do frame/JSON. `response_too_large` é RPC -32081 com mensagem fixa `response_too_large`; o servidor já despachou. SessionEventError mapeia session_not_open→1002 `Session is not open`, invalid_session_event→-32602 `Invalid session event`, demais→-32603 `Session store failed`. Runtime/hook podem virar -32603 `Runtime failed`/`Internal error`. Nunca classificar erro remoto como ausência de efeito.

### Eventos e tenant

Tenant é **somente `SdkServerOptions.tenantId` da composição confiável**, não parâmetro v1. `expected_tenant_id` do Python é dado local do host obrigatório e valida eventos; não é autenticação, descoberta ou negociação, não vai ao wire. Testar injeção de tenant/actor/policy/approval/budget em request bruta: servidor continua com sua composição. O transporte assume endpoints locais confiáveis; não protege de host malicioso capaz de forjar frames.

Envelope exato de SessionEvent v1: `tenantId`, `sessionId`, `formatVersion`, `eventId`, `timestamp`, `correlationId`, `traceId`, `type`, `payload`, `sequence`, `schemaFingerprint`; nenhum extra. IDs do catálogo seguem id string min1/max200 UTF-16, trim JS e sem NUL. formatVersion exatamente1 (não bool); sequence inteiro seguro >=1, maior que cursor e estritamente crescente na página, podendo haver lacunas; eventId único na página. tenantId deve ser expected_tenant_id, sessionId deve ser o solicitado. Não reordenar/normalizar eventos, deduplicar ou substituir identidades.

timestamp exige `YYYY-MM-DDTHH:mm:ss.sssZ` e roundtrip de calendário válido equivalente ao validador TS, incluindo ano0000 (validar calendário gregoriano numericamente; datetime Python sozinho não representa ano0). Catalogar os nove tipos atuais: `turn/start`, `model/request`, `model/result`, `tool/call`, `tool/result`, `turn/end`, `message/user`, `message/assistant`, `context/compacted`. Validar payload pelo subconjunto exato presente em `session-event-schemas.v1.json`: $ref local em definitions, type, enum, minimum/maximum, minLength/maxLength, pattern, x-maxUtf8Bytes, items, required e additionalProperties. Nenhuma lib JSON Schema ou resolução remota. Pattern somente dos dois schemas atuais id/hash, implementados explicitamente; catálogo com keyword/ref/pattern novo exige reprojeção e review, não ignorância silenciosa.

Checks adicionais de `session/events.ts`: payload.correlationId igual ao envelope quando presente; model/request.request.correlationId também igual; context/compacted.throughSequence < sequence. JSON depth<=64/nodes<=20000 por evento, todos os números finitos e evento canônico<=1MiB. Fingerprint **não é hash do payload do evento**: é SHA256 do canonicalizeJson de `{formatVersion:1,type,payload:catalog.events[type],definitions:catalog.definitions}`. Fixar os nove fingerprints projetados em `contract_v1.json`; o recon contém valores derivados estaticamente do catálogo ASCII/integer atual. No BUILD, comparar todos contra `sessionEventFingerprint` público real, sem usar o próprio validador Python como oráculo. Drift de catálogo exige reprojeção explícita, nunca aceitar hash somente por ter64hex.

## 5. Framing, orçamento e algoritmo propostos

UTF-8 estrito; objeto JSON completo mais LF, com CRLF aceito. Tamanho do frame inclui LF, CR e bytes UTF-8. Uma cauda limitada, sem decodificar fragmento UTF-8 antes de LF; sem aceitar EOF como delimitador. BOM, linha vazia e texto JSON sintaticamente inválido fecham por frame/-32080. Após parse JSON bem-sucedido, batch/notification, primitivo ou objeto que não seja resposta v1 válida fecham por invalid_response/-32085, como o cliente TS; os dois caminhos liquidam pending/queue uma vez e não fazem retry. Não há Content-Length, SSE, payload binário, logging em stdout ou recuperação heurística após frame ruim.

| Limite local                                         | Default | Intervalo aceito          |
| ---------------------------------------------------- | ------- | ------------------------- |
| max_frame_bytes                                      | 1048576 | 128..4194304              |
| max_pending_requests                                 | 64      | 1..1024                   |
| max_lifetime_requests                                | 4096    | 1..65536                  |
| max_buffered_bytes (requests aceitas até settlement) | 4194304 | max_frame_bytes..16777216 |
| request_timeout_ms                                   | 30000   | 1..300000                 |

Todas as opções são inteiros, excluindo bool. Preservar ranges/defaults TS; não negociar cotas pelo wire. Host deve compor limites compatíveis nos dois lados. Antes de serializar, percorrer apenas dict/list/escalares JSON locais, sob os mesmos limites64/20000, sem executar conversores/defaults/getters fornecidos pelo caller; recusar ciclos, objetos/subclasses custom e número não finito. Medir por varredura das strings o custo escapado ensure_ascii e por soma limitada a estrutura/números, abortando assim que ultrapassar cap. Isso impede que um único chunk de string gigante do iterencode seja alocado antes do check. Só depois, encoder incremental `json.JSONEncoder(..., allow_nan=False, ensure_ascii=True, separators=(',',':'))` acumula até o tamanho já aprovado, anexa LF e cria snapshot parseado. ensure_ascii=True é JSON wire válido; mensagem usa medição UTF-8 do valor, não tamanho escapado. Portanto um frame pode exceder cap mesmo com userMessage<=64KiB; rejeitar sem escrita, não elevar cap/truncar.

Um writer por conexão usa memoryview do frame ativo e offset; `os.write` pode consumir prefixo. Só avançar offset pelo retorno positivo; zero/BrokenPipe/erro inesperado é falha transport; EAGAIN aguarda readiness com deadline original; EINTR retenta somente a mesma syscall/cauda dentro do prazo, sem reaplicar request. Marcar WRITTEN **imediatamente antes da primeira tentativa** inclusive se EAGAIN/throw entregar zero conhecido: classificação conservadora TS. Nunca intercalar frames nem emitir o mesmo prefixo de novo. Próxima request só começa após todos os bytes da ativa entregues ao OS; isso não prova dispatch/execução. Resposta só resolve pending WRITTEN cujo frame terminou de ser escrito; resposta antecipada ao LF completo é invalid_response e fecha.

Pending contabiliza queued + written aguardando resposta. Soma de bytes aceitos fica debitada até settlement/discard, mesmo após liberar frame já escrito. Sem clones de frames em fila paralela; manter snapshot limitado dos metadados necessários à correlação (method, ID, session/cursor/limit), liberando userMessage do pending depois do snapshot validado/frame codificado. IDs vistos permanecem até close, limitados pela cota lifetime; duplicata pendente ou já resolvida é limit/not_dispatched. Cota cheia rejeita somente nova request sem matar as aceitas. Descartar pending/queue/seen/timers uma vez ao encerrar. O host continua proprietário de buffers/kernel pipes externos.

Leitura: `os.read` de até64KiB por callback, uma cauda <cap até LF, um frame completo <=cap em validação. Não acumular ilimitadamente coalescências: no máximo32 frames processados por turno, remainder<=64KiB, continuação com call_soon sob um único token; não fazer nova leitura até consumir remainder. Readiness/write callbacks também checam monotonic deadline e têm quantum64KiB, para não atrasar timers por peer inundando dados. Não há fila de eventos/notifications separada: response pertence a pending ou fecha. Linha com exatamente cap bytes e LF é permitida; sem LF, atingir cap já falha, pois falta o delimitador. frame/bytes/counters são anteriores à alocação/admissão relevante; offsets não duplicam contabilização.

### Diferenças de linguagem e restrições locais explícitas

Usar trim equivalente ECMAScript (TAB/LF/VT/FF/CR, SPACE, NBSP, BOM, U+1680, U+2000..200A, U+2028/U+2029, U+202F/U+205F/U+3000), não `str.strip()` como equivalência presumida. Comprimentos JS são unidades UTF-16; strings astral contam2. IDs numéricos e contadores aceitam número integral seguro, incluindo JSON1.0; Python bool nunca passa. Normalizar apenas representação numérica do ID para chave (`number`, int), sem stringificar tipo. costUsd aceita finito >=0. Não permitir NaN/Infinity em decode/encode.

Para limitar parser stdlib, pré-varrer JSON com consciência de strings/escapes e profundidade<=64/nodes<=20000 por **frame inteiro**, antes de json.loads; capturar erros de decode/recursão/memória como frame sem eco. Rejeitar nomes JSON duplicados e strings contendo surrogate isolado, inclusive escapado. Números de entrada seguem binary64 JS: inteiros fora do safe range são convertidos a float finito para JSON arbitrário; campos safe rejeitam se não seguros. Não arredondar IDs inseguros para fazê-los passar.

Estas são restrições locais deliberadas além do TS: depth/nodes do frame inteiro, nomes duplicados recusados e surrogate isolado recusado. O TS JSON.parse pode aceitar tais casos dentro de alguns resultados; não prometer equivalência de toda entrada v1. A rejeição de resposta antes de terminar a escrita local do frame também é uma guarda adicional: o servidor CVG real só responde após LF, mas um peer artificial pode responder mais cedo do que o validator TS exige. Args de usuário com surrogate isolado são recusados antes de encode, não substituídos silenciosamente por U+FFFD. Os casos astral válidos/acentos permanecem aceitos. Falha por orçamento local não redefine schema ou código de servidor.

Não implementar um RFC8785 genérico novo para medir evento perto do limite. Para o cap canônico de evento, calcular **limite superior seguro** da serialização TS: somar estrutura e strings com escapes JSON JS, ordenação irrelevante ao tamanho; reservar25 bytes para cada valor numérico (cobre JSON.stringify de binary64 finito) e usar soma exata dos demais escalares. Aceitar só se upper_bound<=1048576. Isso pode recusar evento v1 válido perto do teto; declarar como limite conservador Python e testar comparação com canonicalizeJson real. Fingerprints do catálogo usam projeção fixa verificada pelo TS e não esse estimador. Não usar json.dumps(sort_keys=True) como canonicalização geral de valores de eventos: ordenação UTF-16, floats, -0 e escapes diferem.

Bound de memória lógico: <=max_buffered_bytes de frames pendentes + uma cópia ativa durante encode <=max_frame_bytes + cauda/frame de entrada e parse temporário O(max_frame_bytes) com <=20000 nós + remainder64KiB + pending<=1024 + IDs<=65536. Nenhuma promessa de RSS igual ao número de bytes wire: objetos Python/encoder/JSON possuem overhead finito dependente do runtime. Testar contagens/altas d'água e ausência de crescimento após settle/close, sem fingir que stdlib transforma MemoryError em isolamento de OS.

## 6. Lifetime, deadlines, cancelamento e resultado incerto

Conexão: OPEN→CLOSING→CLOSED, sem reopen. Request: validação/admissão→QUEUED→WRITTEN→sucesso/falha terminal. Timers começam na admissão com `loop.time()` monotônico e incluem fila, escrita parcial e resposta; um timer por request, nunca renovado por atividade. O primeiro prazo vencido fecha a conexão inteira: todos os waiters liquidam uma vez segundo seu estado, descartar queued, remover callbacks/readiness/call_soon/timers. Deadline venceu mesmo se resposta válida chega no mesmo turno após o instante limite; comparar clock antes de settlement. Sem promise/future órfã ou resposta tardia reaproveitada.

Cancelamento local explícito é `await transport.close()`. Para `Task.cancel()` enquanto aguarda request admitida, implementação usa shield no Future interno, captura CancelledError e executa o mesmo close terminal antes de propagar **SdkWireError(kind='closed', code=-32083)** com classificação da request cancelada. Esta tradução local deliberada difere da convenção asyncio de propagar CancelledError; deve constar da doc pública e de testes. Se a resposta já liquidou antes do cancel, o cancel não desfaz esse fato; se cancel foi observado primeiro, não resolver sucesso. Cancel antes da coroutine entrar não admite/escreve request. Outros pending recebem sua própria classificação. Não criar kind/código/método RPC de cancelamento. O usuário/Lead revisará esta escolha T3 junto ao hash.

| Situação                                                                                        | outcome e retry_safe              |
| ----------------------------------------------------------------------------------------------- | --------------------------------- |
| Validação/cota/duplicata ou close antes de qualquer tentativa para esta request                 | not_dispatched / true             |
| WRITTEN: timeout, EOF, close/cancel, escrita parcial/EAGAIN/throw, resposta inválida ou perdida | unknown / false                   |
| Erro remoto válido, inclusive -32602, -32603,1001..1003 ou -32081                               | unknown / false                   |
| Sucesso correlacionado e validado                                                               | entrega resultado, sem reexecução |

`retry_safe` é fato de dispatch **dessa conexão**, não recomendação de reenvio. Nenhuma chamada, hello/open inclusive, é reenviada automaticamente; não reconnect/retry/backoff, nem troca de ID para repetir turno. Após unknown o operador consulta sessão/journal em conexão confiável separada ou faz handoff; eventos podem ajudar a reconciliar, mas ausência de evento não prova ausência de efeito. Falha de append assistant após model executado é exemplo obrigatório de resultado desconhecido. O cliente não oferece exactly-once, rollback ou cancel do kernel.

EOF com cauda parcial (JSON mesmo completo sem LF, UTF-8 incompleto ou lixo) é frame; EOF sem cauda é transport, inclusive quando não há pending. Erro de input/output fecha por transport. ID inexistente, null, tipo trocado, duplicado/tardio, response para queued, formato/result inválido ou tenant errado fecha invalid_response **antes** de remover pending. Falha coletiva classifica cada request individualmente; queued nunca herda unknown da anterior. Erro remoto válido só rejeita sua request e libera seus bytes/timer, mantendo conexão utilizável para consulta posterior.

close local idempotente impede nova escrita imediatamente, não drena/reenvia pedidos, remove registros do loop e liquida futures sem aguardar peer, dispatch, thread ou processo. Cleanup O(bounds) no mesmo loop; aceite exige término em até1000ms no teste com I/O permanentemente indisponível (margem do harness declarada). O cliente não chama close/shutdown em FD emprestado e não remove dados do host. CLOSED prova cleanup **do adapter**, não fim de efeito servidor. Host deve fechar seu canal e seu child segundo seu próprio contrato.
