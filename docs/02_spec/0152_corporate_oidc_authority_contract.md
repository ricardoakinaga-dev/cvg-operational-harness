# SPEC-PR301/204-003 — autoridade OIDC corporativa no boot da API

- Trilha: **T3**, contrato público de identidade, sessão e configuração de segurança.
- Estado: `BUILD_T3_APPROVED_USER / ISOLATED_SYNTHETIC_BUILD_PASS / STAGING_POSITIVE_NOT_RUN / PRODUCTION_NO_GO` (aprovação explícita do usuário em 28/09/2026).
- Tasks: [PR-301 e PR-204](../03_build/0356_production_backlog_2026-09-26.md). Recon: [AUD-0582](../04_audit/0582_corporate_oidc_boot_gap_2026-09-27.md).
- Base: [SPEC 0144](0144_trusted_operator_session_production.md) aprovada para IdP local sintético e store PostgreSQL, [SPEC 0151](0151_production_boot_configuration_contract.md) aprovada para snapshot de boot e falha fechada, [SPEC 0150](0150_cross_origin_operator_console.md) aprovada para BUILD sintético do transporte HTTPS. D-09 escolhe OIDC corporativo com MFA, mas o issuer e seus parâmetros reais continuam ausentes.
- Limite: BUILD controlado usa somente IdP e dados sintéticos. Esta SPEC não autoriza conexão ao IdP real, deploy, dado real, provider, canal ou GO. A conexão real exige os parâmetros IAM abaixo, revisão da configuração e gate de release.

## Resultado exigido

O entrypoint publicado da API inicia em `NODE_ENV=production` somente quando uma autoridade OIDC corporativa explícita, autenticada e verificada se liga ao store PostgreSQL de sessão e state. O login cria sessão apenas após Authorization Code + PKCE, state/nonce de uso único, ID token assinado e MFA verificado. O browser recebe cookie de sessão; cabeçalhos e tokens de bootstrap nunca criam identidade operacional nesse modo. Ausência, conflito ou indisponibilidade de qualquer dependência impede `listen` ou deixa a operação fechada sem elevar permissões. O IdP local HTTP permanece restrito a desenvolvimento/homologação.

## Configuração de autoridade e identidade

1. O snapshot da [SPEC 0151](0151_production_boot_configuration_contract.md) inclui seleção discriminada `local-controlled` ou `corporate-oidc`, perfil, issuer HTTPS exato, client ID, redirect URI da API, origem de sucesso do console, método de autenticação do client, referências de segredo/keyring, versão da política MFA e versão do mapeamento de grupos. Nenhuma rota, builder, hook ou callback relê `process.env` para alterar essa seleção. O modo corporativo é o único aceito em produção; variáveis `CVG_LOCAL_OIDC_*`, HMAC de bootstrap e overrides de teste são rejeitados quando aparecem junto dele. Hoje `hasLocalOidcConfiguration` classifica equivocadamente `CVG_OIDC_PENDING_COOKIE_KEY`, `OPERATOR_SESSION_DATABASE_URL`, `POSTGRES_AUTH_SCHEMA` e `POSTGRES_AUTH_ROLE` como sinais de IdP **local**. Separar o detector de `CVG_LOCAL_OIDC_*` do detector de campos compartilhados; campos compartilhados sem um modo completo falham fechados e nunca acionam fallback HMAC. Com configuração corporativa completa, a presença deles é obrigatória e não causa recusa de IdP local. Configuração parcial falha antes de criar pools, listener ou poller.
2. Primeiro contrato de client: `client_secret_basic` com segredo injetado pelo cofre no processo, sem valor padrão e com rotação por versão. Discovery do issuer deve anunciar esse método, Authorization Code, PKCE S256 e algoritmo de ID token RS256 ou outro algoritmo assimétrico explicitamente aprovado em revisão da política. `none`, implicit, password grant, `alg: none`, segredo em URL e fallback de método são proibidos. Um IdP que exija `private_key_jwt` ou mTLS precisa de revisão desta SPEC antes da integração; o cliente não infere o método.
3. Issuer, redirect e origem do console são URLs HTTPS canônicas, sem usuário/senha, fragmento ou query de configuração; callback usa caminho `/v1/auth/oidc/callback` exato. O issuer não pode ser loopback, IP literal, host interno ou IdP local. A equipe IAM fornece allowlist de issuer e endpoints de authorization, token e JWKS. Discovery só é aceito se `issuer` corresponder exatamente ao configurado e todos os endpoints estiverem na allowlist HTTPS; redirecionamentos de rede, DNS para faixa privada ou especial não roteável, certificados inválidos e destinos fora da allowlist falham antes de buscar token/chave. A política de egress do ambiente reforça a mesma allowlist. Falha de DNS/TLS/discovery impede startup; mudança de metadata sem revisão invalida a prova do candidato.
4. O ID token é verificado por biblioteca OIDC mantida, contra JWKS do issuer aprovado, assinatura, algoritmo permitido, issuer, audience/client ID, `azp` quando aplicável, nonce, validade, `auth_time` e idade máxima de cinco minutos. JWKS roda com cache limitado e refresh seguro para rotação; indisponibilidade ou chave desconhecida falha fechada. Access token ou claims enviados pelo browser nunca são tratados como ID token verificado.
5. A policy IAM aprovada declara quais valores exatos de `amr` e/ou `acr` provam MFA para este client e fluxo, e quais fatores são independentes. Não se reutiliza a hipótese local `amr: ['pwd','otp']` sem contrato do IdP. Ausência de prova, valor desconhecido, autenticação antiga ou downgrade para sessão só com senha bloqueiam mint. O pacote IAM também fixa o **nome exato do claim do ID token** que contém grupos, como membro de topo cujo valor deve ser array de strings; claim ausente, escalar, aninhado ou com elementos não string falha. Uma matriz de autorização versionada no manifesto de ambiente, aprovada junto com o candidato, associa identificadores **exatos** de grupo do IdP a `tenantId`, papel dentre `Operator`, `Approver`, `Supervisor`, `Admin` e estado `active`. Essa matriz é a fonte de ativação do tenant para este login; entrada ausente/inativa, múltiplos vínculos elegíveis, grupo desconhecido ou papel fora da matriz falham. Ao desativar um tenant, executar a drenagem integral descrita abaixo **antes** de servir com a nova matriz; o preflight confirma sua versão. O mapeador local de `groups` em path não é reutilizado sem adaptação explícita. Nenhum tenant/papel vem de query, header, cookie, frontend ou claim arbitrário de profile. O operador recebe ID estável de `(issuer, sub)` verificados; expiração da sessão é o mínimo entre 15 minutos e expiração do token.
6. `CVG_OIDC_PENDING_COOKIE_KEY`, rate limit distribuído, `OPERATOR_SESSION_DATABASE_URL`, schema/role de autenticação, RLS, store de sessão e state e preflight somente leitura da SPEC 0144 são obrigatórios. O pool de serving não recebe DDL nem acesso ao schema do produto. O client secret e keyrings são usados somente pelo caminho selecionado e nunca entram no resumo não sensível, logs, erro, bundle web ou imagem. O resumo do snapshot vincula versão da policy, IDs de keyring, issuer/client IDs aprovados e digest de campos não secretos ao candidato.

## Composição, HTTP e falhas

1. O entrypoint cria um único snapshot; o composition root constrói o client corporativo, valida discovery e preflights PostgreSQL, então registra rotas/hook e só depois chama `listen`. O `buildServer` direto e opções injetáveis de teste não podem fabricar autoridade produtiva; uma factory interna marcada pelo boot é necessária. Uma configuração OIDC não instancia o resolver HMAC legado. O servidor recusa `production` com `localOidc`, store em memória, `identityMode=simulation`, override de origem, cookie, rate limiter ou auth.
2. O início exige `Origin` exato do console autorizado antes de reservar state. O callback só aceita URI, cookie pendente e state de uso único, consome state antes da troca de code, valida nonce/PKCE e limpa o pendente. Troca de code ou store indisponível não cria sessão e exige novo início. Sessão, logout, replace e replay seguem a SPEC 0144; o modo corporativo usa os nomes `__Host-` e transporte da SPEC 0150. O callback não supõe que o cookie operacional `SameSite=Strict` venha da navegação iniciada no IdP.
3. A API responde 503 para dependência indisponível sem apagar sessão potencialmente válida; 401 é reservado a sessão ausente/inválida. Segredos, token, code, state, nonce, grupos pessoais e URL com credenciais nunca são serializados em erro, log, métrica ou tracing. Logs registram apenas etapa, código de falha, issuer ID não sensível e correlation ID. Retry de discovery/JWKS tem prazo e limite, sem bloquear indefinidamente o boot.
4. A SPEC 0150 governa origem web, CORS com credenciais, CSRF, cache, cookies host-only, CSP, proxy e dois hosts HTTPS. O boot corporativo pode ser implementado e testado isoladamente antes dela, mas nenhum teste de navegador/GO é aceito como prova final sem a topologia HTTPS real do candidato.

## Parâmetros necessários da equipe IAM

O pacote de integração não contém segredos em texto. Antes de ligar o IdP real, registrar: issuer/discovery HTTPS e allowlist de endpoints, client ID, redirect exato permitido, método de client auth aceito, referência no cofre e plano de rotação, algoritmo de assinatura/JWKS, claim e valores de MFA com semântica aprovada, nome/tipo do claim de grupos, grupos exatos e matriz ativa tenant/papel, política de contas desativadas e revogação/logout, política de egress/TLS e contatos operacionais. Alteração desses parâmetros invalida a evidência hash-bound e requer revisão da matriz e teste em staging.

## Prova e rollout

- **Configuração/boot:** testes de tabela para cada campo ausente/inválido, coexistência local+corporativo, client `none`, issuer HTTP/loopback/IP/privado, redirect errado, endpoints de discovery fora da allowlist, DNS rebinding/redirecionamento, TLS inválido, `DATABASE_MIGRATION_URL` em serving, schema/role/RLS inválidos e segredo/keyring ausente. O teste local com loopback usa `NODE_ENV=test` e não reivindica boot produtivo. O **positivo do entrypoint publicado** roda em staging sintético isolado: emissor HTTPS de teste em hostname e IP públicos **sob controle da equipe**, DNS e certificado TLS válidos para esse hostname, egress allowlist restrita a ele, PostgreSQL descartável e identidades sintéticas. Executar o **mesmo binário** Node 22 com `NODE_ENV=production`, sem flag de bypass, transporte injetado ou CA de teste no processo; uma rota pública sintética só é alcançada pelo egress aprovado. Caso essa infraestrutura não exista, o positivo fica `NOT_RUN` e produção `NO_GO`; um IP de documentação ou DNAT de IP alheio não substitui a prova. Positivo deve abrir listener e servir `/live`; negativos devem terminar antes de `listen` ou retornar 503/401 segundo a fase, sem vazamento no stderr. O positivo deve subir sem `CVG_OPERATOR_IDENTITY_KEYRING` HMAC.
- **Autenticação:** code+PKCE S256, state/nonce de uso único, concorrência/replay, assinatura/JWKS e rotação, `iss`/`aud`/`azp`, `auth_time`, expiração, MFA ausente/fraco, grupo zero/múltiplo/fora da matriz, tenant inativo, segredo do client incorreto e indisponibilidade do IdP. Cada negativo verifica que nenhuma sessão foi emitida e nenhum papel foi ampliado. Testar cookie salvo após logout/replace e restart entre réplicas.
- **Navegador:** após SPEC 0150 implementada, a prova **final** usa a mesma imagem/digest e o mesmo entrypoint compilado com `NODE_ENV=production` da prova de boot acima, em staging sintético com DNS/TLS e issuer HTTPS público controlado pela equipe. Chromium atravessa console e API em hosts HTTPS distintos do mesmo site e esse IdP sintético em outro site, completa MFA, callback Authorization Code + PKCE, criação da sessão PostgreSQL e recarga do console **sem** token de bootstrap, adapter local ou override de teste. A prova vincula no relatório digest da API/web, versão da policy IAM sintética, issuer e configuração sem segredos; falha se o browser estiver conectado a processo `NODE_ENV=test` ou a outro candidato. Verifica que o console não recebe cookie da API, o pendente `Lax` chega ao callback, o operacional `Strict` autentica recarga na API e replay/logout é negado; inclui 401/503, CSRF, CORS, cache, CSP, NGINX da imagem e headers reais. O fixture local em loopback de SPEC 0150 é regressão adicional, não substitui essa prova.
- **Regressão:** `typecheck`, lint, formato, `npm test` e cobertura sem skips, `test:postgres`, E2E, `skip:governance`, links/higiene, auditoria de segredos e certificação em Node 22. Crítica independente após BUILD inspeciona o artefato, não apenas testes. CI Verify/Security e atestação externa rodam no **mesmo SHA integrado** após PR-L04; nenhum PASS do branch isolado vira prova do release.
- **Staging e rollback:** antes de migrar o schema de autenticação em ambiente real, publicar uma versão anterior de preflight compatível com os inventários antigo e novo previstos na SPEC 0144; provar coexistência de réplicas, upgrade incremental e rollback **sem** restaurar o banco. Se essa versão de compatibilidade não existir, a migração real fica bloqueada. Então introduzir configuração corporativa e cofre sem tráfego, validar preflight/discovery, publicar digest com canary restrito e verificar MFA/RBAC, telemetria e rotação. Para desativar tenant, mudar matriz ou fazer rollback, usar a **drenagem integral** abaixo e retornar somente à versão preflight compatível que já preserve hosts/cookies da SPEC 0150; não voltar ao token HMAC nem ao IdP local em produção. Se não existir versão compatível, manter login bloqueado até corrigir o candidato. Operação real, issuer real e decisão T4 permanecem fora desta aprovação T3.

### Drenagem integral de autenticação para a primeira versão

O schema atual não marca sessão ou state com digest do candidato e a role de API só revoga uma família mediante digest conhecido. Portanto esta versão **não alega revogação seletiva por tenant ou candidato**. O procedimento inicial sacrifica disponibilidade para não conceder DML/DDL à API nem inventar um identificador que o banco não guarda:

1. Fechar admissão de login e tráfego autenticado no proxy, parar **todas** as réplicas da API e confirmar que não há requests em voo ou processo antigo capaz de criar/renovar sessão ou reservar state. O proxy responde indisponível durante a janela. Registrar o instante `t0` pelo relógio do PostgreSQL e a lista/digest das réplicas drenadas; se alguma permanecer ativa ou reaparecer, reiniciar a contagem da janela depois de pará-la.
2. Esperar pelo menos 15 minutos e 30 segundos após `t0`, mais a margem de sincronização de relógios aprovada no ambiente. O `CHECK` de `operator_sessions` limita a expiração a 15 minutos desde a criação; `oidc_login_states` expira em até cinco minutos. Com nenhuma emissão após `t0`, nenhuma credencial antiga deve continuar ativa. Não apagar linhas: expiração de autenticação e retenção/exclusão são decisões diferentes, e a SPEC 0149 continua governando purge.
3. Um job descartável, fora da API/worker, recebe por tempo limitado a credencial da role owner de autenticação via cofre e executa **somente** transação `READ ONLY` com timeout. Usando `clock_timestamp()` do banco, conta sessões que o lookup aceitaria (`expires_at > clock_timestamp()`, `revoked_at IS NULL` na sessão e família) e states com `expires_at > clock_timestamp()`. O resultado exigido é `0/0`, em duas leituras separadas com ingress ainda fechado; registrar apenas contagens, horário, schema/versionamento e digest do candidato, sem digests pessoais. A role de serving continua sem `SELECT`/`DELETE` direto; nenhuma nova função/coluna/grant é introduzida por esta SPEC. Falha de leitura, contagem não zero, clock incerto ou tráfego reaberto abortam o cutover.
4. Publicar a matriz/versão de rollback aprovada, validar preflight, issuer, hosts e cookies, então reabrir ingress. Todo operador faz novo MFA; cookies e pending states antigos são rejeitados por expiração, e replay é testado. Em staging sintético, automatizar a janela com relógio real do banco e duas réplicas; testar também uma réplica esquecida que força abortar. A operação real requer janela, responsável e aprovação T4. Revogação seletiva imediata, se exigida pelo SLA, é uma migration/função de manutenção T3 separada com role mínima, preflight compatível, testes de concorrência e decisão de retenção; não é inferida deste contrato.

## Gate

I1 rejeitou quatro pontos P1: campos OIDC compartilhados classificados como IdP local, claim de grupos/tenant ativo sem fonte explícita, positivo sintético incompatível com a proibição de DNS privado e rollback sem preflight compatível. A primeira revisão fechou esses contratos; I2 apontou falta de operação executável para invalidar sessões/state por tenant/candidato. A drenagem integral acima substitui a alegação de revogação seletiva por um procedimento verificável sem alterar o schema. I3 apontou que o teste de navegador não estava vinculado ao entrypoint produtivo; o critério acima exige o mesmo digest/processo sem override. I4, em contexto novo e sem edição, retornou `ACCEPT_SPEC_REVIEW_READY` sem P0/P1; foi revisão documental, não execução. O usuário aprovou BUILD T3 sintético em 28/09/2026. A configuração real depende do pacote IAM e a promoção depende das 13 condições de GO do plano 0354.
