# SPEC0231 — mecanismo inicial de qualificação Codex

Task `DX100-Q01-QUALIFIER-001`, ligada a DX100-G04/Q01.18/10/2026. Estado **DRAFT_FOR_INDEPENDENT_REVIEW / HUMAN_T3_REVIEW_PENDING / BUILD_NOT_AUTHORIZED**.

O [PRD0030](../01_prd/0030_codex100_initial_qualification.md), [validado para SPEC documental](../01_prd/0090_prd_validation.md), permite construir primeiro o mecanismo de medida, mantendo a jornada CQ01–14 integral e pendente. Esta unidade T3 cobre o contrato local CodeX do qualificador e sua adaptação compartilhada. Não modifica execução, SDK de aplicação, política/approval institucional, schema SQL, journal, sandbox, provider ou produto. ## Recon e decisão

O qualificador Claude100 está fisicamente integrado em scripts/claude100-qualify.mjs e tests/claude100/qualification. Seu fluxo já separa integridade, wire, schema, referência, captura, autoridade, execução e comparação. Reusar safeIO, parser, budgets de projeção, normalização, índices e julgamento; não clonar um segundo motor de comparação.

O [diagnóstico executado com os helpers atuais](../04_audit/evidence/CODEX100-EXEC-20261017/g04/qualification-mechanism-design/existing-helper-diagnostic.json) confirmou duas incompatibilidades para CodeX: o schema fechado rejeita o catálogo CODEX-CAP-v1 e a conversão Number/CVG-CANON1 faz dois IDs inteiros adjacentes acima de2^53 produzirem o mesmo digest. Isso caracteriza os contratos diferentes; não revoga a qualificação Claude100 no seu domínio. Relabelar o catálogo como CLAUDE-CAP-v1 ou comparar i64 arredondado é proibido.

O registro real compiled-target-features.json de G02 inclui serde_json com arbitrary_precision. Não presumir que todo valor JSON público da referência se reduz ao domínio Number ou que um guard apenas de inteiros resolve frações de alta precisão. O modo CodeX abaixo exige também roundtrip decimal sem perda; outros domínios usam prova por bytes ou extensão lossless própria.

G02 já dispõe do build próprio do fonte8d9f6466, CLI Linuxdefault com versão observada0.0.0 e primeiras nove observações keyless. O [passport](../04_audit/evidence/CODEX100-EXEC-20261017/g02-reference-Lead-acceptance.json) separa essa referência do instalado0.163.0 e de um release oficial assinado. Ele ainda não é captura da jornada inteira. Nenhuma função CVG tem recibo Codex atual.

Decisão proposta: um fluxo compartilhado, dois perfis fechados escolhidos por exports/CLIs diferentes. O perfil Claude permanece o default de seu export existente. O novo export CodeX escolhe internamente schema/bindings CodeX e domínio numérico seguro para comparação JSON. Dados de manifesto, catálogo, env ou opções recebidas do CLI não escolhem um validator, callback, módulo ou perfil executável.

CLI: `node scripts/codex100-qualify.mjs --manifest <file> --catalog <file> --rule <file> --capture-index <file> --authority-index <file> --evidence-root <dir> --out <dir>`. Todas as sete opções obrigatórias, sem extras, repetição ou posicionais; valores são paths de dados, nunca comandos/URLs/módulos/código. Erro de uso sai2. Inputs ilegíveis/inválidos saem1 no estado adequado. Diretório de saída novo, exclusivo, sob os controles físicos do mecanismo; nunca sobrescrever evidência.

Exports do motor compartilhado: `qualify(options)` mantém o perfil Claude; `qualifyCodex(options)` fixa CodeX. A função que recebe perfil é privada, sem opção pública `validator`, `profile`, `eval`, callback ou import dinâmico. parseArgs não seleciona o programa. Importar o módulo CLI Claude para reusar parseArgs não executa seu main.

Preservar os mesmos oito estágios e a precedência da [SPEC0229](0229_claude100_initial_qualification.md): integridade dos bytes; wire suportado; schemas/bindings; referência requerida; origem das capturas; autoridade exata da regra; execução autenticada; comparação. O perfil atua no schema do catálogo, na vista de bindings e no parser numérico; não pula estágios nem afrouxa autoridade/execução por ser CodeX.

O catálogo bruto continua sendo o input cujo SHA aparece em manifesto, índices e relatório. Uma vista privada `{requirements:[{id,verification_class}]}` pode servir ao validador de bindings comum, após validar cada row CodeX. Não criar catálogo CLAUDE intermediário, trocar hash/programa ou gravar a vista como se fosse o catálogo normativo.

## Perfil de catálogo CODEX-CAP-v1

Usar a [baseline proposta de509bindings](../04_audit/evidence/CODEX100-EXEC-20261017/g04/qualification-mechanism-design/catalog-baseline-proposal.v1.json), gerada do catálogo SHA7526e9d172abb1eeffa6981d98f1317fe91af2b617aab2b18a6645a5fd101fa7. Ela fixa source commit8d9f6466ff0294785d56f55b1fe363d132fe4133, repository oficial,22IDs de família e cada ID/família/classe obrigatório corrente. O BUILD copia esses bytes para o arquivo de baseline; alteração exige nova revisão da baseline, não parâmetro do cliente. A baseline não concede PASS e não impede acréscimos válidos.

Regras do perfil:

1. Objeto fechado. Campos permitidos: schema_version,catalog_id,revision,program,status,scope_closure,reference,family_count,functional_denominator,mandatory_cvg_controls,surface_inventory_count,numerator_pass_current,full_codex_parity_claim,scope,omission_policy,literal_metric,governed_metric,completion,qualification_not_started,families,requirements,revision_log,execution. Obrigatórios: schema_version,catalog_id,revision,program,reference,family_count,functional_denominator,mandatory_cvg_controls,families,requirements.
2. schema_version1; catalog_id exatamenteCODEX-CAP-v1; program exatamenteCODEX100; revision stringUTF8 de1..128bytes. reference é objeto de metadata; repository e commit precisam corresponder à baseline. Seus demais campos são dados, não autoridade nem vínculo do instalado com o ELF próprio.
3. families é array de22..1024objetos fechados com id,name,owner,source,reuse; id obrigatório e único, demais campos presentes com seus tipos atuais(string ou array de strings em reuse). Preservar todos os22IDs da baseline. family_count é inteiro seguro igual ao tamanho do array. Nenhuma família declarada fica sem requisito. CROSS_CUTTING é agrupamento reservado dos controles, não uma23ªfamília: não pode aparecer nesse array nem incrementar family_count.
4. requirements contém509..1024objetos. Campos permitidos: id,family,title,kind,mandatory,owner,sources,reference_validation,cvg_validation,status,equivalence,receipt,acceptance,oracle,variants,introduced_in_revision. Obrigatórios: id,family,kind,mandatory,owner,sources,status,receipt. id/family usam o identificador ASCII≤128bytes existente e são únicos no escopo correspondente. Para FUNCTIONAL_PARITY, family precisa existir em families e nunca é CROSS_CUTTING. Para CVG_CONTROL, admite-se o agrupamento reservado CROSS_CUTTING; qualquer outra family ainda precisa existir. A exceção não admite grupo desconhecido nem altera a família/classe de qualquer binding da baseline. owner é string1..128bytes, sem conceder autoridade.
5. kind somenteFUNCTIONAL_PARITY ouCVG_CONTROL; mandatory estritamente true. Todos os509bindings da baseline precisam permanecer com o mesmo id/family/kind. Excluir, substituir, reclassificar ou desobrigar um deles falha, ainda que as contagens sejam recompostas com novos IDs.
6. functional_denominator é inteiro seguro igual à contagem funcional e≥487. mandatory_cvg_controls igual à contagem de controles e≥22. A soma coincide com requirements.length. Novos IDs/famílias são aceitos até os caps quando todos os invariantes e a baseline forem preservados; não são automaticamente qualificados.
7. sources é array não vazio de objetos JSON de metadata. status e strings descritivas opcionais têm tipo string e ficam sob os caps do parser. receipt e outros metadados de progresso são JSON estrito, sem influência em autoridade, captura ou MATCH. Não confiar em PASS_CURRENT, numerator ou full_codex_parity_claim presentes no input para aprovar cenário ou programa.

Os caps são os do wire inicial compartilhado: catálogo até1MiB, arquivos controlados/artifacts até os respectivos caps da0229, arrays até1024onde indicado. Um escopo futuro que exceda o formato requer extensão própria, sem reduzir denominador, truncar captura ou declarar função concluída. Este mecanismo inicial não qualifica sozinho todas as variantes/funções, mídia ou grandes artefatos do programa.

## Números, JSON e bytes

`EXACT_BYTES` preserva bytes completos e é obrigatório nesta versão para comparar diretamente frames Codex que possam conter i64 fora de Number seguro, negativezero ou outra distinção numérica não representada por CVG-CANON1. Não transformar ID em string, remover sinal, arredondar ou normalizar identidade para obter MATCH.

No perfil CodeX, todo documento que o motor efetivamente parsear como JSON usa o domínio numérico CodeX: sintaxe JSON estrita, número finito, e rejeição de valor convertido que seja inteiro fora de Number.isSafeInteger ou Object.is(value,-0). Além disso, o valor decimal exato do token original deve ser igual ao valor decimal do JSON.stringify do Number resultante. Assim,0.1000000000000000000001 e0.1 não podem colapsar para um MATCH, mesmo sem inteiro inseguro. A rejeição ocorre durante o parse e antes de canonicalização/digest/projeção, inclusive em campos fora da projeção escolhida. O modo do parser é um enum interno, selecionado pelo export CodeX; nenhum campo de dados o desliga.

O teste de roundtrip não converte o token original em Number para compará-lo. Após a gramática JSON já validada, normalizar cada token para sinal/coefficient-digits/expoente decimal: concatenar dígitos de inteiro/fração; remover zeros à esquerda; para coeficiente zero usar zero canônico; nos demais, retirar zeros à direita e somar sua contagem ao expoente menos o comprimento da fração. Comparar esses três componentes com os do token JSON.stringify, sem expandir potências de10 ou construir BigInt de um expoente arbitrário. Para coeficiente não zero, magnitude do expoente de entrada acima de maxBytes+400 torna o domínio incompatível e é recusada; conferir tamanho/limite antes da conversão limitada do expoente. Coeficientes e trabalho permanecem lineares no input bounded. Zero negativo já é recusado; positivo zero não precisa materializar expoente gigante. Não usar tolerância/epsilon ou normalização Unicode.

O default do parser e do export Claude continua sendo o domínio Number finito anterior. Preservar seus testes e resultados; esta unidade não reinterpreta o wire Claude. Metadata de controle CodeX também passa pelo modo CodeX. Artifacts opacos usados emEXACT_BYTES não passam por parseJSON para comparação. O helper não apresenta a comparação JSON como um parser lossless do protocolo app-server.

Uma projeção lossless nova, comparador numérico adicional ou transformação prévia de frames só poderá entrar com contrato e prova próprios vinculados aos brutos. Não criar silenciosamente uma projeção no driver para esconder a restrição. A função/variante que ainda não tenha prova representável permanece pendente; a meta integral e o domínio do runtime Codex não são estreitados por este formato de teste.

## Wire e autoridade reutilizados

Manifesto, regra, receipts, capture-index, authority-index, roles, identidades, datasUTC, classes e relatório permanecem no wireversion1 da0229, com a diferença explícita do perfil de catálogo e do domínio JSON CodeX. Os objetos fechados e campos obrigatórios daquela SPEC continuam normativos. Não copiar suas tabelas para outro arquivo e permitir divergência silenciosa; registrar incompatibilidade futura antes de alterar o compartilhado.

Referencia deFUNCTIONAL_PARITY é LOCAL_BINARY ouREMOTE_SERVICE real/autenticada; ausência declarada resultaBLOCKED_REFERENCE. CVG_CONTROL exige referência null e SPEC institucional aplicável. Uma captura do fonte próprio0.0.0 não herda identidade do instalado0.163.0. Para G02, o operador vincula artifactSha256/config/driver ao passport do ELF/sourcepin e às capturas reais. O campo de versão não é carimbo fabricado de release. Serviços/plataformas futuros conservam seus gates/acessos e limitações.

Índices são insumos do operador revisor fora dos mounts graváveis do alvo. Hash é integridade, não assinatura nem autenticação de operador malicioso. Receipt sem origem correspondente, byte alterado, decisão pendente/negada/expirada, SPEC/regra/catálogo/fixture diferentes ou timeout relabelado não passa. Um pacote sintético de teste não entra no índice de captura funcional real.

A revisão humana desta SPEC, quando ocorrer, autoriza somente o BUILD deste mecanismo. Não equivale a aprovar cada regra de equivalência, captura, função ou candidato futuro. O mecanismo não cria decisões, executa alvo, chama modelo, ferramenta, rede, shell, SQL ou aplica aprovação institucional.
