### Invariante e algoritmo proposto

Ordem restritiva `ALLOW < REQUIRE_APPROVAL < DENY`. Manter validação de schema/tenant/resource/action/grant/role **antes** de rules; falha é DENY final, sem override. Calcular `floor` após contexto normalizado:

| Condição                                                       | Piso                                                 |
| -------------------------------------------------------------- | ---------------------------------------------------- |
| Falta de grant/role, tenant divergente, ação/resource inválido | DENY; já checado antes de rules.                     |
| grant.level=require_approval                                   | REQUIRE_APPROVAL.                                    |
| risk HIGH_RISK_WRITE ou ADMIN                                  | REQUIRE_APPROVAL, mesmo emergency e role Supervisor. |
| grant.requiresMedicalOperator=true e medicalOperator≠true      | REQUIRE_APPROVAL, mesmo emergency.                   |
| Nenhum dos anteriores                                          | ALLOW.                                               |

Proposta de combinação: `max(floor, efeitos de todas as rules aplicáveis globais e tenant)`. Prioridade desempata qual reason/policyId explicar entre regras da mesma severidade; desempate final por `(policyId, sourceVersion, ruleId)` lexicográfico. Nunca faz ALLOW apagar DENY/REQUIRE_APPROVAL. Sem matches usa floor. Se piso determina efeito mais restritivo, `policyId=ENGINE_POLICY_ID`; reasonCode interno fechado `high_risk_floor`, `grant_approval_floor`, `medical_operator_floor`. Regra explicativa mantém seu `policyId`, mas **todas** as decisões emitidas pelo algoritmo v2, inclusive DENY de schema/tenant/grant e decisões determinadas por rule, levam a versão efetiva abaixo. `sourceVersion` da regra é evidência interna; não é `PolicyDecision.policyVersion`.

### Contrato proposto e renderização v1

Escolher renderer **literal-v1**: instrução governada é exatamente PromptRecord.content UTF-8, sem trim, normalização Unicode, interpolação ou texto de caller. Proposta evita linguagem de templates neste módulo. Dynamic input separado: mensagens user/assistant como dados (roles system rejeitadas), userMessage/context/goal/capability/repair diagnostics serializados e limitados; não altera instrução. Instruções de agente/objective que têm autoridade pertencem ao registro pinado aprovado, ou devem ter nova versão de registro aprovada; não podem entrar por slot dinâmico como “system”. Assistant histórico é dado, não credencial de autoridade.

Novo shape wire V2 em `ModelGatewayRequestSchema`: `{inputVersion:'governed-input-v1', dynamicInput:{messages}, promptId,promptVersion,promptSha256,...}`; dynamicInput strict, até 64 mensagens/32.000 caracteres cada, total ≤64 KiB UTF-8, sem system. `input` legado deixa de ser usado em governado. Compatibilidade: caller legado só é traduzido se `input.system` ausente ou byte-idêntico ao registro e no máximo uma mensagem system também byte-idêntica; remover duplicata e renderizar um único system do registry. Qualquer content B ou system adicional nega `prompt_content_mismatch` antes do provider. Ambos formatos no mesmo request negam; legacy conversion é função auditável, não flag permissiva.

Material final canônico: `{rendererVersion:'literal-v1', system:record.content, messages:dynamicMessages}`. `instructionSha256=SHA256(UTF8(record.content))` deve igualar registry.sha256; `renderedInputSha256=SHA256(UTF8(canonicalJSON(material)))`. canonicalJSON tem ordem fixa nos objetos (rendererVersion/system/messages; role/content), arrays em ordem, escapes JSON padrão, sem whitespace extra. Hash inclui conteúdo dinâmico sem exigir aprovação humana de cada mensagem do usuário. Hash não inclui token/header/credential e não substitui redaction; não persistir texto dos prompts.

Gateway cria input imutável, ignora digests fornecidos pelo caller e adiciona PromptBinding a ProviderRequest/ModelResult: promptId/version/registry hash/rendererVersion/instruction hash/renderedInput hash. Antes de **cada** attempt, resolve novamente status/effectivity/tenant/hash; revogação impede repair/retry/fallback. Prompt global só aceita tenant explícito da execução; registro tenant-scoped com tenant omitido nega. Status approved exige approvedBy presente, sem promover draft por caller; lifecycle administrativo continua processo externo.

Provider adapter precisa construir payload a partir do material canônico e validar que exatamente um system byte-idêntico e mensagens dinâmicas em ordem sobreviveram. Recalcular digest do conteúdo/messages extraídos do body imediatamente antes de fetch. Proibir alteração tardia, segundo system, prepend automático ou mudança de role após binding. Adapters que exigem transformação de instrução precisam renderer versionado próprio e nova revisão, não reaproveitam literal-v1 silenciosamente. Hash da instrução vincula seus bytes; digest do material vincula a forma renderizada. Não é hash de todo HTTP body, que também contém model/temperature/limites; binding desses parâmetros continua routing/profile.

Esse desenho permite conteúdo dinâmico arbitrário dentro dos limites de dados, mas não prova imunidade a injection nem equivalência semântica de modelos. Responses continuam não confiáveis; policy/approval/grounding verificam seus efeitos.

Tool result já permanece no journal existente; aprovação/payload no store existente; fonte e mensagem nos seus stores. Não criar repositório paralelo de fatos.

#### effectReceiptRefs e readback das provas originais de S1

Para efeito admitido, `effectReceiptRefs` usa shape strict `{store:'operational_effect_journal',recordId,fieldPathId:'admission_receipt',contentSha256,tenantId,executionId,executionRef,attemptId,admissionSha256,bindingSha256,approvalId,reservationId,reservationGeneration,confirmationBindingRef?}`. recordId é operationKey da PK tenant/operationKey existente (não inventar journalId); tenant vem do pin autenticado e IDs/generation copiados exclusivamente do receipt armazenado de S1, null somente na variante não sensível. contentSha256 é SHA256 do canonicalJSON do **JSON completo persistido**, distinto de admissionSha256 que exclui seus campos de digest/attempt. Não incluir revision/updated_at/lease atual como identidade dessa ref: heartbeat/confirm não modificam o objeto admitido.

Para claim CONFIRMED, exigir confirmationBindingRef strict `{fieldPathId:'confirmation_binding',contentSha256,confirmationSha256}`, com contentSha256 sobre o JSON completo da confirmação armazenada e confirmationSha256 pelo algoritmo S1. O receipt de admissão e o binding de confirmação são gravados nas CAS/transações autoritativas do journal antes de salvar refs em checkpoint; checkpoint contém somente referências/identidades/hashes minimizados, não cópia de payload nem journal alternativo. Unknown/commits parciais podem conservar ref de admissão sem confirmação, mas nunca sustentar efeito confirmado.

Save e load sob scope tenant leem os JSONs persistidos e conferem schema/version, contentSha256, admissionSha256/bindingSha256, attemptId e igualdade de todos os campos de referência com os **snapshots originais**. Validar ainda equality com tenant/operation_key/proposal_hash/attempt_id da row e coerência dos dois objetos; para CONFIRMED, comparar a confirmationEvidenceRef/executionRef terminal do approval ao confirmation_binding e ler o result original: schema pinado e recálculo sha256-canonical-effect-result-v1 devem igualar algorithm/digest do binding antes de replay, reidratação ou publicação. Result ausente/substituído com receipts intactos produz checkpoint_integrity/result_integrity, zero reuso e zero redispatch. Reserva limpa no terminal não torna ref inválida se a prova original e seu binding terminal forem íntegros; tampouco autoriza aceitar generation nova/stale ou fabricar receipt a partir de campos agora ausentes. Lease/fence atuais autorizam somente acesso/recuperação, não reescrevem a geração/fence/expiry admitidos.

Row/coluna JSON ausente, NULL legado, ref parcial/forjada, hash de receipt de outra tentativa/tenant/generation, ou falta de confirmation_binding exigido produz checkpoint_binding/integrity, handoff e zero redispatch. Nunca rehidratar esse comprovante por síntese de updated_at/lease/reserva, nem executar o destino para recuperá-lo. Objeto JSON imutável permite retomar leitura da evidência após heartbeat/terminal cleanup sem confundir snapshot de admissão com estado atual. Cenários de refs originais após essas mudanças, legacy NULL e claims de geração errada são provas de integração futuras **NOT_RUN**, dependentes do schema/adapter S1; S4 isolado não qualifica o receipt.

HOW save/recovery: projetar/sanitizar e validar todo state **antes** de serializar/hashing/INSERT; preservar contadores/consumo/pins. Load valida tenant/execution/version/digest original e refs; reidrata estado efêmero lendo somente stores pinados, valida digest/revision atuais e jamais executa tool/search/model para recuperar. Ref ausente/revogada/alterada, pending input calculado sem storage autoritativo ou metadata não representável produz `checkpoint_binding`/`checkpoint_integrity`, handoff e zero novo efeito; não salvar snapshot bruto para evitar esse bloqueio. Modelo que gera novo input ainda sem store/ref precisa resolver pelo fluxo de proposta/aprovação existente antes de efeito; ramo ALLOW sem ref imutável não é retomável e deve bloquear admissão até integração qualificada. Isto é limite conservador explícito de compatibilidade, não alegação de recovery universal.
