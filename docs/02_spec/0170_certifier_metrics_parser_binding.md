## Contrato de correção proposto

1. Normalizar somente controles de terminal com `stripVTControlCharacters` de node:util antes de localizar resumoVitest. Não reescrever bytes/hashes do log original. Mesmo contrato de parse: passed/failed/skipped/total ou null quando inexistente/inválido. Contadores não negativos inteiros seguros; reconhecer todo como não executado/skipped; não reinterpretar fail/skip/todo como pass. Totais conflitantes, resumos concorrentes distintos ou labels sem counts reconhecíveis retornam null, nunca zeros inventados. Delimitador de label exige fronteira de palavra, não aceitar TestsFake.
2. Para gatesVitest com JSON produzido, comparar a projeção do lognormalizado com assertions e suite status do relatórioJSON obrigatório do mesmo gate/run/candidate. Reusar binding/hashes da matriz vigente; freshness/headers/process exit code permanecem obrigatórios. `testResults.length` mede arquivos; numTotalTestSuites pode incluir nested describes e não substitui arquivos. Ignorar número de describes para files; Status unknown/disabled/interrupted impede PASS. Pending/todo são contados como skipped, nunca passed, e só podem satisfazer o gate com catálogo/justificativa/binding vigente pela matriz atual; gates skipPolicy=none continuam zero skips. A rodada T2 atual exige zero skips. Exceção/unparseable/conflict/missing/stale/mismatch marca gateFAIL com código estável; não restaurar PASS pelo exit0 sozinho.
3. `metrics.unit` do resultado válido recebe contadores efetivamente verificados. Sem métricas utilizáveis, emitir record `{status:'UNAVAILABLE',reasonCode:'unit_metrics_unverified'}` compatível com schemaV1 existente, gateunitFAIL e bloqueador explícito. Não alterar schema para aceitar null nem fabricar contadores. Verificador rejeitaPASS com recordUNAVAILABLE e exige comparação com artefatos reais; caso essa forma não passe no schema atual, parar e submeter delta, sem supressão/cast.

## Integração fechada da evidência e emissão FAIL

Binding proposto `vitest-evidence-v1`: certifier gera UUID executionId novo **por gate**, transmite runId/candidateId/gate/executionId à instância do reporter por environment server-side. Reporter JSON produz, no próprio encerramento do runner, `cvgVitest:{version,runId,candidateId,gate,executionId}` no JSON e marcador único `[vitest-evidence]` no stdout com os mesmos IDs e contagens; não aceitar JSON fornecido por caller. Reporter usa a estrutura JSON original de Vitest4 e acrescenta somente metadata; API local Vitest4 consultada: `JsonReporter` de vitest/reporters expõe onInit, onTestRunEnd(testModules) e writeReport(report); subclass guarda state/mode por filename em onTestRunEnd e sobrescreve writeReport para validar/acrescentar binding ao JSON produzido pela base, escrevendo pelo writer base. Não reconstruir JSON ou assertions por regex do stdout. Helper comum emissão/verificação exige equality de metadata, marcador, gate.executionId e evidence.executionId para log e JSON. Header/gate/evidence ficam associados ao run/candidate pelos guards existentes. Resultado sem metadata v1 não qualifica novo PASS; leitura histórica segue contrato histórico sem promover a live.

Manter remoção dos outputs próprios antes da execução já existente no certifier; incluir chaos JSON e outputs do novo reporter. Capturar bytes imediatamente após o subprocesso, sem reler arquivo substituído mais tarde. startTime/endTime do runner devem ser finitos e coerentes com janela do gate gerada pelo certifier; registrar start/end no marcador e na metadata. Negative: copiar JSON de run anterior com contagens iguais e apenas rehash/associar evidence ao run novo deve falhar `vitest_binding_mismatch`; sem marcador/resultmetadata também falha. Esta prova pressupõe produtor/processo/checkout confiáveis, como bindingE2E atual; não promete resistir ao atacante que altera todos os artefatos e o produtor. Autenticidade/head/digest/closure externa permanecem fora desta SPEC, em0157 e guards atuais.

Projeção strict: em cada `testResults` (arquivo) exigir name único, status passed/failed/pending/todo/skipped reconhecido e assertionResults array; assertions passed→passed, failed→failed, pending/todo/skipped→skipped; unknown→unverified. Reporter inclui `cvgVitest.files:[{name,mode,state}]` extraído dos testModules oficiais: file state fail/status failed/assertion failed→failed; file mode skip/todo→skipped; file state pass/status passed→passed (mesmo com assertions skipped, desde que o runner concluiu o arquivo). Unknown/run/queued/estado ausente sem mode skip/todo→unverified. Validar correspondência 1:1 de nomes com testResults e não derivar estado do arquivo apenas das assertions. Arquivo sem assertions precisa evidência explícita de erro/skipped; vazio declarado passed é inválido. No JsonReporter instalado, numPendingTests inclui mode skip ou result skip/run/queued e numTodoTests inclui mode todo; separar assertion todo de pending/skipped, exigir numPendingTests+numTodoTests igual à projeçãoskipped e cada subtotal igual aos respectivos statuses. Metadata files e contagens são geradas do estado real, não supplied request. Status unknown/run/queued invalida qualificação; total=passed+failed+pending+todo, sem dupla contagem. Todo no resumo textual é contado como skipped no contrato legado de métricas, conservando total. Labels não reconhecidos (inclusive expected fail até ter projeção explícita) tornam unverified, nunca pass implícito. Tests total é soma passed+failed+skipped; file total é testResults.length, não numTotalTestSuites. logTests/logFiles/marker devem bater com projeção. `metrics.unit={testFiles,filePassed,fileFailed,fileSkipped,tests,passed,failed,skipped}` é projeção única, com inteiros seguros; `gate.metrics` e métricas públicas devem comparar exatamente esses campos na verificação. Resumo repetido idêntico pode ser aceito uma vez; contraditório falha. Não somar duas impressões iguais.

Códigos estáveis: `vitest_binding_missing`, `vitest_binding_mismatch`, `vitest_report_invalid`, `vitest_summary_invalid`, `vitest_counter_mismatch`, `unit_metrics_unverified`, `skip_inventory_unverified`. Invalidade/missing de unit força gateunitFAIL e metrics.unitUNAVAILABLE. buildSkipInventory atualmente já captura JSON inválido em collectReportRows e reportHash retorna null para missing; conservar failures/reports/executed=false, sem substituir por relatório vazio inventado. Se exceção inesperada da coleta escapar, boundary no certifier registra skip_inventory_unverified, result record de falha com causas e NO_GO; nunca marcar skipped=0 ou skip governancePASS. Shared verifier recusa PASS+UNAVAILABLE, ausência, contadores discordantes e inventedzero; resultadoNO_GO válido pode conter fatos indisponíveis e continua FAIL no comando verify. Outros gates que abortam não entram no scope como PASS nem são ocultados.

Nova fixture contém um arquivo e cinco assertions passed, métricas reais completas e binding de produtor específico da fixture. Ela é **SELF_TEST_FIXTURE**, não certificação do produto. Manter todos os negativos existentes e adicionar tamper isolado metrics.unit, PASS+UNAVAILABLE, JSON/log divergente, arquivo antigo rehashado, JSON missing/invalid e catalogued pending permitido versus skipPolicy none negado.
