## BUILD A — alias TypeScript no auditor

1. Em `readTsconfigPaths`, validar antes da resolução as entradas `compilerOptions.paths` de cada config lida: `paths` deve ser objeto (sem array/null), cada chave deve ser string não vazia e mapear para array **não vazio** de targets string não vazios, com **no máximo um `*`** na chave e em cada target. O contrato cobre `TS5061`, `TS5062` e `TS5066` do TypeScript, além de tipos malformados. Preservar a leitura de configs estendidas já suportadas. Uma entrada inválida gera gap estável `TSCONFIG_PATHS_INVALID` com config e padrão, sem ecoar conteúdo sensível; o relatório deve terminar `UNRESOLVED`/exit não zero, mesmo se uma aresta for classificada `MISSING_ALIAS_TARGET` ou não houver import que use o alias. Não silenciosamente descartar a entrada.
2. Para padrão válido com um wildcard, substituir exatamente um wildcard no target, preservando a semântica atual. Para padrão sem wildcard, manter correspondência exata. Checagens `isWithin`, symlink e classificação de dependência existentes permanecem fail-closed. Não usar `replaceAll('*', captured)` para normalizar input inválido.
3. Negativos em workspace sintético: dois `*` na chave (`TS5061`) e no target (`TS5062`), array de targets vazio (`TS5066`), valor `paths` não objeto, target não array, string vazia e entrada malformada, target que escapa do root, symlink e alias não resolvido. Ambos os casos multi-`*` devem dar não zero no auditor; o target de um `*` continua `PASS` quando existente. Comparar diagnostics do `tsc` no fixture. Fonte histórica sob `docs/04_audit/evidence/` não é reescrita.

## BUILD B — custo linear nas URLs e no filtro de instrução

1. Nas duas implementações de provider (`ollama`, `openai-compatible`) e nos dois adapters (`evolution`, `chatwoot`), substituir `.replace(/\/+$/, '')` por operação de sufixo em tempo **O(n)**. Preservar o resultado byte a byte de entradas hoje válidas: zero ou muitas barras finais, URL com path, URL sem barra final, espaços externos já tratados por cada construtor e URL inválida que continua recusada pela validação existente. A operação não pode introduzir chamada de rede nem afrouxar validação de protocolo, host, DNS, SSRF ou tamanho de resposta. Preferir helper local por pacote se isso evitar nova dependência cruzada.
2. Em `hasUntrustedInstructionContent` (`packages/conversation/src/state.ts`), substituir o padrão com retrocesso por scanner determinístico ou expressões sem caminho superlinear. Preservar a detecção dos nove grupos de comandos atuais: `ignore`, `desconsidere`, `system`, `assistant`, `execute tool`, `grant approval`, `override policy`, `reveal secrets/credentials/reasoning` e `call hidden.capability`, incluindo alternativas português/inglês e espaçamento hoje aceito. Manter negativos comuns de texto institucional benigno. Para valor com mais de **16.384 unidades UTF-16**, retornar `true` antes de qualquer varredura: este `true` significa **recusa por tamanho**, não evidência de instrução. Documentar o limite e a razão de recusa para os chamadores sem alterar a assinatura booleana. Testar texto benigno nos limites 16.384/16.385. A função continua pura e sem efeitos externos.
3. Testes de regressão: matriz positiva/negativa por grupo, incluindo match como substring, variações de maiúsculas/minúsculas, `\s` Unicode e pontuação opcional hoje aceita; corpus diferencial determinístico até 16.384 unidades UTF-16 contra a **expressão antiga congelada no teste** (com hash da fonte): semente `0xC0DE0159`, geradores dos nove grupos com espaços ASCII/Unicode (incluindo NBSP), caixa, opcionais, prefixos/sufixos e entradas benignas. Todo positivo antigo **do corpus** continua positivo; novos positivos precisam ser revistos como recusa conservadora. Incluir explicitamente `preignore all suffix`, NBSP e `call hiddencapability`. Cobrir espaços longos sem match, repetição de barras com sufixo que impede o match, comprimentos 2k/4k/8k/16k, limite 16.384/16.385 e chamadas reais dos construtores com config sintética. Medição diagnóstica em Node 22 aquecido: três ou mais amostras por tamanho para URL e filtro, com comparação de crescimento em 2k/4k/8k/16k e orçamento indicativo de 50 ms no caso de 16k; não usar um limite de relógio isolado como único gate de CI. O aceite exige revisão de que o algoritmo é O(n), limite de entrada aplicado antes da varredura e evidência de tendência aproximadamente linear; registrar as amostras.
