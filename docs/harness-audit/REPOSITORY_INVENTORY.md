# Inventário do repositório

## Escopo, unidade e método

Foram inventariados **28 componentes estruturais**: 21 workspaces (`apps/*` e `packages/*`) e sete superfícies (`scripts`, `tests`, `docs`, configuração raiz, infraestrutura dedicada, `deploy`, `certification`). A unidade é componente/package, não arquivo. `node_modules`, caches, coverage, logs históricos e temporários foram excluídos. O candidato é `HEAD 512bc11e80fbf7c7b8baf6263aacc811ff829309` mais o worktree observado em 2026-09-13.

O inventário cruza manifests, imports de produção (testes excluídos), barrels/exports, implementações, testes e configuração. Dependência significa import/runtime direto observado; dependente significa consumidor no repositório, não todos os consumidores externos. `CONFIRMED` é inspeção direta, `INFERRED` é conclusão limitada pelos anchors e `UNKNOWN` marca ausência de prova suficiente.

## Direção e divergências verificáveis

- `apps/* -> packages/*` e `agent-runtime -> approval/model/observability/policy/shared` são observados. `persistence -> agent-runtime|approval-engine|channel-gateway|platform` existe porque adapters duráveis conhecem contratos superiores; em um storage core neutro isso é inversão de dependência.
- `rag -> platform`, `tools -> platform|persistence` e `workflows -> platform|persistence|policy` confirmam acoplamento ao produto; nomes de packages não os tornam genéricos.
- Manifests divergem dos imports atuais: `apps/worker` omite packages novos; `packages/persistence` omite `agent-runtime`, `approval-engine` e `channel-gateway`; `apps/api` omite `platform`; `packages/tools` importa `platform` sem declará-lo. Builds isolados e semver não estão comprovados.
- Barrels `src/index.ts` são a API de facto, não um contrato versionado suficiente. A extração deve congelar somente os símbolos escolhidos por consumer-contract tests.

- Checkpoint original: `npm test` — 249 arquivos, 240 pass/9 skip; 1.680 testes pass/105 skip, exit 0. `npm run typecheck`, exit 0. `npm run test:evals`, 1 arquivo/8 testes, exit 0.
