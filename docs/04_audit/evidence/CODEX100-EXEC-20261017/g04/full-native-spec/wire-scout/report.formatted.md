## Concrete projection proposal and incompatibilities

1. Persist native resource bindings separately from RPC correlation: thread → native session/composition; turn → native execution/attempt; item → native tool/response item. Thread.sessionId is a session-tree identity, distinct from Thread.id. Keep those bindings across restart. No DDL is proposed here. [S16:201–294,383–437](sources/S16-thread_data.rs.source.txt).
2. Keep approval waiting nonterminal: `turn.status=inProgress`, `thread.status={type:active,activeFlags:[waitingOnApproval]}` when observed through read. The revisor decides through the native institutional port, and guarded native resume validates the exact binding. `thread/resume` or an RPC reply cannot become an approval mutator. The six selected notifications contain no dedicated approval-state event; use the separate native surface or qualified read behavior. [PRD0030:29–35,70–78](sources/S06-0030_codex100_initial_qualification.md.source.txt), [S12:1679–1723](sources/S12-thread.rs.source.txt), [S31:160–203](sources/S31-iterative-dispatch.ts.source.txt).
3. For `responseIntent`, qualify the actual RESPONSE call carrying the full admitted tool result; the prompt's instruction to use observations does not prove the result reached it. `responseText` takes the direct branch and requires its own provenance case. Only admitted output becomes an agentMessage. [S31:835–988](sources/S31-iterative-dispatch.ts.source.txt).
4. Add an admitted incremental provider path before projecting `item/agentMessage/delta`. The inspected provider is `execute -> Promise<ProviderResult>` with complete text. Slicing that result cannot meet CQ06. Reference deltas are forwarded independently of item completion. The Lead must settle stream admission, bounds, durable append, cancellation and first cause. [S30:76–110](sources/S30-contracts.ts.source.txt), [S25:1014–1147](sources/S25-bespoke_event_handling.rs.source.txt), [S32:364–420](sources/S32-event_mapping.rs.source.txt).
5. Registry READ/WRITE bodies remain native. Reference `item/tool/call` requests **client execution**, after dynamicToolCall item start. A proposed native-tool → dynamicToolCall **item lifecycle** is therefore a governed projection needing an explicit comparison rule; it must not solicit a client response as evidence of native execution. Its exact request/result shapes are included only to prevent conflation. Command/file/permissions server approval requests are unnecessary for this registry journey and remain outside the selected contract. [S11:1793–1831](sources/S11-common.rs.source.txt), [S14:1665–1696](sources/S14-item.rs.source.txt), [S25:1087–1128](sources/S25-bespoke_event_handling.rs.source.txt).

[S12:436–488](sources/S12-thread.rs.source.txt), [S29:199–306](sources/S29-events.ts.source.txt).
