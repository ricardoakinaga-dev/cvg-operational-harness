## 2. Fatos e fronteiras atuais

Armazenar o resultado no journal não resolve automaticamente outros campos

## 3. Decisão proposta e alternativa descartada

Adicionar **duas colunas** ao journal existente:
`result_storage_version` e `result_storage_payload`. A versão fica fora do
conteúdo da ferramenta. O payload1 contém bytes JSON canônicos em base64 ASCII;
`result` continua reservado ao armazenamento legado.

| Alternativa                                                              | Decisão                                                                                                      |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| JSONB direto com correção do mapper                                      | Não representa NUL; mantém o gargalo de256KiB.                                                               |

| Reutilizar versão do checkpoint ou de outro registro                     | Não identifica o formato de cada linha do journal.                                                           |

| Serviço de blobs, nova tabela de journal, compressão ou dados ilimitados | Não necessários para esta fatia limitada.                                                                    |

Não haverá coexistência de binários antigos e novos com acesso ao mesmo schema

## 4. Contrato lógico, domínio e opt-in

As assinaturas de `EffectJournal`, seus estados e os bindings de
operationKey/proposalHash/attempt não mudam. `confirm({result:v})`, `get` e
`reserve` confirmado devolvem `v`, nunca base64, envelope, summary ou receipt
fornecido pela ferramenta. Preservar tipo, valores vazios/falsy e null como
propriedade própria. Não normalizar Unicode, truncar ou coagir números.

O domínio é o JSON estrito da0224: null/boolean/string Unicode escalar,
números finitos exceto -0, arrays densos e objetos simples ou de protótipo
nulo com propriedades próprias de dados. Recusar undefined, BigInt, símbolos,
holes, getters/toJSON, ciclos, NaN/infinidades e surrogates isolados. Chaves
seguem ordem lexicográfica UTF-16 do canonicalizador; arrays mantêm ordem.
Aliases acíclicos repetem por valor. Isso não é sandbox para Proxy ou código
instalado hostil.

Opção proposta do adapter:

```ts
new PostgresOperationalEffectJournal(connection, {
  resultStorage: { version: 1 }
  // fence permanece a porta nativa existente, quando aplicável.
})
```

Sem opção: escrita legada. Versão desconhecida: falha antes da execução.
Somente composição confiável escolhe o modo; campos de HTTP/modelo/output,
variáveis não validadas ou uma tag não o ativam. Fixar modo, principal, schema
e binário no manifesto de composição; não trocar modo durante uma execução.

`toolResultContext:{version:1}` não configura sozinho o armazenamento da porta
externa. A composição isolada deve injetar explicitamente um journal
compatível. Journals customizados continuam sob responsabilidade do seu owner.
Não se alega persistência nativa para uma porta in-memory.

O worker comum hoje constrói o journal sem opção; a composição published passa
o fence. Não ligar a nova opção implicitamente em nenhum dos dois, SDK,
produto ou host principal. Todo consumidor admitido ao recurso novo deve ter
wiring e readiness qualificados; consumidor não qualificado fica fora dele.

## 5. Formato físico e limites exatos

Estas são exigências de schema, não SQL implementado:

| Campo/estado                                | Invariante                                                                                                  |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `result_storage_version`                    | smallint NOT NULL, default0, somente0/1, imutável por linha inclusive retry.                                |
| Versão0                                     | `result` mantém os bytes/significado JSONB existentes; payload novo SQL NULL.                               |
| Versão1, qualquer estado                    | `result` legado SQL NULL.                                                                                   |
| V1 RESERVED/EFFECT_STARTED/FAILED/UNCERTAIN | payload SQL NULL.                                                                                           |
| V1 CONFIRMED                                | payload completo válido e bounded; `error` SQL NULL; estado/payload gravados atomicamente.                  |
| Envelope                                    | Exatamente `encoding:"base64"`, `decodedBytes`, `decodedSha256`, `data`. A autoridade de versão é a coluna. |

DB CHECKs cobrem estados, exclusividade, tipos, forma, ASCII e comprimentos.
Guard de escrita protege versão, principal autorizado e imutabilidade do
confirmado. O adapter valida conteúdo, JSON estrito e SHA. Hash detecta
corrupção; não autentica uma escrita privilegiada maliciosa.

Seja C(v) o JSON canônico e B seus bytes UTF-8. Exigir
`decodedBytes=|B|`, `decodedSha256=SHA256(B)` sem prefixo e igualdade byte a byte
entre B e a recanonicalização do valor decodificado. Um hash de conteúdo não
substitui o binding de tenant/operação/tentativa.

| Limite                      | Valor inclusivo                                                                               |
| --------------------------- | --------------------------------------------------------------------------------------------- |
| Resultado lógico no journal | 1048576bytes (1MiB); mínimo um byte JSON válido.                                              |
| Forma lógica                | profundidade64 com raiz1;1000000nós de valor; chaves contam bytes, não nós.                   |
| `data` base64               | `4*ceil(decodedBytes/3)`, máximo1398104caracteres ASCII.                                      |
| Envelope JSONB expandido    | 1398616bytes, máximo do data+512; usar `octet_length(payload::text)`, não tamanho comprimido. |
| Contexto0224, inalterado    | 32768bytes, profundidade32,10000nós.                                                          |
| Checkpoint0224, inalterado  | 8388608bytes canônicos unsigned incluindo todo o restante do estado.                          |

1MiB é a redução proposta do teto do journal, autorizada pela decisão, sem
alegar throughput/capacidade medidos. Fica acima dos32768bytes do contexto
com folga e abaixo dos8MiB originais. Checkpoint/capture não são aumentados.
O capture atual limita **todo ToolResult** a8MiB; logo, o output público máximo
fica abaixo do máximo isolado da API do journal. Os testes devem distinguir
essas fronteiras. Não aumentar budgets de capture, checkpoint, mensagem,
tokens, provider ou duração por consequência deste codec.

NUL e Unicode ficam nos bytes B, codificados como ASCII. IDs, erros e
proveniência mantêm sua validação própria; não passam a aceitar NUL.

Encode verifica limites antes de crescer buffers/strings. SELECT/RETURNING
suprime payload oversized **antes** do parser JSONB do driver, devolvendo flag
de overflow distinta de ausência; todos get/reserve/transition usam a projeção
bounded. CHECK não autoriza trazer conteúdo danificado sem limite.

Depois disso, validar versão, quatro chaves exatas, tipos, ASCII, fórmula de
tamanho e padding. Reencodar base64 e exigir igualdade; Buffer permissivo não
basta. Validar bytes/SHA, UTF-8 fatal sem BOM, scan lexical de profundidade/nós
antes do grafo, um único valor JSON e recanonicalização idêntica. Recusar
duplicatas de chaves, trailing material e formas não canônicas. Decodificar
uma vez, sem interpretar recursivamente a forma do output.

## 6. Legado, órfãos e barreira de readers/writers

Versão0 é dado bruto legado, inclusive se contiver campos que imitam o novo
envelope, `storageCodec` ou nome de versão. Versão1 com esses mesmos campos
como valor é codificada uma vez e decodificada uma vez.

Na porta opt-in, `get` pode inspecionar0 para reconciliação: strings como
`"42"`, `"null"`, `"{}"` mantêm tipo; null JSONB com flag de presença é null.
SQL NULL confirmado é resultado desconhecido, nunca null inventado. Essa
inspeção não autoriza gerar observação0224 completa nem replay.

`reserve` e transitions opt-in encontram versão0: falhar
JOURNAL_STORAGE_MODE/LEGACY_RESULT_UNKNOWN antes de replay/markStarted/corpo,
preservando a linha. Isso inclui CONFIRMED com proposal igual, FAILED,
trabalho ativo e órfãos. A0016 não dá FK de journal para parent: operationKey
igual não prova admissão sob o modo novo. Não fabricar parent, fence ou
conversão para adotar um órfão. Novas execuções opt-in reservam linhas1 novas;
histórico permanece no recurso legado qualificado ou em handoff.

Separar payload e deixar `result` SQL NULL impede devolver base64 pelo mapper
antigo, mas sozinho pode produzir SUCCEEDED/undefined. Isso também reprova a
compatibilidade. Nenhuma geração de reader antigo é considerada protegida só
por coluna, prefixo ou tag.

A alternativa de filtro RLS não foi selecionada. A política atual é de tenant;
adicionar outra permissiva faria OR e poderia manter um bypass. Uma opção RLS
teria de restringir/substituir a política existente, adaptar preflight e provar
com roles sem bypass que conflito invisível não concede reserva. O código
atual faz INSERT ON CONFLICT DO NOTHING, SELECT FOR UPDATE e lança conflito
se não lê a linha, antes do corpo; isso é fato de fonte, não prova executada
de uma política nova. Não se concede autoridade de modo por GUC de ferramenta.

### 6.1 Cutover exclusivo selecionado

No schema ativado, admitir só binários qualificados e um LOGIN runtime novo,
dedicado, com **zero memberships** e grants mínimos diretos. Sem SUPERUSER,
BYPASSRLS, ownership, DDL ou alteração de roles/triggers; manter isolamento de
tenant. Migration owner é separado. Não reutilizar credential em binário
legado, em outro recurso ou por um role compartilhado.

O guard migration-owned é SECURITY INVOKER e compara `session_user` e
`current_user` com o principal exato provisionado e o schema fixado na
instalação. SECURITY DEFINER identificaria o owner e não implementa esse
binding. Nome do principal é parâmetro confiável de instalação, não de output
nem GUC runtime. Renomear/trocar exige requalificação.

A expansão inicial não permite escrita1 por ninguém. A ativação instala o
binding imutável do principal no guard, sob owner, antes de habilitar admissão.
A ferramenta de instalação deve gerar o binding a partir de identificadores
validados/quotados e persistir seu hash no recibo de readiness; depois o runtime
não pode alterá-lo. Nenhuma janela entre expansão e ativação libera escrita1.
Essa configuração não altera os bytes aprovados da migração nem usa um GUC
runtime como autoridade persistente.

Drenar trabalho e encerrar pools/sessões antigos **do recurso sintético próprio**.
Revogar SELECT/INSERT/UPDATE/claim e rotas herdadas/PUBLIC/SECURITY DEFINER dos
principals antigos; eles não podem assumir o novo role nem obter seu segredo.
Manter somente USAGE de schema durante as provas negativas: a consulta antiga
precisa resolver a tabela pretendida e falhar42501, sem fallback para public.
Verificar privilégios efetivos, memberships, sessões e binários por hash.

A consulta SELECT original, usando credential antiga, deve falhar42501. Linha
vazia RLS ou SUCCEEDED/undefined não passam. Worker antigo deve falhar
readiness/claim antes de modelo/corpo. Permissão administrativa usada para
provisionar fixture não é prova do role de serviço. Quarentenar até essas
provas passarem; não disponibilizar o schema novo por pressuposição.

O guard exige inserts1 pelo principal ativo, recusa0 por esse principal,
recusa escrita1 por outros e mudanças de versão/payload confirmado. Guards0029
continuam condição AND independente; codec não concede fence published.
Modo ausente sob principal ativo falha readiness antes de aceitar trabalho.
Novos readers sem opt-in recusam linhas1, sem decode oportunista; queries
legadas em schema não expandido mantêm seu caminho anterior. Readiness
distingue explicitamente schema legado/expandido/ativado antes de escolher
projeção; ausência de coluna no opt-in não autoriza fallback para legado.

Isso é isolamento de credential e configuração, não atestação criptográfica
de um processo JS. Entregar a credential nova a binário antigo quebra a
premissa. Se exclusividade não puder ser garantida, não ativar. Operação mista
somente em schemas/recursos distintos; não há promessa de upgrade sem parada.

## 7. Confirmação, replay e falhas

Preservar a transação/ordem nativa: contexto tenant, locks de parent/fence/outer
existentes, journal FOR UPDATE, identidade/tentativa, recheck, UPDATE atômico e
recheck após escrita antes do commit. Revalidar prazo/lease depois de encode
bounded. Pré-calcular fora do lock não dispensa guard; não há writer paralelo
sem fence, backfill que settle ou nova garantia exactly-once externa.

Reserva1 cria RESERVED sem payload. markStarted só de RESERVED; confirm só de
EFFECT_STARTED para a mesma tentativa. CONFIRMED/payload/timestamp commitam
juntos. Repetição da confirmação da mesma tentativa exige mesmos bytes/hash;
dados diferentes geram conflito, sem shortcut que aceite qualquer resultado.

Se cair após confirmação commitada e antes do checkpoint, recuperar o valor
pelo journal, validar pela0224 e reconstruir observação sem corpo novo. Perda
de commit/ack/fence ou payload inválido exige reconciliação, sem transformar
em FAILED para retry. Estado started/uncertain não adota tentativa nova. Só
FAILED genuinamente pre-effect-safe mantém o retry nativo, limpando payload
atomicamente. Versão0 não ganha essa adoção pelo modo novo.

Resultado32769bytes/profundidade33/nós10001 que caiba no journal pode ser
CONFIRMED integralmente e virar SUCCEEDED/UNAVAILABLE no contexto0224. Parar
antes do próximo modelo; manter operationKey/settlement, sem truncar, repetir
corpo ou declarar objetivo completo por summary. Testar também300KiB.

Valor fora do domínio/1MiB/profundidade64/1000000nós não admite confirmação
parcial. Falha antes do commit continua o caminho nativo de journal incerto:
preservar started/UNCERTAIN e fato de sucesso em memória em evidência redigida,
sem confundi-lo com confirmação durável. Não demover CONFIRMED, liberar retry
ou fingir hash completo. Nova API de sucesso sem resultado não é introduzida.

Falha de markUncertain não mascara a falha original de confirm. Se re-read
provar CONFIRMED após ack perdido, preservá-lo; sem DB, parar com settlement
não resolvido. Não emitir ACTION_CONFIRMED de texto fornecido pela ferramenta.

Usar categorias existentes de OperationalExecutionError: validation_failed,
invalid_action, conflict e lease_lost. Razões redigidas propostas:
JOURNAL_STORAGE_MODE, JOURNAL_RESULT_INVALID, JOURNAL_RESULT_TOO_LARGE,
JOURNAL_RESULT_CORRUPT, JOURNAL_RESULT_CONFLICT, LEGACY_RESULT_UNKNOWN.
42501 não vira resultado ausente/sucesso. Logs contêm motivo, versão, tamanhos,
IDs/correlação e estado, nunca conteúdo/base64/credential.

### 11.1 Consequência quantitativa do teto reduzido

O cap de profundidade64 e o guard de1000000nós continuam iguais. Com o teto
público de1048576bytes, contudo, o guard de nós não é o primeiro limite
atingível: JSON estrito com N nós de valor exige ao menos2N−1bytes (chaves
não contam como nós; arrays de zeros atingem o mínimo). Assim, no máximo
524288nós cabem no journal antes do limite de bytes.

J03 deve distinguir a prova pública da prova do componente: o journal rejeita
os casos de1000000/+1 por bytes; isso não prova uma rejeição específica do
guard de nós. Exercitar o canonicalizador/scan isolado com seus parâmetros
de teste para discriminar o guard original, com evidência etiquetada como
componente, e provar a dominância do cap de bytes para a porta pública. Não
aumentar o cap do adapter, checkpoint ou captura para produzir uma fronteira
pública impossível. A revisão técnica deve validar essa consequência da
redução, sem remover o guard ou declarar uma prova não executada.
