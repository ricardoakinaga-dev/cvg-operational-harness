## Get-only transaction qualification

R2:19–33 adds the private boolean `pg_current_xact_id_if_assigned() IS NULL` in the **same native mode1 SELECT** that reads the result. Only true, with readiness/version/CONFIRMED/physical-field/decode checks, permits the exact record stamp. False/missing/unknown returns an ordinary unqualified record; confirm/reserve/transition results do not attest commit. No caller transaction is committed or rolled back by this mechanism.

This addresses a concrete durability distinction in the current adapter: [S06](sources/before/06-operational-execution-postgres.ts.source.txt):1195–1209,1271–1293 permits get through either a pool or an injected client, so a read can otherwise see that client's own uncommitted write. A permanent-journal write assigns a transaction ID; rejecting an assigned current transaction is conservative even if that ID came from unrelated work. A read transaction without an assigned writing ID can still read previously committed rows; the design does not require autocommit and does not use absence of a transaction label as proof. The boolean is native query metadata, not a field accepted from logical output. MVCC, normal native access controls and exact record bindings remain necessary; this signal is not a replacement for them or a new fence.

[S17 probe](sources/before/read-transaction-probe.json.source.txt) records true for autocommit read and BEGIN without assigned xid, false with assigned xid, then true after rollback. Its limited local/admin signal observation is **not** a journal recovery proof or runtime-role permission proof.
