Host futuro `apps/cli`, pacote privado `@cvg/cli`, binário `cvg` compilado pelo build do workspace. Entradas propostas: `src/{main,argv,output,config,bootstrap,commands}.ts`, testes próprios e manifesto do pacote. O bootstrap é código estático do host, composto com os mesmos exports instalados de SDK, harness, adapters e persistência. Não carregar módulo, script, executável ou plugin indicado pelo arquivo de entrada, cwd, modelo ou configuração de usuário. Não modificar SDKv1, vocabulário Codex selecionado, core/contracts, migrations, controles ou política para acomodar o CLI sob este gate. Mudança necessária nessas fronteiras volta ao contrato do respectivo owner.

A composição confiável fornece portas mínimas: consulta de sessões; leitura/fork de sessão; facade0239 em roleclient; cliente HTTP para as rotas K06 e inspeção existente da API; resolução de perfis autorizados; identidade autenticada; e fechamento dos recursos locais. O bootstrap usa o binding de identidade e credenciais já qualificado do host, sem derivar grants de JSON. O CLI não recebe o executor0239, `runExact`, tools, modelo ou autoridade de aprovação. Um worker independente consome a execução durável. Não usar `createSdk` com seu store de memória padrão para simular uma instalação durável.

Cada porta traz binding confiável do principal/tenant e manifesto qualificado. As portas de sessão, execução e API precisam provar o mesmo principal/tenant e a mesma composição durável; não comparar apenas strings fornecidas pelo usuário. O CLI não traduz identidade de sessão em permissão de caso e não importa o domínio de produto para o núcleo. Sessão/execução alheia e inexistente preservam a resposta opaca do backend.

Nenhum argumento aceita tenant, principal, papel, grants, orçamento de execução, SQL, pool, ferramentas ou approval. O nome de perfil é uma seleção entre perfis autorizados pela composição, não uma fonte de autoridade. Composição sem a porta necessária retorna `UNSUPPORTED_CAPABILITY` antes de dispatch; não substitui a operação por uma parecida. A indisponibilidade deve continuar contando como requisito não implementado, mesmo que a recusa passe em teste.

## 3. Configuração e operação offline

`--config <arquivo-absoluto>` é explícito e opcional para configuração de apresentação/seleção. Sem esse argumento, usar defaults internos; não procurar HOME, cwd, `.env`, repositório ou URL. Arquivo regular aberto por descriptor com verificação de tipo e leitura limitada, UTF8 estrito, JSON objeto sem campos desconhecidos, até64KiB, profundidade8, até128 aliases e strings até256 caracteres. O único schema aceito é:

```ts
type CliConfigV1 = {
  formatVersion: 1
  profileAliases?: Record<string, string>
  defaultProfile?: string
  output?: { color?: false }
  observationTimeoutMs?: number
}
```

Aliases e IDs têm1–120 caracteres, padrão `[A-Za-z0-9][A-Za-z0-9._-]*`; resolver exatamente um alias, sem herança/ciclo. O alvo só vira perfil operacional depois da resolução autorizada do host. `defaultProfile` precisa ser alias declarado ou ID sintaticamente válido. Config não aceita credenciais, referências de credencial, endpoints, paths de módulo, providers, subprocessos, prompt, persona ou opções de policy. Sua validação offline prova o schema, não a existência/autoridade operacional do perfil. Flags explícitas prevalecem apenas nos campos locais; elas nunca ampliam os limites/grants do host. Timeout é de observação, não deadline do modelo.

Doctor e config não inicializam autenticação, pool, conexão, processo, modelo ou ferramenta. O binário precisa fazer parse e escolher esse ramo antes de importar/inicializar o bootstrap online. Leitura/hash de configuração e metadados locais do pacote são permitidos. Não ler variável secreta para depois tentar redigi-la.

`config dump --redacted` emite somente a projeção `{formatVersion,profileAliases,defaultProfile,output,observationTimeoutMs}` validada, com `operationallyVerified:false`. Paths de origem, variáveis e diagnósticos arbitrários não entram na saída. Campos proibidos são erro, nunca impressos. Os dois níveis de validação são explícitos: `STATIC_VALID` offline e seleção efetiva autorizada durante um comando online. Não adicionar herança/presets de0256 nesta implementação.

## 5. Entrada, saída e códigos de retorno

`--input -` lê stdin atéEOF; arquivo deve ser regular e escolhido explicitamente. Abrir descriptor, conferir tipo/tamanho e ler com contador de bytes, inclusive se o arquivo crescer; não carregar diretório/FIFO/socket nem seguir leitura ilimitada. Limite1MiB, UTF8 fatal, sem executar/template/interpolar o conteúdo. `run` envia um item textual0239, preservando o texto e a normalização de text_elements do contrato; o arquivo não é RuntimeInput nem configuração. Steering também aplica o limite nativo1–4096 pontos de código antes de qualquer envio. IDs seguem limites dos respectivos contratos; CLI não converte identificador/cursor opaco em número.

Stdout é JSONL UTF8 comLF, sem ANSI/progresso/debug. Cada objeto tem `{schemaVersion:1,kind,command,...}`. Kinds fechados: `request_prepared`, `thread_created`, `result`, `execution_receipt`, `session_event`, `native_event`, `command_end`, `error`. `command` é o nome fixo da operação, não argv bruto. IDs da CLI são strings; valores wire/i64 do subpathCodex, se utilizados por um adapter, passam pelo codec exato antes da projeção, nunca por Number. Isso é um protocolo CLI próprio, sem alegar compatibilidade literal com o wireCodex.

`command_end` tem `status`, `exitCode`, `executionTerminal:boolean` e, quando conhecidos/autorizados, sessionId/executionId/lastCursor. Status fechado: `SUCCEEDED`, `ATTACHED`, `STATIC_VALID`, `READY_OFFLINE`, `ACCEPTED`, `CANCEL_REQUESTED`, `WAITING_APPROVAL`, `PENDING`, `CANCELLED`, `FAILED`, `OUTCOME_UNKNOWN`, `UNSUPPORTED_CAPABILITY`, `INTERRUPTED`. `executionTerminal:true` só acompanha fato nativo confirmado. Há no máximo um command_end por processo/comando; receipt, delta, espera e terminal da execução são fatos distintos.

`error` contém somente `{code,phase,outcome:'not_dispatched'|'unknown'|'known',retryable:false}` mais IDs autorizados. Códigos locais fechados: `INVALID_ARGUMENT`, `INVALID_CONFIG`, `INPUT_LIMIT`, `INPUT_INVALID_UTF8`, `UNSUPPORTED_CAPABILITY`, `NOT_FOUND`, `DENIED`, `TRANSPORT_UNAVAILABLE`, `STORAGE_UNAVAILABLE`, `OUTCOME_UNKNOWN`, `CONFLICT`, `CAPACITY`, `CONTEXT_OVERFLOW`, `CURSOR_INVALID`, `CURSOR_UNAVAILABLE`, `DELIVERY_LIMIT`, `INTERNAL_ERROR`, `CLEANUP_UNCONFIRMED`. Mapear códigos nativos conhecidos sem imprimir stack, SQL, headers, token, argv bruto, conteúdo de config ou mensagem arbitrária de exceção. `retryable:false` significa ausência de retry automático deste CLI, não que uma futura leitura/reconciliação seja proibida. Stderr só recebe um resumo fixo do código e logs locais seguros, nunca payload de usuário.

O stderr do processo não substitui o envelope de erro. Se stdout fechar/EPIPE, parar o leitor/novas admissões locais, não avançar o cursor e não tentar escrever um terminal impossível nesse pipe. O exit ainda registra falha/interrupção local. Nunca transformar perda de observação em sucesso da execução.

## 6. Streaming, cursores e lifecycle

Uma escrita por vez; respeitar callback/drain de stdout. Frame CLI máximo4MiB incluindoLF, fila máxima16MiB e128 registros; ao atingir o limite, parar de buscar páginas, sem descartar silenciosamente dados. Se um único evento exceder o frame, `DELIVERY_LIMIT` e último cursor anterior; não truncar dado e avançar. Página nativa segue128eventos/2MiB0239; sessão segue os limites do port. Solicitar a próxima página somente com capacidade na fila. Não materializar todo o histórico para depois simular deltas.

Manter cursor de fonte e escopo distintos; um cursor de sessão não pode ser aplicado ao log nativo nem a outra sessão/execução/tenant. O CLI usa o cursor opaco do port, com selector de fonte explícito, e não cria cursor durável concorrente. Cursor confirmado localmente é só o último write concluído; isso não prova consumo do outro lado do pipe. Um novo processo pode receber replay e deduplicar pelo ID/ordinal nativo. Nunca anunciar entrega exatamente uma vez.

Timeout de observação padrão300000ms, configurável100–3600000ms; request de leitura/controle tem teto30000ms por chamada ou limite menor do port. Esses limites não estendem lease/deadline do kernel. Sem busyloop: SDK sessão usa espera cancelável de250ms entre páginas vazias; subscribe0239 usa sua sinalização/releitura e a APIwait seu limite0302. Não auto reconectar nem reenviar chamada perdida. EOF do input antes de submit só completa a leitura textual; EOF/EPIPE do consumidor fecha a observação.

SIGINT/SIGTERM fecham o leitor e as portas locais, sem chamar cancel implicitamente. Cancelamento durável exige `execution cancel`; a mensagem de ajuda precisa declarar esse comportamento. A composição fecha readers/subscriptions/client e os pools/conexões que ela própria criou; não encerra worker, pool emprestado, outra execução ou geração de outro owner. Deadline de cleanup local5s não prova quiescência: se não confirmado, registrar `CLEANUP_UNCONFIRMED` separado da causa inicial, sem emitir execuçãoCANCELLED/SUCCEEDED. Não chamar `process.exit` para esconder handle vivo; falha real de término é resultado que bloqueia a qualificação nativa. Fechar o reader enquanto o worker persiste eventos deve permitir inspeção/retomada por outro CLI.
