## F01 — P2 / material design revision: no specified final pause/cancel veto after ledger and journal awaits

**Candidate contract.** S:322 (A11) requires pause/cancel after checkpoint/approval but before body to produce body0 and keep a consumed grant consumed. S:112 delegates guards/dispatch to the real kernel. S:126 specifies receipt, operation/binding and authorization checks in `CapabilityImplementation.execute` / `executeAuthorizedPreparedCommand`. S:165 specifies a latch check around `EffectLedger.started`; S:167 adds a latch recheck before the handler. None specifies re-reading the pause port or checking the effective tool signal after the remaining awaits, immediately before invoking the original handler. A healthy evidence latch is not the same fact as an unpaused, uncancelled turn.

**Captured mechanism.** `I/packages/harness/src/kernel/pipeline.ts.source.txt:474–513` checks duration and `revalidate` first, then **awaits** `effects.started`, and then calls `raceInvoked`. That helper explicitly starts the operation before inspecting cancellation (`:157–180`, particularly `:166`); it is not an additional pre-body cancellation gate. `I/packages/harness/src/kernel/controls.ts.source.txt:232–249` reads pause at step entry and kernel guards, with no subscription that re-runs guards after ledger acknowledgement. The selected journal wrapper adds awaits for `journal.reserve` and `journal.markStarted` before `tool.execute` (`I/packages/harness/src/effect-journal.ts.source.txt:314–348`). The capability adapter then validates input and calls its implementation (`I/packages/harness/src/capability-boundary.ts.source.txt:351–372`), without another kernel pause check.

**Concrete counterexample permitted by the written HOW.** The valid single synthetic scheduling command has passed policy/approval and final kernel revalidation. Hold `EffectLedger.started` (or the subsequent `journal.markStarted`) pending. Acknowledge pause on the same injected local pause port while that operation is pending, then acknowledge the write successfully inside the deadline. Evidence remains healthy and receipts remain valid. The kernel proceeds through the journal to the proposed executor; all checks expressly listed in S:126/165/167 can succeed, and the original handler can run despite the earlier pause acknowledgement. For cancellation, a successful bookkeeping await can similarly return into an already aborted effective tool signal; the specified receipt/latch checks alone do not prohibit handler entry. No evidence fault is required for this interleaving.

This is a gap in the proposal's mechanism, not an observed execution failure. Restricting the public scope to a pure synthetic tool reduces immediate impact, so this is P2, not a claim of an actual sensitive effect. It still contradicts an explicit material control contract and leaves implementation to invent a new final veto and projection rule.

**Required revision.** Specify an internal monotonic final admission check at the actual prepared-handler boundary, after ledger/journal awaits, using the same composed pause state and effective signal/deadline. State its ordering relative to `bodyStarted`, receipt consumption and the synchronous invocation of the original handler; avoid an unguarded await after that check. Define how pause-read failure and a late pause/cancel project into the exact stop/trace/handoff/tool status matrix when the kernel has already entered its executor wrapper, while keeping consumed approval consumed and preserving ledger/journal facts without pretending the handler ran. If this instead requires a kernel seam, declare that change and its scope explicitly; do not silently rely on an existing factory option.

Add a static acceptance oracle to the proposed suite: hold ledger-start ACK and journal-start ACK separately, inject pause and cancellation separately, then release a successful ACK. Assert original handler count0, no successful public output, exact chosen normalized stop/envelope, no grant release/reissue and no replay. Include late ACK after deadline as a separate case. This expands A11's concrete windows; it does not require running tests during this review.
