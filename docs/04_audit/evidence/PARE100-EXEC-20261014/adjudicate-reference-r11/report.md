## Original contract and interpretation

SPEC0209:8 asks for manifests, exports, declared methods/interfaces/configs/events and generated catalog data. SPEC0209:10 expressly requires both `source path relativo` and a `declaração/forma de contrato sem corpo de implementação`, followed by `Extrair somente dados de contrato; não importar/vendorizar/copiar implementação DeepSeek.` These obligations must hold together.

SPEC0209:12 requires UNKNOWN, reason and source for data dependent on execution or not statically extractable, and prohibits parity PASS from cataloging. It does not say that every statically extracted token needs proof that it cannot parse in any programming language. SPEC0209:14 prohibits silent reference changes, missing sources and removed requirements; SPEC0209:20 prohibits denominator reduction and retains semantic review beyond the index.

Accordingly, three roles have distinct legitimate treatment:

1. **Implementation:** function/method bodies, executable expressions, and literal program text supplied as executable source are excluded from copied contract output. Moving established implementation bytes to a type, identity or metadata-looking key does not create an exemption. UNKNOWN alone does not cure a raw body still serialized elsewhere.
2. **Declaration/contract data:** public names, module/event/property identifiers, declared types and recognized schema vocabulary may require their actual spelling to describe the contract. A valid literal-valued declaration is not automatically an implementation body. Its incidental parseability in another grammar is insufficient evidence of a violation. Conversely, an alphabet predicate alone cannot establish a payload's semantic role.
3. **Provenance:** an authenticated relative source path is a locator required by SPEC0209:10. It need not be an identifier in the source language. Program-looking characters in the locator do not make the locator a copied source body. Provenance must remain inert, authentic and traceable; copying body-derived text into a fake locator would fail this role test.

Source authentication proves origin, not semantic role. The role is established by the source slot and its relevant context, not the words `name`, `type`, `source`, a marker, or a slash/brace blacklist. A public declaration can have dual roles; where the permitted evidence cannot resolve whether it also carries an implementation payload, that material issue stays OPEN. This report neither invents a universal language recognizer nor grants a blanket exemption for all declarations.

**What the examples establish and what they do not.** The critic's report:30 declares a literal type and initializes an exported constant with the same literal. It demonstrates two representations of identical bytes, one opaque and one readable. The name `WORKER_SOURCE` is evidence to question the role, but does not itself show a worker constructor, evaluator, program-source format, or other consumer. Even accepting the critic's JavaScript parsing observation, a statement-shaped literal can also be an exact API value. The original SPEC does not settle this particular dual-role specimen solely by its characters or variable name. Treat its semantic role as **OPEN**, rather than pronounce the output either safe or a demonstrated HIGH implementation leak.

The standalone JSON `{"name":"throw/GUEST_BODY_MARKER/"}` (critic report:38) is weaker evidence: in a recognized tool catalog, that can simply declare the tool's actual name. A declared required-property token can similarly be legitimate. The report has not shown an implementation consumer or context for that JSON value. Copying that name is not intrinsically a breach of SPEC0209:10. Python annotations and string-named members require their own role analysis; one cross-language parse example does not establish implementation vendoring for all those categories.

**A narrower concern is grounded in source.** `projectJsonContract` receives only the immediate field name. Array recursion keeps it (:915–916), but object recursion replaces it with each child key (:927–931). Therefore entering an arbitrary data object under `default`, `const`, `examples`, or another payload field does not preserve that context: a nested `name` is again eligible for the vocabulary allowance. A NOT_RUN illustrative object is `{"default":{"name":"throw/GUEST_BODY_MARKER/"}}`. This proves a context reset in the projection, not by itself an actual executable payload: an instance property named `name` could still be legitimate default data. A finding must identify its role before declaring a body leak. If that nested value actually supplies program source, the present lexical allowance is not a sufficient contract boundary. The same applies to a literal type that reproduces established worker-source bytes. The no-implementation constraint applies across both representations.

**Materiality and confidence.** High confidence (0.93) that REFINE is the correct disposition and the broad HIGH rationale is insufficient. High confidence in the source traces and JSON context loss. Confidence that the minimal examples themselves prove implementation copying is insufficient; their payload role remains OPEN. A confirmed complete program-source leak would be material regardless of length, an UNKNOWN enclosing entry, or hashes elsewhere. A legitimate selector/name merely resembling a program does not establish that leak.
