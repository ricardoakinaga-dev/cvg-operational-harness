## Findings

### I1-001 — P1: bootstrap and evidence recovery lack a consistent commit-state predicate

**Candidate:** `spec.md:60`, `:119`, `:123–126`, `:177`; related policy mapping `:50`.

Bootstrap returns a BOOTING owner and only successful boot/publication/evidence permits OPEN. Bootstrap is serialized with publication and must authorize before activation and immediately before its first publication. Yet the only concrete commit sequence requires “checar owner OPEN” at step 4. It does not give a BOOTING-specific commit predicate. Separately, failed post-commit append moves the owner to EVIDENCE_PENDING, but step 6 allows its ACK to reopen admission only “se o owner ainda estiver OPEN.” The state table instead permits EVIDENCE_PENDING → OPEN on valid receipt/ACK. These are different state predicates, not synonyms for an admission flag.

**Counterexample schedules (not executed):**

1. Create owner B; B is BOOTING. Both bootstrap policy calls ALLOW; candidate READY; publish-authorized append ACKs. Step 4 rejects B because it is not OPEN. Opening B first contradicts the requirement that only the successful bootstrap publication/evidence admits work. A separate initial-publication exception would be a new design decision.
2. An OPEN owner's replacement commits revision 2. `published` append rejects or is unknown; owner becomes EVIDENCE_PENDING. Reconcile authorizes and its observation ACKs. Step 6's OPEN predicate is false; the state table's recovery predicate is true. Implementers must choose between a permanent fence and a transition the numbered algorithm does not authorize.
3. Close wins during either schedule: CLOSING must dominate both completion paths, including a delayed ACK.

**Required revision:** specify distinct initial-publication and replacement state transitions, the synchronous point where each is eligible, and a single receipt-bound EVIDENCE_PENDING → OPEN recovery predicate that explicitly excludes CLOSING/CLOSED. Freeze whether the temporary publication fence is a separate flag or an owner state. Preserve the stated no-rollback/no-reactivation rule.

### I1-002 — P1: reverse cleanup joins returned disposer promises, but not explicitly each disposer's outstanding producer subtree

**Candidate:** `spec.md:147`, `:159–161`, `:165`, `:167–171`. **Native evidence:** `cvg/packages/harness/src/kernel/host.ts:90` invokes rollback cleanup; `:134–142` pops and awaits each returned disposer, swallowing rejection. The proposed shared primitive must replace that observable behavior; current `dispose(): Promise<void>` is not a proof of quiescence.

The candidate correctly retains original promises and child IO after consumer timeout. It requires zero operations before **starting** generation cleanup, and reverse sequential unwind until a pending disposer resolves. It does not specify the advancement predicate when a disposer has settled while a separately tracked cleanup IO child remains active. The explicit owner-port close barrier in lines 161/171 is later than generation-resource disposal and does not define this per-item barrier. The broad no-resource-in-use invariant states the desired result; the stated cleanup sequence leaves this lifetime decision unresolved.

**Counterexample schedule (not executed):** generation reaches zero users and begins reverse cleanup `[D2, D1]`. D2 issues permitted, tracked cleanup/audit IO Q that uses resource R1 owned by D1. D2 awaits Q through a finite timeout race and then resolves or rejects; Q's original promise remains ACTIVE. The sequential algorithm can now invoke D1, closing R1 while Q uses it. Q is declared/observed IO, so this does not rely on hidden plugin IO or a resurrected token. Repeating the generation's initial zero-counter test is also insufficient if it accidentally includes the currently executing cleanup token itself and self-joins.

**Required revision:** define the private cleanup-item root and its descendant join, and require both the original disposer promise and all its admitted descendants to settle before advancing to any dependent earlier item. If Q hangs, keep the current item/resource dependency chain CLEANUP_PENDING. If Q fails after D2 returns, preserve that failure in the same item's report. Apply this to boot rollback, normal retirement, late acquisitions, and owner-owned resources through the one shared primitive. Do not add a retry of an uncertain disposer.

### I1-003 — P2: full authenticated AgentProfile snapshots have no aggregate retained-size bound

**Candidate:** `spec.md:65–66`, `:80`, `:133–137`. **Native fields:** `cvg/packages/contracts/src/contracts.ts:22–31` contains unbounded arrays `instructions`, `skills`, `tools`, and `policies`. Context/state also contain arbitrary JSON values (`:143–152`).

The 256 KiB aggregate limit is explicitly for plan/config. The 16 MiB bookkeeping enumeration covers requests/receipts/history/attempt snapshots; it does not explicitly charge the complete authenticated agent snapshots held by live pins. A per-string limit and a pin count do not supply this missing aggregate bound. This is owner-created retained memory, not the excluded memory of an external port or caller's copies.

**Counterexample (arithmetic only, not allocated):** a valid AgentProfile with 2,048 distinct ASCII instruction strings of 16,384 bytes retains at least 33,554,432 payload bytes before JSON/object overhead. Each string meets the stated ceiling; the profile is not plan/config. One pin already exceeds the entire stated bookkeeping budget unless an unstated aggregate rule rejects or charges it. Up to 1,024 live pins can amplify the gap.

**Required revision:** bound total bytes/nodes/depth/array lengths of agent and turn snapshots, identify which owner budget pays for them, and reserve before cloning/hashing/authenticating or invoking policy. Define dedup/reference accounting and release of terminal snapshots without losing the full-profile binding. Include oversized full-agent fixtures, not just oversized plans and strings.

### I1-004 — P2: self-join prevention does not cover release receipts and read authorization recursion

**Candidate:** `spec.md:67`, `:69–71`, `:119`, `:145`, ML15 at `:220`. **Native dependency:** single-pass `kernel/kernel-runtime.ts:635–649` awaits turn/end listeners; audit control `kernel/controls.ts:702–722` races the audit append but its original promise remains owned under the proposed tracker.

The concrete rule detects self-join for close and waits on **that** close receipt. Release is separately allowed cleanup without a new grant. There is no corresponding rule for an owned callback waiting for release of the lease whose outstanding work includes that callback. Nor does “inventory is read-only” prevent recursive PolicyEngine.evaluate calls when the policy port itself calls authorized inventory. Mutation-queue recursion detection alone does not cover either dependency.

**Counterexample schedules (not executed):**

- A trusted audit port callback, with a host-held native lease, calls `lease.release()` for its own turn. Release waits for admitted use including the original audit callback. After a PENDING result, the callback polls `owner.wait(releaseReceipt)` until release completes. The audit's native 200 ms grace may finish the runtime race, but its original callback is still active and part of the join. No poll can complete the dependency it is blocking. Finite observer timeouts bound each poll, not this self-wait cycle. Even one long finite self-wait cannot make progress.
- A captured management policy callback calls `owner.inventory()` and awaits it. Inventory requires read authorization through the same policy port, recursively reentering that callback. The rule describing inventory as read-only does not reject this recursion.

These host callbacks need no payload-supplied functions or exposed plugin mutator.

**Required revision:** define one native dependency/reentrancy rule for ready/release/wait/close and management policy/audit/read callbacks. A wait whose target transitively depends on the current ACTIVE producer must immediately reject REENTRANT_OPERATION (or return an explicitly nonwaiting observation), while cleanup admission changes remain monotonic. Include release-receipt self-wait and policy→inventory recursion as distinct ML15 cases.

### I1-005 — P2: persisted lifecycle action names disagree between the canonical adapter and the publication algorithm

**Candidate fields:** `spec.md:52` requires `AuditEvent.action = plugin.lifecycle.v1.<kind>`; `:123` calls the record `plugin.lifecycle.publish_authorized`; `:125` calls it `plugin.lifecycle.published`. Native `AuditEvent` has exactly a string `action` and string `result`, not a separate event-name/metadata field (`cvg/packages/contracts/src/contracts.ts:493–508`).

**Counterexample (not executed):** one adapter persists `action=plugin.lifecycle.v1.published`, `kind=published` in result; another follows step 5 literally and persists `action=plugin.lifecycle.published`. Both can retain all listed result fields. An evidence reader/filter keyed to either exact action omits the other's committed/reconciled decisions. This is material for a contract that specifically requires lossless native evidence and distinguishes unknown writes from absent effects.

**Required revision:** provide a finite canonical table of exact `kind`, `phase`, and `AuditEvent.action` for bootstrap authorization/commit, replace authorization/commit, and reconciliation attempts, including failed/unknown outcomes. Use those exact literals in the algorithm. State explicitly if the non-versioned strings were intended only as prose aliases. Keep `ML1:` canonical JSON in native `result`, its byte limit, attempt identity, and the no-exactly-once-audit limitation.
