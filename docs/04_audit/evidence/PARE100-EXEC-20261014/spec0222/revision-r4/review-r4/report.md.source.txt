## Finding I1-R4-001 — Effective tool configuration is not bound to native effect replay identity

**Severity:** MEDIUM; blocks an unambiguous lifecycle foundation. **Confidence:** 0.86 overall (high for the native hash/replay behavior, moderate-high for the missing normative restriction). Static contract finding; no runtime exploit or simulation was executed.

**Candidate evidence:** `spec.md:34` binds a catalog entry to reviewed artifact bytes, configuration validators and activation; it records artifactDigest, configDigest and compositionFingerprint separately. `spec.md:113` admits plugin/version/config plans. `spec.md:119` mandates the existing CapabilityRegistry and journal adapters with an owner-shared effectJournal. `spec.md:121` retains the descriptor fingerprint algorithm and puts configuration/artifacts in a separate plan digest. There is no explicit rule making a changed effective tool configuration change a descriptor/provider version, or otherwise change the native proposal binding. `spec.md:105` injects local execution identities but does not specify a generation/configuration namespace for ToolInvocation.operationKey.

**Primary-source evidence (paths relative to the sealed packet):**

- `cvg/packages/harness/src/capability-boundary.ts:133-144`: compositionFingerprint hashes the sorted descriptors only. The normalized descriptor fields at `:249-262` include provider identity/version, but no effective configuration or reviewed artifact digest.
- `cvg/packages/harness/src/createOperationalHarness.ts:221-227`: the current factory passes that fingerprint to the journal adapter.
- `cvg/packages/harness/src/effect-journal.ts:251-278`: proposalHash includes compositionFingerprint, selected tool/provider fields and invocation input, not configDigest, planDigest, generationId or executionId.
- `cvg/packages/harness/src/effect-journal.ts:119-141`: native in-memory reserve keys by tenant/operationKey and rejects a different proposalHash; an equal proposal returns the previous record.
- `cvg/packages/harness/src/effect-journal.ts:314-324`: CONFIRMED returns the saved output without executing the current tool.
- `cvg/packages/harness/src/kernel/kernel-runtime.ts:477-508`: single_pass passes the resolved requested invocation into the native pipeline. The contract allows an operationKey (`cvg/packages/contracts/src/contracts.ts:97-102,192`).

**Concrete permitted counterexample:** A reviewed synthetic catalog plugin `kv@1` accepts configuration `{namespace:"A"}` or `{namespace:"B"}`. Its activation closes over that namespace, while producing the same valid `kv.put@1` descriptor/providerVersion in both cases. In generation G1, a single_pass request for tenant T, operationKey K and input `{key:"sample",value:"x"}` confirms a synthetic result identifying namespace A. An authorized replace installs the same reviewed artifact with namespace B; configDigest and planDigest change correctly, but its descriptors and capabilityFingerprint do not. A new G2 turn carrying K and the same input reaches the same journal proposalHash and returns the confirmed A output without invoking B or detecting a changed proposal. Unique local execution IDs do not enter this journal binding.

This does not require forged metadata, an unreviewed module, changed artifact bytes, malicious policy, durable resume, or a raw ToolRegistry. The last sentence of `spec.md:119` rejects swapping only an implementation while retaining an old identity/digest; here artifact bytes remain correct and configDigest is updated truthfully. If that sentence is intended to prohibit all behavior-changing configuration aliases too, the catalog/config-to-descriptor rule needs to say so concretely.

**Invariant:** the native journal's exact-composition/proposal conflict boundary must not silently identify two different effective tool targets as the same proposal. A lifecycle plan digest outside the proposal hash cannot enforce that invariant. Reporting G2 execution with a replay from a different effective binding also needs an explicit contract, not an accidental alias.

**Minimal normative correction:** for managed tools, require an immutable catalog binding from the normalized tool/provider identity/version tuple to reviewed artifactDigest **and canonical effective tool configuration** (including any target-affecting binding). A changed binding must change an existing descriptor/provider version so the unchanged native CapabilityRegistry fingerprint changes; reject a plan that aliases different effective bindings under the same descriptor identity. State the scope of this binding across retained generations and owners sharing a journal. Do not silently change the legacy fingerprint algorithm or contracts package. If the intended solution instead changes operationKey/proposal semantics, specify that alternative and its compatibility consequences explicitly before BUILD.

**Required future negative/positive proof:** a synthetic A→B configuration change with the same descriptor identity is refused before publication, or has a specified distinct native proposal binding; reusing K must not silently yield A as B's result. Verify actual factory/kernel/journal wiring, unchanged-binding retries retaining native idempotence, and concurrent old/new leases. Add this case to ML04/ML06/ML07/ML18 rather than declaring an existing broad family sufficient. Do not infer approval reuse: native executionRef checks may independently prevent some approval scenarios, and no approval-port implementation was exercised here.
