**F1 — P1: the explicit operation boundary omits an asynchronous managed planner and nested control IO.**

Invariant: a generation's owned resources, and subsequently the owner's owned controls, must remain alive until every admitted native callback and its owned continuation settles, even after the turn returns a deadline result.

Proposed contract: SPEC lines 16, 96–106 manage `planner/model/tools/telemetry`, but line 98's concrete mandatory instrumentation enumerates `ModelGateway.complete`, `ToolDefinition.execute` and capability hooks. It does not name the planner/iterative-orchestrator promise or original asynchronous control-port calls. The generic statement “real operations” does not resolve that gap at the actual native boundaries.

CURRENT evidence: `cvg/packages/harness/src/kernel/kernel-runtime.ts:281–297` races `host.get('planner').decideNextStep(...)`; `kernel/pipeline.ts:139–154` returns the budget/cancellation winner without joining the callback. `iterative-runtime.ts:991–1015` similarly races the original `options.orchestrator.decide(...)`. `hybrid-orchestrator.ts:135–153,196–210` confirms that a gateway is only one constituent operation of an orchestrator. Separately, `kernel/controls.ts:702–730` and `iterative-runtime.ts:1660–1687` can return an audit failure after a deadline while the original `AuditSink.append` is still unresolved. The former is a control hook, not one of the capability hooks enumerated by line 98.

Counterexample schedule (deduced, NOT_RUN): G owns resource R acquired during activation. Its ordinary `decideNextStep` returns an asynchronous promise that waits on a barrier and then reads R; it uses no model/tool/hook and starts no detached background task. The native planning race times out; `runTurn` returns; release removes the last pin; replace retires G. Under the listed instrumentation, no real-operation count retains this planner, so cleanup disposes R. The barrier then resolves and the still-running planner uses a disposed resource. The analogous owner case closes an OWNED audit client after its turn/end hook has returned a deadline while its original append is still active.

Observable wrong result: inventory/close can claim disposal before the admitted callback has stopped using its resource, followed by a use-after-dispose/rejected late write. This directly defeats quiescence, not merely output completeness.

Minimal contract repair: enumerate and require tracking of the full original `planner.decideNextStep` and generation-created iterative-orchestrator `decide` promises. Preserve a producer token through their continuations, independently of individual model-call tokens. Specify original control/store/journal IO accounting wherever a native deadline can detach it, with owner-level joins before OWNED controls close. BORROWED ownership does not remove the join obligation. Fix the wrapper placement and no-new-producer rules; do not rely on optional plugin calls to `track` to compensate for an ordinary native service invocation. Add these exact schedules to ML11/ML13/ML16, all **NOT_RUN**.

**F2 — P1: “controls first” does not define monotonic authority for admitted capability hooks.**

Invariant: a capability cannot convert a control-denied/unaudited result into apparent success or alter the already-authorized dispatch identity. Protecting control registrations alone is insufficient.

Proposed contract: SPEC lines 36, 68, 78 allow “permitted” hooks and forbid control replacement/reordering, but never enumerate the permitted HookPoints or constrain what their arguments, continuation and returned outcome may change.

CURRENT evidence: `kernel/types.ts:170–198` defines outcome-replacing `tool/post-execute` and `turn/end` hooks and around-body continuations. `kernel/host.ts:115–121` orders controls first. In `kernel/kernel-runtime.ts:635–649`, each turn/end return replaces `current`, including returns by capability listeners after the audit control. `kernel/controls.ts:702–730` changes a result to `INSUFFICIENT_EVIDENCE` when audit fails. `kernel/pipeline.ts:574–595` likewise accepts each post-execute replacement, without a monotonic control-outcome check.

Counterexample schedule (deduced, NOT_RUN): a reviewed capability registers a turn/end result formatter that returns its cached successful result. Audit append fails; the fixed audit control returns `INSUFFICIENT_EVIDENCE`; the capability runs afterward and returns `COMPLETED`; the final kernel log succeeds. The native finish path returns/logs `COMPLETED` for a turn whose mandatory audit failed. No control was unloaded, reordered or replaced. The new catalogue/hook API has not said whether this hook is illegal or how such a result is constrained.

Observable wrong result: success reaches the caller despite a mandatory control failure. This is a concrete native-hook authority discrepancy, not a claim of isolation against arbitrary hostile JavaScript.

Minimal contract repair: freeze a finite managed hook matrix specifying allowed points, detached/read-only versus mutable fields, outcome authority, and continuation cardinality/lifetime. Either reject outcome-transforming hooks in this foundation or enforce that capability returns cannot weaken a control stop/uncertain settlement; similarly preserve authorized tool/approval identity and prevent multiple/delayed continuation dispatch from bypassing a single authorization. Catalogue review must enforce this explicit contract. Extend ML03/ML09/ML15 with the audit-failure schedule; **NOT_RUN**. Merely retaining “controls first” does not repair it.

**F3 — P2: lifecycle policy and evidence facts have no specified mapping to the actual native ports.**

Invariant: the management authorization decision and its audit observation must bind the same actor, tenant/profile, action, request digest and committed revisions through the real port contract.

Proposed contract: SPEC line 40 asks the existing PolicyEngine to evaluate an actor, profile resource and request digest; lines 70 and 86–89 require runtimeProfile/owner/revision/request/digest/attempt facts in audit. Line 131 defers whether public contracts need changing until BUILD.

CURRENT evidence: `cvg/packages/contracts/src/contracts.ts:294–312` requires a `PolicyRequest` containing `tenantId`, `agentId`, `action`, **tool: ToolDefinition**, **invocation: ToolInvocation**, and `correlationId`. It has no actor/profile/resource/digest fields. `contracts.ts:493–509` gives `AuditEvent` only the fixed actor/agent/tenant/action/policy/approval/tool/result/timestamp/trace/correlation fields; there is no facts/metadata field. `TelemetryEvent.attributes` exists at lines 523–527, but is a different port with fixed-label restrictions. Extra object fields are not a portable AuditSink storage contract.

Concrete discrepancy: an implementation passing the prose-shaped `{actor, profile, resource, digest, ...}` to `evaluate` lacks the native required tool/invocation. Filling those with unrelated execution-tool data authorizes the wrong target. Adding undeclared audit `facts` can be accepted by a structural adapter and silently discarded by a sink that persists only AuditEvent's declared fields. Publication can receive ACK while the required request/commit binding is absent from stored evidence.

Observable wrong result: management cannot be authorized against the intended target consistently, or two distinct publication decisions become indistinguishable in the supported audit projection. This is unresolved API design; no assertion is made that a proposed method already exists or compiled.

Minimal contract repair: decide now between a precise local adapter and an explicitly reviewed public-contract extension. The smaller option is a host-created, non-executable lifecycle target descriptor/invocation with a versioned canonical resource/digest envelope, and a versioned encoding of all required evidence into supported AuditEvent fields. Specify actor-to-agent mapping, trace/correlation issuance, digest inputs, required evidence fields and rejection of every non-ALLOW policy outcome, including HANDOFF. Map bootstrap and reconciliation authorization explicitly too. Do not expose a tool or introduce another PolicyEngine. If richer public fields are necessary, include their exact T3 contract and changed scope before human review. Add native-shaped ML19/ML09 fixtures; **NOT_RUN**.

**F4 — P2: request/receipt and terminal-history retention contradict the bounded-memory promise.**

Invariant: a live owner has bounded retained bookkeeping while matching requestId/digest retries never trigger another activation.

Proposed contract: SPEC lines 28, 52, 64, 84, 115 promise bounded memory and replay of the original operation, including immutable request snapshots. Quotas bound concurrent work/live generations, not the lifetime count/bytes of completed requestIds, terminal receipts, disposed generation history or reconciliation attempts. No retention/expiry/tombstone semantics are defined.

Counterexample schedule (deduced, NOT_RUN): submit N sequential successful replaces with distinct requestIds; let every old generation dispose before the next replace. There is one mutation at a time, no leaked pins and no retained live retired generation. Every concurrency quota continues to pass. Retaining each original result/request/receipt to satisfy arbitrary later duplicates grows without bound. Evicting them silently instead permits an old request to be reactivated (or changes a promised replay into a stale/conflict response). WeakMap receipt authentication cannot deduplicate string requestIds after their native operation record is gone.

Observable wrong result: either monotonically growing owner memory/inventory or an undocumented breach of idempotency after eviction. No runtime memory measurement is claimed.

Minimal contract repair: choose a numeric retained-request/byte budget and terminal-history/attempt policy. A sufficient local solution is bounded owner-lifetime request tombstones/results with quota refusal for **new** IDs before activation when exhausted, while existing IDs still resolve/conflict without reactivation; specify how larger snapshots/terminal generations compact. Alternatively define an explicit retry horizon and non-reactivating expired-key behavior. State duplicate-versus-quota/revision precedence. Pending resources/decisions must never be evicted to meet bookkeeping limits. Add long sequential history and oldest-key retry cases to ML07/ML17/ML20; **NOT_RUN**. No durable database is required.

**F5 — P2: sharing the prepared host does not define iterative dispatch of declared hooks.**

Invariant: a generation advertises only hooks actually dispatched by its supported runtime profiles, with one defined order and invocation cardinality.

Proposed contract: SPEC lines 68–72 call for declared hooks, one prepared host shared by single_pass/iterative, and all announced hooks/ports wired before ACTIVE. No profile-specific hook eligibility or managed finalization adapter is defined.

CURRENT evidence: single_pass invokes `host.listeners('turn/end')` in `kernel/kernel-runtime.ts:635–649`. In the iterative source, the only `runGate` call is turn/before-step at `iterative-runtime.ts:790–804`; model/tool pipelines dispatch their own points, but `finalize` at lines 1569–1641 calls `recordAuditOutcome` and `recordTelemetry` directly and never iterates host turn/end listeners. Audit and telemetry at lines 1644–1722 also retain direct profile-specific behavior. Merely substituting the same prepared host cannot make a new turn/end capability listener run.

Counterexample schedule (deduced, NOT_RUN): publish a READY generation declaring a turn/end capability hook used for per-turn observation/cleanup. Its single_pass turn invokes the hook; an iterative turn finishes through direct finalization and invokes it zero times. Inventory nevertheless labels the generation ACTIVE and its declared hooks wired. A naive additional listener pass can instead double-run the fixed host audit/telemetry if the old iterative direct finalization remains.

Observable wrong result: the same advertised hook is silently inert in one profile, or fixed finalizers execute twice after an unspecified adapter choice.

Minimal contract repair: define dispatch/support per hook and runtime profile. Either explicitly route managed iterative finalization through a single native host finalization primitive, specifying ordering relative to checkpoint/log/audit/telemetry and early failures, or reject unsupported hook/profile combinations before activation/publication and keep their remaining parity requirement mandatory. Resolve the managed audit label at the same boundary. Test exact hook/finalizer counts and order for both profiles in ML01/ML16/ML17, including failure exits; **NOT_RUN**. This repair must reuse the true runtime/pipeline rather than create a manager executor.

**Design decisions that are sufficiently explicit for this foundation.** The selected immutable-generation/local-owner design is proportionate. Restart-only remains the rollback baseline; mutating the active host, a second dependency resolver/registry/executor, and another durable journal are correctly rejected. Source inspection confirms that the present host boot/order, capability adapter, journal adapter and Hybrid gateway capture are the right seams; it does not prove that the new helper or public API exists.

The proposed contract explicitly protects optional sandbox without making it required; uses the same captured controls while separating registration cleanup from borrowed-resource ownership; authenticates owner/lease/receipt objects by native identity; binds tenant/agent/version/generation; fences new admissions at commit and close; preserves pre-admitted uses; distinguishes observer cancellation from native work; owns late acquisitions and boot failure cleanup; requires disposer singleflight/reverse sequencing, preserves the primary boot error, and reports hang/failure honestly. It also forbids mutation reentrancy/self-wait, requires pre-activation/pre-commit policy, fences uncertain publication evidence, and makes reconciliation append another observation without reactivation or rollback. Those are suitable proposed invariants. F1–F5 prevent treating their implementation boundary as fully settled.

The evidence-reconciliation design correctly acknowledges that AuditSink has no deduplication/readback and that process-local pointer publication is not a durable commit. Hung native callbacks/disposers may remain pending; this lane does not demand killing arbitrary JavaScript, production rollout, or cross-process availability guarantees. Future native fixtures must still prove all of these behaviors, including late acknowledgments, close dominance, reentrancy and cancelled waits. This review proves none of them operationally.
