## 3. PROPOSED — escolha mínima e composição conectada

Alternativas avaliadas: (a) apenas trocar Map por PG, rejeitada por closures, identidade aleatória, pause async e ausência de pai0016; (b) executar a fachada dentro do `OperationalExecutionWorker` atual, rejeitada por buffering do audit e dupla factory/loop; (c) migrar todo o worker `kernel`/legacy, adiada por expansão de capabilities/policy/protocolos; (d) **adapter published por inbound**, selecionado: reusa ingresso, completion, execução/steps/journal PG e o kernel0214, acrescentando só vínculo/state/evidência do adapter e fencing necessário. Não criar broker, pacote, provider ou política paralela.

```text
API webhook autenticado/tenant resolvido
  -> receiveInboundMessage + inbound.process [atuais, duráveis]
worker published-agent / postgres-v1 [opt-in proposto]
  -> load inbound + sessão/pinned version [atuais]
  -> admitInbound + claimInbound [novos; pais0016 + sidecar na mesma tx]
  -> executePublishedAgent -> executeConfiguredAgent [atuais; contexto host novo]
     -> preparação validada / reidratação do planner0214
     -> createOperationalHarness [MESMA factory pública, uma por tentativa ativa]
        -> controls obrigatórios + guarded PG ports -> única tool pura atestada
     -> fechar entrada local -> evidência/fechamento PG -> trace mascarado
  -> completeInboundRuntime [atual; idempotente pelo inbound + trace fixo]
  -> ACK do inbound outbox [atual]
```

Reentrega de **mesma execução fechada** lê a projeção persistida, sem outra factory/model/body, e repete somente completion/ACK idempotentes. Uma tentativa retomada de ponto seguro compõe novamente a factory pública; nunca invoca classes de runtime nem o antigo pipeline diretamente.

### 3.1 Port do host, explicitamente NOVO

Adicionar um segundo argumento opcional e exclusivamente in-process a `executeConfiguredAgent(input, host?)` e `executePublishedAgent(input, host?)`. O argumento proposto `ControlledKernelHostContext` é exportado pela raiz platform; agent-core apenas o encaminha. Não adicioná-lo a `TestLabInput`, schemas HTTP, config de agente, runtime.context público ou SDK. Assinaturas existentes de um argumento continuam válidas e locais.

Contrato **proposto**, não chamadas existentes:

- `identity`: `{ tenantId, executionId, correlationId, traceId, inboundMessageId, conversationId, sessionId, agentId, versionId, attempt, workerId, requestDigest }` já validado pelo adapter. A fachada compara cada binding com input/versão, sem confiar em branded cast.
- `signal`: AbortSignal de tentativa, obrigatório. `expiresAt`: deadline absoluto do kernel, definido uma vez depois da preparação e persistido; ausência antes desse marco significa “kernel ainda não iniciado”, nunca Infinity para executar.
- `ports`: o contrato privado atual `ControlledKernelCompositionPorts`, promovido a tipo suportado somente para composição confiável. Nenhuma dependência de persistence em platform/harness.
- `state`: snapshot JSON validado do adapter ou null. Não contém handler, validators, gateway, closures, token, grant booleano ou secretRef.
- `continuation`: port novo com `saveResumePoint(snapshot, checkpointDigest, evidenceSequence)`, `close(snapshot, runtimeResult, trace)` e `poison(phase, reason)`. Cada operação é await, vinculada ao fence; nomes são **novos**. `close` persiste envelope de execução/result e a projeção após todos os ACKs obrigatórios, ou falha sem autorizar sucesso.

A fachada mantém preparação/policy/output/projeção atuais; o host só seleciona armazenamento, IDs, clock/deadline e reidrata estado validado. O driver não pode fornecer um executor alternativo, omitir controlo ou transformar deny em allow. No novo perfil, ausência de port obrigatório recusa antes do modelo; nunca cai em `createLocalControlledPorts`. Test Lab/inline sem host seguem a composição local aprovada0214.

### 3.2 Identidade e correlação, sem autoridade do corpo

No primeiro claim, obter tenant da conexão/evento validado e conferir mensagem, conversa e sessão no banco. Chave idempotente interna proposta: `published-inbound-v1:` + SHA-256 UTF-8 da tupla canônica `[tenantId,inboundMessageId]`; tamanho <200. `externalMessageId`, texto, traceId recebido, approvalId, correlationId e ID de sessão não substituem essa chave.

`admitInbound` cria exatamente um `exec_<UUID>` pela factory de IDs existente, um TraceId pela factory platform e vínculo imutável. Correlação raiz é o `event.correlationId` persistido no ingresso, conferido com o inbound; conservar também ID do outbox para witness. Não gerar outro correlationId na0214 quando host presente. Se a API recebeu outra correlação numa redelivery, ela continua correlação de transporte; não muda o turno existente. `traceId` também não deriva de uma nova tentativa.

Runtime público recebe `executionId`, `traceId`, `correlationId`, conversationId, sessionId e fingerprint do binding. A operationKey permanece **a fórmula existente** `${executionId}:s${stepNumber}:${toolId}` (`iterative-runtime.ts:1494–1500`); sem attempt no prefixo. Attempt do lease e attemptId do efeito são identidades distintas. Fonte da authority, journal, steps, audit/log, callbacks, trace e completion deve permitir join pelos mesmos IDs; receipt de approval inclui também seu ID e inputHash. Nenhum novo ID público de mensagem ou envelope é exigido.

Digest de pedido inclui tenant/inbound/conversa/sessão, versão fixada, config/prompt checksum, versão do adapter, perfil/policy, fingerprint, entrada/história normalizadas e redigidas, actor canônico, bindings configurados de knowledge e limites de orçamento. Exclui attempts/timestamps de retry, funções e signal. Usar canonicalização/hash existentes (`canonicalizeCapabilityInput` para input de capability; canonical JSON para snapshot), sem usar JSON.stringify não canônico como equivalência de autoridade. Mesmo inbound com digest diferente é conflito; nunca “última escrita vence”.

Admissão antecede o modelo, não exige que a preparação toda já terminou: o `ExecutionSubmission.runtime` inicial é um bootstrap JSON válido montado de IDs/input/versão/config/budget conhecidos, sem funções nem autoridade de execução. `prepared`/started_at/expires_at começam null. Adicionar ao port continuation o método **novo** `startPrepared(fence, prepared, runtimeInput)` para CAS write-once da preparação validada, seu digest e início/deadline, antes de qualquer `model/request`. O runtime realmente executado é conferido com esse payload preparado; não executar cegamente o bootstrap persistido. Reentrega carrega o prepared existente e verifica o digest, sem renormalizar histórico com mensagens novas nem renovar deadline. Antes de startPrepared, morte do processo é S0 seguro. Não editar o request original0016 depois de admitido.

Para esse bootstrap, propor o export puro `prepareControlledPublishedAdmission({version,input,actor,gateway})` no módulo continuation: extrai a normalização/bounds atuais e a montagem de inventário/fingerprint da0214 e retorna input canônico, hashes e runtime bootstrap. O host fornece versão já lida do ControlPlaneStore e gateway controlado; a fachada revalida os mesmos bindings. Não chama `planTools` antes da guarda de saída, provider, authorizer, approval ou handler. É API **nova proposta**, não deep import autorizado do core privado pelo host. Separar bootstrap puro de preparação completa evita ter de serializar closures ou inventar um método atual do store.

Worker publicado hoje não fornece actor de operador: manter identidade System controlada e authorizer confiável da factory controlada, não copiar permissions de payload. Para testes de approval, o host injeta um actor/authority sintéticos confiáveis; isso não habilita canal de aprovação automática nem novo fluxo público. Reidratar identidade não equivale a reaproveitar decisão de autorização: reavaliar authorizer/policy/takeover antes de novo dispatch. O opt-in conserva também o worker atual sem approvedKnowledge/resolver injetado: perguntas institucionais continuam com a resposta segura atual quando não há fonte. Não habilitar resposta RAG/`knowledge.status=answered` nesse perfil por esta SPEC. Resolver institucional durável e revogação até a publicação da resposta exigem extensão própria; não persistir snippets aprovados como autorização perpétua.

| `loadBoundState(tenantId, executionId)` | Valida schema/digests, FK, IDs, revisão, relação checkpoint/evidence/resume seal. Retorna snapshot/trace ou erro fechado. Não lê outro tenant por fallback. |
| `saveResumePoint(fence, snapshot, checkpoint)` | Sob lock de execução e binding, valida fence vivo, state_revision e sequence esperados, grava checkpoint0019 + snapshot/revision/seal de evidência juntos. Nenhum upsert de estado atrasado pode sobrescrever snapshot novo. |

| `poison(fence, phase, reason)` | Latch monotônico: grava primeiro fault/dispatch_closed e evento quando DB disponível. Segundo fault não apaga o primeiro. Fence perdido impede alterar vencedor; falha de persistência mantém somente resposta segura local e bloqueia sucesso na recuperação. |

Reusar `PostgresOperationalExecutionStore.heartbeat/transition/cancel/get/listEvents` e a state machine0018. `close` usa helper transacional da transição, não invoca método que abre BEGIN dentro de BEGIN. `claimNext` **e `recoverExpired` genéricos** devem excluir qualquer execução com binding controlled publicado (anti-join tenant/exec), evitando roubo ou recuperação sem fence pelo worker neutro. A admissão interna valida namespace e associa row ao inbound; o endpoint genérico `/v1/executions` nunca cria esse binding e não escolhe adapter por context.values. Copiar JSON/UUID/fingerprint no corpo não concede admissão. O cancel autenticado de row bound ainda QUEUED continua permitido e não precisa de lease de worker; CLAIMED/RUNNING mantêm409.

Uma opção interna de fence nos adapters operacionais step/journal é necessária: todos os writes devem travar a linha0016 e conferir `(tenant,exec,owner,attempt,lease_until>clock_timestamp(),state)` **na mesma transação** que a alteração. Extrair helpers transaction-free do código atual para permitir a composição; não aninhar BEGIN/COMMIT, compartilhar client concorrente ou manter uma conexão por todo o turno. Reuso de pool usa `withTenantContext`/`withTenantTransaction`, com limpeza/destroy de conexão na falha, como hoje. Ordem de locks única: execução → binding → step/checkpoint ou journal → evidência/audit. Uma operationKey precisa corresponder à execução/step/tool desse binding; não aceitar starts por chave alheia.

Stores operacionais genéricos sem fence mantêm o comportamento antigo para execuções **não bound**. Para bound, writes sem fence devem falhar, inclusive `recordStep/saveCheckpoint`, journal transitions e transições0016 de worker antigo. Não confiar apenas no anti-join de um worker novo: preflight/role e rollout impedem executável antigo de servir filas bound (ver8). Não alterar regras de tenants de stores antigos.

Callback durável: substituir `toolAuditEvents.push` somente nesse opt-in por callback do compositor que valida pais tenant/trace/agent/version e grava o mesmo PluginAuditEvent através de appendEvidence com key estável `${operationKey}:callback/tool`. Receipt contém mirrorAuditId e digest; repeating key não insere novo audit. Antes de completion, o compositor exige receipts para todas as tools tentadas. Chamar então `completeInboundRuntime` com `toolAuditEvents:[]`: seu contrato atual valida os eventos fornecidos e aceita array vazio (`postgres-audit.ts:564–619`); os tool audits já estão duráveis. Não fazer push+mirror+completion triplo, não alterar validação geral, não passar callback arbitrário não durável. Demais caminhos mantêm o buffer/completion atual. A transação de completion ainda grava seus próprios audits de integração/handoff e trace/marker; esses são fatos de conclusão inbound, distintos do audit obrigatório do turno.

`close` usa um classificador **específico do perfil**, não `classifyRuntimeResult` neutro que promove falhas técnicas a FAILED_RETRYABLE e APPROVAL_REQUIRED a WAITING_APPROVAL0015. COMPLETED validado e sem fault → SUCCEEDED; CANCELLED → CANCELLED; todos os outros21 stops (excluindo os dois anteriores do total23) → FAILED_TERMINAL, com failure.kind POLICY_DENIED para POLICY_DENIED/UNSAFE_REQUEST, UNKNOWN_EFFECT para incerteza de dispatch/settlement e SEMANTIC_TERMINAL nos demais. Nenhuma nova approval pendente ou retry de modelo/tool é criada. Recuperar lease após crash em ponto seguro continua permitido; repetir turno já fechado não é recuperação de lease.

O `RuntimeResult` gravado em0016 e visível pelo GET/trajectory usa a **mesma decisão final projetada**, não o retorno bruto: stopReason do veto final, response segura de handoff e toolResult omitido quando turno não COMPLETED, contadores/usage reais conservados. Trace falho mantém toolResults.output=null; resultado bruto/CONFIRMED ficam apenas nos fatos privados sanitizados. Dessa forma o endpoint neutro não vaza sucesso residual que a fachada mascarou.

## 5. Reidratação: fechar as closures antes de prometer restart

Snapshot do adapter é independente do checkpoint cognitivo, mas ambos têm seal atômico. Schema `controlled-published-state-v1` inclui:

- IDs/requestDigest/versões e fingerprint; normalização/parse version; estado de preparação, safe response/risk/policy/knowledge/sourceVersion, prompt checksum e texto redigido necessário para reconstruir a requisição do modelo. Config/versão vêm do ControlPlaneStore, nunca do modelo.
- `output` já guardado, `providerInvoked`, payload/usage do modelo necessários à reconstrução, `names`, `planSealed`, `finalIssued`, posição esperada do planner; etapa completed/pending do checkpoint. Não presumir expectedStep=1 depois de restart: pendingDecision do kernel pode dispensar decide; derivar posição de checkpoint+plano e validar ambos.
- Cada attempt N≤1: dados canônicos de comando + inputHash/descriptorFingerprint (sem funções), phase/cause/closed/operationKey, policyAllowed/denied, approvalRequired/consumed e receipt de consumo (ID/inputHash/executionRef), output validado, log/callback/result ACKs e suas evidence refs, ledger start/finish, settlement outcome. Booleanos isolados nunca substituem essas refs.
- Primeiro fault e dispatch_closed monotônicos, stop candidato, budgetUsage cumulativo, deadline absoluto, evidence cursor e último ponto seguro. Tempos de spans medidos por tentativa, acumulados sem inventar duração durante downtime.

Ao reidratar, resolver a **mesma** versão pinned (PUBLISHED/ARCHIVED no comando publicado); comparar config/prompt/policy e descriptor/handler/validators com atestação **privada atual**, fingerprint e formato. Não serializar/reconstituir WeakMap atestado a partir de strings. `PreparedCapabilityCommand` é reconstruído por rotina privada nova de reidratação canônica: valida igualdade estrutural/bounds/digest e funções atestadas sem reaplicar transformações ao input/output já canônico. Novo input HTTP continua parse1. `approvalMatchesAction`/inputHash permanecem sobre o mesmo valor. Falta de atestação/versão/knowledge revogada → STATE_CONFLICT/POLICY_DENIED seguro, zero provider/body/consume; sem fallback para versão nova.

**Pontos seguros permitidos:** (S0) admitido, kernel ainda não iniciado; (S1) resultado do único modelo e guarda de saída persistidos, uso debitado, checkpoint correspondente ao passo RESPOND inicial e snapshot do planner selados; (S2) tool resultado, journal, approval settlement, log/result/callback/audit, step/checkpoint todos ACK e selados; (S3) execução/trace fechados, faltando completion/ACK inbound. A passagem S1→tool usa a decisão/plano canônico persistido; nenhum segundo modelo nem nova intenção. Revalidar safety/knowledge/authorizer/pause/cancel/deadline antes de novo body.

`saveResumePoint` é o barrier explícito após os awaits obrigatórios bem-sucedidos, não simplesmente “último checkpoint encontrado”. Se existe evento/intent posterior ao último seal, step in-flight, consumed sem receipt, journal RESERVED/EFFECT_STARTED/UNCERTAIN ou ACK terminal incompleto, **não** retroceder ao seal e repetir. Encerrar como uncertain/evidence failure com handoff; preservar todos os fatos. CONFIRMED privado sem conjunto completo de ACKs não promove turno a sucesso. Depois de S2, pode finalizar sem body a partir do resultado selado. Depois de S3, apenas completion/ACK.

Cada chamada de modelo tem intent durável antes da chamada e request redigida reconstruível (prompt/history/context/model/profile/checksum/fingerprint, não somente promptLength). Persistir guarded output, usage e model/result antes de S1. Crash com model/request sem S1 não chama o modelo outra vez: failed/handoff. Não prometer exatamente uma execução externa; o perfil nem permite provider externo. O critério é upper bound de chamadas e continuidade nos pontos seguros acima.

O fechamento durável do adapter não depende de reabrir o `InvocationEvidenceState` local já fechado. Não reconstruir êxito a partir de resultado antigo ou de ausência de fault em RAM.

Para linearizar pause com admissão quando ainda não existe linha0027, o adapter deve fazer INSERT default paused=false **ON CONFLICT DO NOTHING** e depois lock/read da linha na tx de admissão; nunca chamar setPaused(false) como inicialização. Cancel remoto só vence antes do claim (ou em QUEUED depois de recovery); signal ativo é a garantia cooperativa adicional. | Janela/falha | Estado observado em PG | Retomada permitida e resultado |

### 7.1 Como obter o seal sem hook fictício no kernel

O adapter controla planner/model gateway/guarded ports. O model gateway guarda o output validado e uso em estado pendente antes de devolver `ModelResult`. O wrapper `stepStore.saveCheckpoint(checkpoint)` inspeciona o step/contexto real e, quando todos os pré-requisitos S1 ou S2 já estão ACK, chama o método **novo** de persistence `saveResumePoint` para gravar checkpoint e snapshot do adapter na mesma tx. Nos demais checkpoints grava apenas progresso não retomável, marcado como tal. Não chamar `saveResumePoint` antes de o runtime produzir checkpoint válido, não fabricar BudgetUsage/stepNumber, não mudar digest do kernel sem `validateCheckpointIntegrity`/função atual de criação.

S2 só existe quando ACKs de settlement/log/callback/step estão de fato concluídos; caso o kernel grave checkpoint antes de algum ACK obrigatório, esse checkpoint **não** é S2. Uma gravação posterior do adapter pode selar a mesma revisão/digest depois de conferir todos os ACKs sem executar novo passo. Sequência de writes deve ser provada pelos testes reais, sem assumir um callback inexistente `onResume`/`afterCheckpoint`.

`executeAuthorizedPreparedCommand` CURRENT recebe `admit:()=>boolean` (`plugin-execution-core.ts:188–216`); não passar uma Promise, que seria truthy e abriria bypass. O wrapper `controlledRegistration.execute` deve primeiro await um preparo de admissão novo, que lê guardas PG e obtém o permit de6/D10. Depois chama a função existente com callback **síncrona**, que compara permit/IDs/attempt/signal/expiry/fault/closed e chama o handler capturado no mesmo turno síncrono. Nenhum await entre essa última verificação local e a chamada do handler. O permit não é token público nem substitui authorizer/policy/approval. Isso preserva a garantia de fechamento da0214 e permite pausa PostgreSQL async sem modificar a ABI do executor privado.

Preflight verifica versão/schema, e role antiga perde autorização de escrita das linhas bound por guarda de DB/migration, além de guardas no código; não alegar segurança só de uma variável de ambiente.

**Guarda DB proposta para mixed writers:** triggers nos writes de rows bound de0016/0019/journal verificam contexto transacional interno de execução/attempt e estado/fence no pai; a role serving não pode desabilitar triggers. O contexto é defesa contra software antigo, não credencial contra um processo serving malicioso com capacidade SQL. Constraints/RLS/locks continuam autoridade. Anti-join evita roubo normal; rollout exclui concorrência com binário antigo antes do enable. Se essa guarda não for implementada/provada, mixed versions são **não suportadas** e qualquer worker antigo ativo bloqueia enable; não apresentar rollback online como seguro.

Rollback: desligar novo ingresso ao perfil e drenar/pausar filas; manter novo binário para fechar/completar bindings pendentes, ou deixar handoff auditado sem executar. Não voltar binário antigo para schema/tenant com bindings ativos, não remover tabela/migration nem resetar journal/checkpoint. Reverter configuração não apaga dados nem autoriza replay. S3 pode completar com mesmo binário; registros incertos exigem decisão/handoff, não um botão de retry automático. Migração interrompida deve rollback/retomar pelo runner checksum atual.
