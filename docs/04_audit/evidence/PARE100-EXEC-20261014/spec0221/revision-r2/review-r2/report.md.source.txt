## Official PG16 premises

The documentary basis supports the chosen lock lifetime, reentrancy and nonblocking primitives; it does not implement database guards. See [PG16 advisory locking](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS) and [advisory functions](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS). The migration runner's key-space distinction is consistent with that documentation.

A single transaction alone is insufficient to freeze multiple queries under READ COMMITTED; the recovery requirement for a fresh REPEATABLE READ snapshot is meaningful. See [PG16 isolation](https://www.postgresql.org/docs/16/transaction-iso.html). Trigger timing and data visibility must still be implemented correctly, including the distinction between BEFORE checks and final deferred checks; see [CREATE TRIGGER](https://www.postgresql.org/docs/16/sql-createtrigger.html) and [trigger visibility](https://www.postgresql.org/docs/16/trigger-datachanges.html).

Synchronous commit conditions acknowledgment on WAL processing, while asynchronous acknowledgment can precede crash safety. See [PG16 WAL configuration](https://www.postgresql.org/docs/16/runtime-config-wal.html). That premise is insufficient to certify the proposed no-logical-change UPDATE barrier or its native crash behavior. SP09/SP18 remain necessary future evidence after explicit T3.
