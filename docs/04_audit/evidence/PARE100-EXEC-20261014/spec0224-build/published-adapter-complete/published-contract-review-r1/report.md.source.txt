## What is technically coherent already

The selected vertical outcome is concrete: trusted server selection, immutable mode/digest, actual published facade/host, deterministic M1 → actual constant tool → M2, native completion and outer ACK. The proposed 3/2/1 step/model/tool budget, 9024 synthetic-unit budget, 512 output reservation and fake byte64 pair are explicit proposed deltas. The native V2 CAS/current-token requirement, separate bounded host reference, C1/C2-only dispatch recovery, conservative OPEN/UNKNOWN treatment, final M2 projection and CLOSED-only completion replay are sensible choices. The exact `controlled-published-v1` marker is preserved. Rollback retains generation2 readers/writers for written complete rows and stops new admissions; it does not send old binaries onto V2 state. New GUCs are accurately described as stale-software guards, not credentials against arbitrary SQL from a malicious serving process.

The unchanged tool is small, pure and NUL-free by its actual S14 handler/validator. PA03 cannot prove a 4096-byte/NUL consumer result. PA15 explicitly remains blocked on separately authorized full-domain work; that is honest staging, not full224-domain acceptance. ### I1-F01 — HIGH — The security migration and outer-claim transaction are not yet an exact reviewable contract

Confidence: **HIGH**. Canonical-review blocker: **yes**. Claim type: `CONFIRMED_DESIGN_DEFERRAL`.

The proposal defers numeric migration slot, exact trigger/preflight/claim-caller design and checksum to the lead before canonical approval. Existing 0029 has no outbox_events/outbox_attempts writer guard. The candidate supplies intended outcomes and GUC names but no exact trigger lookup/locking behavior, candidate predicate placement, unsupported-row behavior, transaction GUC initialization point, renewal/ACK/fail coverage, or trigger/dependency ordering. A requirement to reject old claims is not that executable design.

A canonical human would be approving unresolved security/schema choices; a later trigger or claim implementation could consume attempts, block all claims, introduce lock inversion, or bypass generation checks. These are possible consequences, not observed runtime failures.

### I1-F03 — HIGH — The sole complete checkpoint phase has no constrained settlement classification

Confidence: **HIGH**. Canonical-review blocker: **yes**. Claim type: `NATIVE_PHASE_CONTRACT_GAP`.

Every new CAS, including terminal and UNKNOWN writes, requires phaseType complete.checkpoint; commitKind distinguishes only CHECKPOINT_ONLY and RESUME_POINT. The current native settlement allowlist admits step.saveCheckpoint but not complete.checkpoint, and both continuation.run and store.beginPhase classify permission by that list. Terminal wrappers close dispatch before the checkpoint await; recovered FAULTED/OPEN is settlement-only. Merely forwarding the new phase encounters the active-only guard. The phrase existing settlement-only exception does not choose the new classification, actor/cancellation route or allowed next-state changes.

Terminal success checkpoint/UNKNOWN recovery can be rejected after local close, or an overbroad repair can allow active progress through a settlement fence. This is a specified-contract gap, not a reproduced runtime failure. Retaining RESERVED when diagnostic CAS is unavailable remains a valid fail-closed fallback.
