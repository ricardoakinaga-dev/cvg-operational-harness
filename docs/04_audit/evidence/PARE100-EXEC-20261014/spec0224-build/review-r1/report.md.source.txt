**I1-R1-001 — HIGH / P1: A fully persisted tool result cannot resume across the post-result checkpoint boundary (TR06)**

Anchor: `packages/harness/src/iterative-dispatch.ts:465`; related: `packages/harness/src/iterative-dispatch.ts:714`, `packages/harness/src/iterative-dispatch.ts:723`, `packages/harness/src/iterative-runtime.ts:765`, `packages/harness/src/iterative-runtime.ts:983`.

Own public factory reproduction saved a valid V2 checkpoint with stepNumber=0, pendingStepNumber=1 and a COMPLETE 4096-byte result; the native step ledger already had step 1 SUCCEEDED. Subsequent writes were refused to preserve that boundary, then the factory/runtime was recreated over the same memory store and journal. Resume returned INTERNAL_FAILURE: Step transition SUCCEEDED -> RUNNING is not allowed. One body and one model call total; no replay occurred, but the saved result could not reach the next decision.

The missing-result recovery guard only handles SUCCEEDED without an observation. When the full observation exists, pendingDecision is dispatched again and beforeDispatch unconditionally records RUNNING over the already successful native step.

Required behavior: SPEC0224 sections 2, 3.2 and TR06: acknowledged complete results survive recreation and resume without another tool body.

Reproduction: repro.test.ts test 'TR06 resumes a durably saved full result after recreating the public runtime'; run argv in repro-r2.command.json. Deterministic factory/runtime recreation in one process using real in-memory stores and synthetic ports; not an independent PostgreSQL process-restart run. The later public PG addendum fails before this saved-result boundary, so it does not independently corroborate this exact failure.
